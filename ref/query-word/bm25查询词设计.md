这是一个非常典型且极具实战价值的 RAG（检索增强生成）架构问题。你的架构设计非常巧妙：**Tree-sitter 提取结构 + 语义转换**，这实际上将代码检索变成了“代码 API/实体描述检索”。
在这种架构下，BM25 索引里存的不是代码逻辑细节（如 `for i in range(len(list))`），而是代码的**结构化身份和语义概括**（如 `user service get user by id`）。
因此，BM25 查询词的规范必须与你的索引结构严格对齐。以下是针对你项目的查询规范设计及 LLM Prompt 策略：
---
### 一、 核心原则：理解你的 BM25 索引特征
既然你的 BM25 路径对实体仅做了 `.` 和 `_` 转空格的处理（如 `UserService.get_user_by_id` -> `User Service get user by id`），这就意味着：
1. **BM25 擅长匹配“命名习惯”**：它捕捉的是开发者如何命名类、方法、变量。
2. **BM25 不包含实现逻辑**：如果用户问“如何遍历字典并删除特定元素”，BM25 索引里大概率没有这些词，只有 `delete dict item` 或 `remove entry`。
3. **分词边界由你定义**：由于你已经把 `_` 和 `.` 替换成了空格，BM25 的分词器实际上是按空格切分的。
### 二、 BM25 查询词的 4 条规范
基于上述特征，让 LLM 生成 BM25 查询词时，必须遵循以下规范：
#### 1. 命名还原（去自然语言，还原标识符风格）
将自然语言的提问，还原为开发者写代码时会用的“动词+名词”组合。
* **反例**：`how to get user information`
* **正例**：`get user info` / `fetch user detail`
#### 2. 驼峰/蛇形拆解（与索引预处理对齐）
**这是最关键的一点！** 既然你的索引把 `get_user_by_id` 拆成了 `get user by id`，那么 LLM 生成的查询词也**必须是拆分后的形态**，否则 BM25 会把 `get_user_by_id` 当成一个整体词去匹配，导致漏召回。
* **反例**：`getUserById` 或 `get_user_by_id`
* **正例**：`get user by id`
#### 3. 聚焦实体与动作，去除逻辑描述
BM25 索引里没有代码逻辑，只有实体定义。所以查询词必须是“找什么实体/方法”，而不是“怎么做”。
* **反例**：`check if email is valid and throw error` (逻辑描述)
* **正例**：`validate email format` / `check email` (方法命名风格)
#### 4. 动作同义词扩展（Coding Thesaurus）
代码命名中，同义词极其常见（如 add/create/insert, get/find/query/fetch, delete/remove）。LLM 需要生成这些同义词以扩大召回。
* **正例**：`delete user` OR `remove user`
---
### 三、 LLM Prompt 设计：一次性生成双路查询词
为了让 LLM 同时生成高质量的向量检索词和 BM25 检索词，你需要使用 **Few-Shot Prompting**，并明确定义两者的分工：
* **向量检索词**：负责语义匹配，保留完整意图，使用自然语言和业务术语。
* **BM25 检索词**：负责结构匹配，还原代码标识符，使用空格分隔的词汇。
#### 推荐 Prompt 模板：
```markdown
你是一个代码检索专家。用户将提出一个关于代码库的问题。你的任务是将其转化为两种检索查询词，用于从代码库中检索相关代码片段。
【背景知识】
代码库已经通过 tree-sitter 提取了代码实体（类名、方法名、变量名等），并转换为语义描述。
特别地，对于 BM25 检索引擎，代码实体的下划线(_)和点(.)已被替换为空格。例如：`UserService.get_user_by_id` 在索引中表现为 `User Service get user by id`。索引中不包含具体的代码实现逻辑，只有实体名称和语义描述。
【任务要求】
请根据用户问题，生成两类查询词：
1. **Vector Query (向量检索词)**：保留用户的完整语义意图，使用自然语言描述，重点突出“想做什么”和“业务概念”。
2. **BM25 Query (关键词检索词)**：将意图转化为代码命名的风格（动词+名词），必须将驼峰或下划线命名拆解为空格分隔的独立单词，并补充编程中常见的动作同义词（如 get/find/fetch, add/create/insert, delete/remove）。去除逻辑修饰词。
【输出格式】
严格以 JSON 格式输出：
```json
{
  "vector_query": "...",
  "bm25_query": "..."
}
```
【示例】
用户问题：How to delete a user from the database if they are inactive?
输出：
```json
{
  "vector_query": "delete inactive user from database",
  "bm25_query": "delete remove user inactive database repository"
}
```
用户问题：我想看看怎么解析JWT token并获取用户ID
输出：
```json
{
  "vector_query": "解析JWT token获取用户ID的逻辑",
  "bm25_query": "parse validate jwt token get fetch user id subject claim"
}
```
用户问题：{user_question}
```

### 四、 工程实现上的补充建议
当 LLM 生成了规范化的查询词后，在搜索引擎（如 Elasticsearch / Whoosh / Meilisearch）侧，还需要做一点适配：
1. **BM25 查询词的分词器设置**：
   确保你的搜索引擎在对 BM25 Query 进行分词时，使用的是**按空格切分的简单分词器**，不要再使用自然语言分词器（如中文的 ik 分词），否则可能会把 LLM 辛苦拆解出来的 `get user by id` 再次组合或错误切分。
2. **BM25 检索的算分逻辑**：
   LLM 生成的 `bm25_query` 可能包含多个词（如 `delete remove user inactive`）。建议使用 `Multi-Match Query` 中的 `most_fields` 或 `best_fields` 模式，允许文档只要匹配了其中的几个词（如匹配到了 `delete` 和 `user`）就能得到较高分数，而不是要求所有词都匹配。
3. **处理缩写与全称**：
   在 Prompt 的 Few-Shot 中，可以加入针对你项目特有名词的缩写/全称转换示例。例如用户问 `DB`，LLM 应该在 BM25 query 中生成 `db database`。
### 总结
在你的架构下，**向量检索负责捕捉“用户的业务问题”，BM25 检索负责捕捉“程序员的命名习惯”**。通过 Prompt 强制 LLM 将自然语言意图“降维”成空格分隔的、带有同义词的标识符词汇，是打通 BM25 召回率瓶颈的关键。
