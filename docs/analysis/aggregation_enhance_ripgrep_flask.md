# 聚合增强（Aggregation Enhance）基准测试分析报告：ripgrep 与 flask

## 1. 概述

本项目基于已有的 `once_cell` 聚合增强基准，新增了 `benchmark_agg_ripgrep` 与 `benchmark_agg_flask` 两个示例，用于评估在纯基线排序（`emb`、`bm25`、`minmax-0.5`）之上叠加离线关系增强（`+rel`）、文件级摘要增强（`+sum`）或两者兼有（`+both`）对检索效果的提升。

数据来源为各项目预生成的 `full_pipeline` 基准数据（无重新生成、无额外 LLM 调用），增强参数沿用生产配置默认值。评估尺度为 `All`（全部查询类型），top-5 下的 `F1_any` 为主要指标。

| 项目 | 查询数 | embedding chunks | BM25 chunks |
| --- | --- | --- | --- |
| ripgrep | 45 | 1798 | 1702 |
| flask | 45 | 679 | 1196 |
| once_cell（参照） | 39 | — | — |

输出报告路径：
- `crates/app/cce-e2e-tests/outputs/benchmark/ripgrep/aggregation_enhance/`
- `crates/app/cce-e2e-tests/outputs/benchmark/flask/aggregation_enhance/`

> 说明：`parity=yes` 表示走生产增强路径（可作为是否上生产的判定依据）；`exploratory` 表示与生产配置偏离的探索性方案。

## 4. 分析与发现

### 4.1 关系增强（+rel）普遍显著降低效果

三个项目一致地呈现同一趋势：叠加关系增强后，`F1` 大幅下降。

- ripgrep：emb F1 0.2388 → emb+rel 0.0885（-62.9%）；Recall 0.6081 → 0.2609，Precision 0.1556 → 0.0533。
- flask：emb F1 0.4177 → emb+rel 0.1949（-53.3%）；Recall 0.9185 → 0.4815。
- 一级命中（1st-hit rank）同步变差：ripgrep emb 2.34 → 3.67，flask 1.95 → 2.65。

**根因推测**：关系增强基于文件同批次（file-cohort）图对文档向量做按元素加权/重定向，其意图是让同文件/同依赖群组内的文档评分上浮以聚合相关上下文。然而在 top-5 检索中，它易把高分文档重新分配，导致本来已命中的相关项被挤出，同时召回大幅收缩。关系信号更多服务于“跨文件语义连带”，对精确命中（qualified/fuzzy）反而造成干扰。

### 4.2 摘要增强（+sum）近乎中性，个别场景小幅受益

- 各基线下 `+sum` 的 F1 变化基本在 ±0.2% 内；ripgrep 的 `qualified` 查询 emb+sum = +0.20 是唯一明显正向增益。
- `bm25+sum`、`minmax-0.5+sum` 在 ripgrep / flask 上几乎不改变指标（增益 0.00 或接近），说明文件级摘要向量与基线分数高度冗余，既未带来正向扰动也未造成明显回退。

### 4.3 既有基线内部差异

- **bm25**：ripgrep 上明显偏弱（F1 0.219），flask 上却是最强基线之一（F1 0.459）。这与两库的分词/文本覆盖差异相关。
- **minmax-0.5**：几乎一致地优于单通道 emb/bm25，是当前默认融合基线；其对增强的敏感度较低（增强后变化最小）。
- **嵌入召回**：flask 的 emb Recall 高达 0.9185，说明嵌入通道在 flask 上几乎穷尽全部相关项，增强提升空间本就有限。

### 4.4 增强对“融合基线的边际效应”

由于 `minmax-0.5` 本身已是混合信号，额外的 `+rel`/`+sum` 增强增益显著小于作用于单通道 emb 时。这说明增强的主要价值窗口在“纯嵌入通道 + 关系密集语料”，而在已融合的基线上发挥空间有限。

---

## 5. 结论与建议

1. **暂不建议上线关系增强（+rel）**：在其默认参数下，`+rel` 与 `+both` 在 ripgrep、flask、once_cell 三个项目上均导致 F1 实质回退（-3.8% ~ -72%）。关系增强的收益可能在更大语料、跨文件语义链需求下才会显现，需先在真实大规模数据上验证后再决定是否启用。
2. **摘要增强（+sum）风险低**：增益接近中性、几乎不回退，在特定查询（ripgrep qualified）可小幅受益。可作为安全选项保留，并建议结合参数调优（如提高 `+sum` 权重）做进一步探索。
3. **`emb+rel` 的 Recall 塌缩需要关注**：三个项目均出现 Recall 与一级命中同时恶化，属于结构性副作用，应优先排查 enhance 模块中关系图聚合的评分重分配逻辑。
4. **基线增强耗时可忽略**（复用已有向量，无 LLM 调用），便于放入常规回归验证流程。
