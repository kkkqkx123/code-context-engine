# Summary 功能集成分析

## 集成全景

Summary 功能贯穿配置 → 生成 → 存储 → 搜索 → 导出 → API/CLI 全链路：

```
Config Layer
  └─ AppConfig.summary / ProjectConfig.summary
      └─ SummaryGenerationStrategy (Auto / RuleBased / ModelEnhanced / Minimal)
          └─ Generator 选择
              ├─ RuleBasedGenerator (默认路径)
              └─ ModelEnhancedGenerator (LLM 增强路径)

Pipeline Layer
  └─ IndexingPipeline (Phase 5a, 紧随 chunking)
      └─ generate_with_groups_sync(parsed_file, processing_result) → FileSummary

Orchestrator Layer
  ├─ IndexOrchestrator::execute()  → 批量生成 + store_summaries()
  └─ HotUpdateCoordinator::update() → 增量更新

Storage Layer
  ├─ Qdrant (SummaryPayload, point_type="summary")
  ├─ BM25 (全文索引)
  └─ SQLite (file_summaries 表)

Search Layer
  └─ SummaryBoost (查询时对匹配文件加权)

Export Layer
  └─ include_summary → NL 文档导出

API Layer
  └─ POST /api/summary → 即席摘要生成

CLI Layer
  └─ cce summary generate --file
```

## 各层集成详情

### 配置层

| 字段 | 位置 | 说明 |
|------|------|------|
| `summary.strategy` | `summary.rs:27` | 生成策略: auto/rule_based/model_enhanced/minimal |
| `summary.max_summary_length` | `summary.rs:29` | 最大 token 数 (已修正注释) |
| `summary.max_entities` | `summary.rs:31` | 最大实体提取数 |
| `summary.max_imports` | `summary.rs:33` | 最大导入数 |
| `orchestrator.indexer.store_summaries` | `orchestrator.rs` | 控制是否生成并存储摘要 |
| `search.summary` | `search.rs` | 查询时 SummaryBoost 配置 |
| `export.include_summary` | `export.rs` | 导出时是否包含摘要 |

配置支持全局 (`config.toml`) 和项目级 (`.cce/.cce.toml`) 两层覆盖。

### 生成层

`SummaryGenerator` trait (`types.rs:224-271`) 定义核心接口：

```
generate(parsed_file)                         → FileSummary
generate_with_groups(parsed_file, groups)     → FileSummary (富化路径)
generate_batch(parsed_files)                  → Vec<FileSummary>
generate_batch_with_groups(...)               → Vec<FileSummary>
```

**RuleBasedGenerator** 流程：
1. `FileCategory::determine()` → 判断文件类型 (test/config/doc/generated/schema/minimal/normal)
2. 特殊类型走 specialized generator (test/config/doc/generated/schema)
3. 普通类型：提取主要实体（按调用次数、group type 打分）→ 提取 imports/exports → 生成 tags → 拼接 summary_text（按 token 截断）
4. 返回 `FileSummary`

**ModelEnhancedGenerator** 流程：
1. `FileCategory::determine()` → 若 `should_skip_model()` 则降级为 specialized
2. `ImportanceDecision::determine_generation_strategy()` → 决定 RuleOnly 或 ModelEnhanced
3. 若 ModelEnhanced：先走 RuleBased 生成基础摘要 → LLM 增强 → 解析模型响应 → 合并
4. 若 RuleOnly：降级为纯规则路径

Generator 选择 (`orchestrator.rs:236-258`)：
```rust
fn build_generator(config: SummaryConfig) -> Box<dyn SummaryGenerator> {
    if config.strategy == ModelEnhanced && (LLM client available) {
        ModelEnhancedGenerator::with_config(client, chat_cfg, config)
    } else {
        RuleBasedGenerator::with_config(config)
    }
}
```

### 管线层

`IndexingPipeline::process_file_internal()` (`pipeline_coordinator.rs:190-197`)：

```
parsed_file (Parser)
  → ProcessingResult (Grouper)
    → GroupConversions (AST-to-NL)
      → ChunkedResult (Chunker)
        → FileSummary ← Phase 5a — 使用 generate_with_groups_sync()
```

Summary 生成在 chunking 之后执行，结果作为 `ProcessedFile` 的字段附着。

### Orchesrator 层

**全量索引** (`orchestrator.rs:698-770`)：
- 使用 `generate_with_groups()` 对每个文件生成摘要（并发）
- 若 `processing_results` 和 `parsed_files` 数量不一致则降级为 `generate()`
- 通过 `storage.store_summaries()` 批量持久化

**增量更新** (hot update)：
- `SummaryUpdateProcessor` 实现 `UpdateProcessor` trait
- 处理已删除文件：调用 `remove_file_from_summary()`
- 处理已添加/修改文件：若解析结果未附着摘要则重新生成，然后批量存储

### 存储层

`store_summaries()` (`storage_coordinator.rs:698-770`) 三路持久化：

1. **Qdrant**：以 `file_path` 为 point ID，设置 `point_type: "summary"`，存储 `SummaryPayload` embedding
2. **BM25**：将 summary 转为纯文本存入全文索引
3. **SQLite**：写入 `file_summaries` 表（含 file_id、文本、配置快照）

`remove_file_from_summary()` (`storage_coordinator.rs:807-825`)：
- 仅清理 Qdrant（通过 `delete_by_file_path_scoped` 过滤 point_type="summary"）
- ⚠️ 不清理 SQLite `file_summaries` 表

### 其他层

- **搜索**：`SummaryBoost` 在查询时计算 query embedding → 搜索 summary 索引 → 对匹配文件做加权
- **导出**：`export_batch_with_summaries()` 将 summary 纳入 NL 文档
- **API**：`POST /api/summary` → 创建独立 `RuleBasedGenerator` → 解析文件 → 生成摘要（不持久化）
- **CLI**：`cce summary generate --file` → 调用 API

## Summary 与 Chunk 的关系

Summary 和 chunk 是**两条独立的平行产出**：

- Chunk：用于语义检索和 BM25 全文检索的最小单位
- Summary：文件级元数据，仅用于搜索时对匹配文件做加权

设计意图清晰：chunk 解决"找到相关内容"的问题，summary 解决"这个文件是否值得深入查看"的问题。两者不互相依赖，当前实现符合预期。

## 缓存问题说明

当前实现中没有摘要缓存或脏检测机制，每次全量索引都重新生成所有文件的摘要。由于摘要已持久化到 Qdrant + BM25 + SQLite，且向量存储本身没有"缓存失效"的概念，因此缓存本身不是必要组件。

**真正的问题在于脏文件检测与热更新的集成**——即增量索引时是否能正确识别已变更的文件并只重新生成受影响的摘要，详见下节。

## 现存问题

### 问题 1: `/api/summary` 路径受限

`handlers/summary.rs:148` 硬编码 `RuleBasedGenerator::new()`，且仅调用 `generate()` 而非 `generate_with_groups()`。

影响：
- 即席 API 不支持 model-enhanced 策略
- 缺少 grouper 处理后的实体信息，生成的摘要质量低于索引管线

### 问题 2: UTF-8 截断风险 (低)

`rule_based.rs:420-424` 使用字节索引切片 `&text[..split_point.saturating_sub(3)]`，可能截断在 multi-byte UTF-8 字符中间。

### 问题 3: 热更新脏文件检测集成缺陷 (严重)

详见下节专门分析。

## 脏文件/热更新集成缺陷分析

在深入分析热更新 (`HotUpdateCoordinator`) 与 summary 系统的集成时，发现两个严重缺陷和一个中等缺陷：

### Bug 1 (Critical): SummaryUpdateProcessor 死代码

`SummaryUpdateProcessor` 已完整实现但**从未被注册到处理器管线中**。

`factory.rs::create_all_processors()` (`factory.rs:171-254`) 创建以下处理器：
- `EmbeddingUpdateProcessor` (index 阶段)
- `Bm25UpdateProcessor` (index 阶段)
- `NlDocumentUpdateProcessor` (derived 阶段)

但从未创建 `SummaryUpdateProcessor`，尽管 `ProcessorConfig` 包含 `enable_summary: true`，且 `classify_processor("summary")` 正确返回 `Derived` 阶段。

**根因**：`create_all_processors()` 遗漏了 summary 处理器的实例化分支 (`factory.rs:238-250`)。

**影响**：热更新期间摘要完全绕过更新。文件变更后：
- Qdrant 中的旧摘要向量未被删除
- 新摘要未被生成并存储
- 摘要索引在热更新后完全过期

仅在全量索引（`IndexOrchestrator::execute()`）时摘要才是正确的。

### Bug 2 (Critical): 文件表缓存更新被禁用

`coordinator.rs::update()` (`coordinator.rs:1487-1488`)：
```rust
// 第 4 步：更新文件缓存（已跳过）
// self.update_cache(&cache_result).await;
```

缓存更新被完全注释掉，导致：
- 新文件检测为 "added" 但哈希值未存入 `files` 表
- 已修改文件的哈希值未更新
- 每次热更新周期中同一文件被重复处理（非增量行为）
- 间接导致 `store_summaries()` 在 SQLite 持久化时因 `FileRepository::get_by_path_and_project()` 查不到记录而跳过写入

**影响**：
- 热更新并非真正的增量更新，效率极低
- 新文件的摘要仅存在于 Qdrant，SQLite 中无记录（影响恢复能力）

### Bug 3 (Medium): remove_file_from_summary 清理不完整

`storage_coordinator.rs:807-825`：

```rust
pub async fn remove_file_from_summary(&self, file_path: &Path) -> Result<()> {
    let file_id = file_path.to_string_lossy().to_string();
    qdrant.delete_by_file_path_scoped(&file_id, &self.project_group_id, Some("summary")).await?;
    // ⚠️ 没有清理:
    //   - SQLite file_summaries 表
    //   - files 表中的 content_hash
    //   - 实体映射
    Ok(())
}
```

对比全量索引的 `remove_file()`（清理 Qdrant、BM25、实体映射、块记录、缓存），`remove_file_from_summary()` 仅清理 Qdrant 一端。

### 次要问题

- **实体映射脏数据累积**：文件重新处理后，旧 `EntityDetailMapping` 未被清理，可能引用已过期的 Qdrant point ID
- **文件重命名事件丢弃**：`coordinator.rs:734-766` 中 `FileEventType::RenamedFrom`/`RenamedTo` 被 `_ => {}` 忽略（但底层 notify 库通常发出独立的 remove/create 事件，实际影响有限）

### 修复建议

1. `factory.rs`：在 `create_all_processors()` 中添加 summary 处理器的实例化
2. `coordinator.rs`：恢复 `update_cache()` 调用
3. `storage_coordinator.rs`：`remove_file_from_summary()` 补充 SQLite 清理

## 总结

Summary 功能的**核心链路（全量索引路径）实现完整且正确**，配置→生成→存储→搜索→导出各层集成良好。主要问题集中在**增量索引/热更新路径**：

| 场景 | 状态 | 说明 |
|------|------|------|
| 全量索引 → 生成摘要 | ✅ | IndexOrchestrator::execute() 正确完成 |
| 全量索引 → 删除文件 | ✅ | remove_file() 完整清理所有后端 |
| 热更新 → 文件变更 → 摘要更新 | ❌ | SummaryUpdateProcessor 未注册（死代码） |
| 热更新 → 文件删除 → 摘要清理 | ❌ | Qdrant 清理但 SQLite 孤立 |
| 热更新 → 新增文件 → 摘要持久化 | ❌ | 文件表缓存未更新，SQLite 写入跳过 |
| 重命名/目录移动 | ⚠️ | 功能上有效，但存在孤立数据 |

## Rule-Based 与 Model-Enhanced 切换分析

### 架构层面的两级切换

切换逻辑分为**构造期**和**运行期**两个层次：

```
[构造期] IndexOrchestrator::build_generator()
  │
  ├─ config.strategy == ModelEnhanced && LLM client 可用
  │   └─ → ModelEnhancedGenerator (封装了 rule_generator 作为 fallback)
  │
  └─ 否则 → RuleBasedGenerator
          │
          └─ 两者都实现 SummaryGenerator trait，接口完全一致

[运行期] ModelEnhancedGenerator::generate()
  │
  ├─ 1. FileCategory::determine()
  │     └─ should_skip_model() → specialized (test/config/doc/generated/schema/minimal)
  │
  ├─ 2. PreprocessingPipeline::process() → ProcessingResult
  │
  ├─ 3. ImportanceDecision::determine_generation_strategy()
  │     ├─ GenerationStrategy::RuleOnly → rule_generator.generate_with_groups()
  │     └─ GenerationStrategy::ModelEnhanced
  │           ├─ rule_generator.generate_with_groups() (基础摘要)
  │           ├─ LLM call → model_summary
  │           └─ 合并: summary_text = model_summary, importance_level = High
  │
  └─ 返回 FileSummary
```

### 切换决策因子

`ImportanceDecision::determine_generation_strategy()` 使用以下维度：

| 因子 | 影响 |
|------|------|
| 实体数量 | 越多 → 越可能走 ModelEnhanced |
| Doc comment 覆盖率 | 越高 → 越可能走 ModelEnhanced |
| 文件行数 | 越大 → 越可能走 ModelEnhanced |
| 调用关系复杂度 | 调用者/被调用者多 → 越可能走 ModelEnhanced |
| 配置 `max_summary_length` | 太短 → LLM 空间不足，降级为 RuleOnly |

### 切换的优缺点

**优点**：
- 调用方完全无感知：`SummaryGenerator` trait 统一接口，`IndexOrchestrator` 不需要知道具体实现
- 降级路径完整：LLM 失败自动回退到 rule-based，不会让用户看到空摘要
- 按文件粒度决策：同一项目中不同文件可以走不同路径

**缺点**：
- `ModelEnhancedGenerator::generate()` 内部重新创建 `PreprocessingPipeline` 做 grouper，而索引管线中 grouper 已经执行过了——这是**重复计算**（在索引管线中是用 `generate_with_groups` 传入已算好的 `ProcessingResult`）
- 文件级决策没有缓存：同一个文件在每次全量索引中会重新走决策逻辑

## 单独路径 (`/api/summary`) 问题分析与修复方案

### 现状

`handlers/summary.rs` 中的即席 API：

```rust
let generator = RuleBasedGenerator::new();    // 硬编码，无配置
let parsed = parser.parse(&path, &content);   // 仅解析
let file_summary = generator.generate(&parsed).await;  // 无 grouper
```

问题：
1. 硬编码 `RuleBasedGenerator::new()`，使用 `SummaryConfig::default()`，完全忽略项目配置
2. 不调用 `generate_with_groups()`，跳过 grouper 富化路径
3. 从不查询 `SummaryRequest::strategy` 字段（该字段已定义在 `models.rs:757-765` 但未被使用）
4. 不持有 LLM client，即使请求 model-enhanced 也无法支持

### 需求分析

单独路径的核心场景：用户通过 CLI 或 HTTP API 对**任意文件**（不一定是已索引项目中的文件）**临时**生成摘要，不存储。

主要差异 vs 索引管线：

| 维度 | 索引管线 | 单独路径 |
|------|----------|----------|
| 输入源 | 扫描的目录文件 | 用户指定的任意路径 |
| 是否有 grouper | 是（管线自带） | 否（需独立创建） |
| 是否有 LLM | 可配置 | 当前无 |
| 是否存储 | 是 | 否 |
| 是否需配置 | 项目配置 | 当前无配置传入 |
| 文件系统范围 | 项目内 | 任意路径 |

### 修复方案

#### 方案 A（推荐）：使用 SummaryGenerator trait 统一路径

将 `AppState` 中已有的 `index_orchestrator` 的 `summary_generator` 暴露出来复用：

```
handle_summary 收到请求
  │
  ├─ 1. 从 AppState 获取 generator (dyn SummaryGenerator，已有 config + LLM)
  │      → 若走索引管线，用 orchestrator 中的 generator
  │      → 若走独立路径，用 state 中缓存的 generator
  │
  ├─ 2. 对每个文件:
  │     ├─ 读取 + 解析文件
  │     ├─ 创建 PreprocessingPipeline::process() → ProcessingResult
  │     └─ generator.generate_with_groups(parsed, groups) → FileSummary
  │
  └─ 3. 返回结果
```

关键改动点：
1. `AppState` 中暴露 `summary_generator: Arc<dyn SummaryGenerator>`（从 `engine.get_orchestrator()` 中提取）
2. `handle_summary` 从 `generate()` 改为 `generate_with_groups()`
3. `SummaryRequest` 中 `strategy` 字段生效：若请求 model-enhanced 且 state 中有 LLM client，则可支持

```rust
// handlers/summary.rs 改动示意
async fn handle_summary(State(state): State<AppState>, Json(request): Json<SummaryRequest>) ... {
    let generator = &state.summary_generator; // 复用已配置好的 generator
    let processor = PreprocessingPipeline::new(); // 轻量，可随时创建

    for file_path in files_to_process {
        let content = read_file(&file_path).await?;
        let parsed = parser.parse(&path, &content)?;

        // 新增: grouper 处理
        let groups = processor.process(&parsed);

        // 使用富化路径
        let summary = generator.generate_with_groups(&parsed, &groups).await;

        summaries.push(summary);
    }
}
```

#### 方案 B（轻量）：仅修复硬编码问题

不改动架构，只修复最明显的缺陷：

```rust
// 从 AppState 获取默认 config 创建 generator
let strategy = request.strategy.unwrap_or(SummaryGenStrategy::RuleBased);
let config = if strategy == ModelEnhanced {
    SummaryConfig::model_enhanced()
} else {
    SummaryConfig::rule_based()
};
// 但 LLM client 问题仍未解决...
```

此方案不能解决 LLM 支持和 grouper 缺失的问题，不推荐。

### 临时数据释放分析

无论是索引管线还是单独路径，summary 生成过程中的临时数据都能被及时释放：

| 数据 | 生命周期 | 释放时机 |
|------|----------|----------|
| 文件内容 (String) | parser.parse() 后被 ParsedFile 持有 | ParsedFile 被 drop |
| ParsedFile | generate_with_groups 调用后被持有，后存入 FileSummary | FileSummary 提取所需字段后 drop |
| ProcessingResult (含 EntityGroup 列表) | PreprocessingPipeline::process() 创建，generate_with_groups 消费 | generate_with_groups 返回后 drop |
| TokenEstimator / AstParser | 函数内临时创建 | 函数返回后 drop |
| FileSummary | 返回给调用方 | 调用方消费后 drop |

**关键路径**的典型内存占用（单文件）：
- 文件内容：~文件大小（KB-MB）
- ParsedFile entities：实体数 × 约 200 bytes/entity
- ProcessingResult groups：约 groups 数量 × 300 bytes/group
- FileSummary：固定大小 ~KB 级

**无泄漏风险**：Rust 的所有权系统确保所有临时数据在变量离开作用域时立即释放。唯一需要注意的点：

- 文件内容在 ParsedFile 中持有，ParsedFile 在 summary 生成后不再需要（可以 `drop` 或让其离开作用域）
- ParsedFile 中的 `source: Arc<String>` 使用 Arc，如果多处持有引用则需等引用计数归零
- PreprocessingPipeline 本身是 stateless（仅持有配置），可重复使用，无需重复创建

**建议的显式释放方式**：
```rust
// 将解析和摘要生成放在块作用域中，确保临时数据及时释放
let summary = {
    let content = read_file(&path).await?;
    let parsed = parser.parse(&path, &content)?;
    let groups = processor.process(&parsed);
    let result = generator.generate_with_groups(&parsed, &groups).await;
    result // 仅返回 result，其余数据随块结束释放
};
// 此时 content, parsed, groups 均已释放
```

## 决策策略方向分析

### 当前策略

`decision.rs:248-261` 中，doc comment 覆盖率高的文件走 `RuleOnly`（信任现有文档注释）：

```rust
if doc_quality.should_skip_model_enhancement() {
    return GenerationStrategy::RuleOnly;
}
```

阈值条件 (`doc_quality.rs:168-170`)：

```
should_skip_model_enhancement = documentation_ratio >= 0.6 && average_score >= 0.4
```

| 条件 | 含义 |
|------|------|
| `documentation_ratio >= 0.6` | 至少 60% 的 public entity 有质量合格的文档 (score >= 0.5) |
| `average_score >= 0.4` | 所有被评估文档的平均质量分 >= 0.4 |

**方向正确**：高 doc comment 覆盖率 → 走 rule-based，相信开发者已写的文档注释，无需 LLM 介入。

### 决策路径总览

```
determine_generation_strategy()
  │
  ├─ SummaryStrategy::RuleBased / Minimal → RuleOnly
  │
  └─ SummaryStrategy::Auto / ModelEnhanced
       │
       ├─ FileCategory::should_skip_model()
       │    └─ test/config/doc/generated/minimal → RuleOnly (specialized)
       │
       ├─ doc_quality.should_skip_model_enhancement()
       │    └─ 文档覆盖率高 → RuleOnly
       │
       ├─ boilerplate_ratio > 0.6
       │    └─ 样板代码占比高 → RuleOnly
       │
       ├─ is_core_module()
       │    └─ main/lib/mod/index → ModelEnhanced
       │
       ├─ entity_count >= 10 || groups >= 7
       │    └─ 复杂文件 → ModelEnhanced
       │
       └─ → RuleOnly (默认)
```

## Summary、AST-to-NL、Export 数据流分析

### 当前三条路径的关系

```
ParsedFile → Grouper → ProcessingResult
                              │
                    ┌─────────┼─────────────┐
                    │         │             │
                    ▼         ▼             ▼
              AST-to-NL    Summary     RelationIndex
```

### 核心问题

**Summary 完全独立重头推导**，做了大量重复工作：

| 工作 | AST-to-NL | Summary | Export |
|------|-----------|---------|--------|
| Entity → NL 转换 | ✅ 产出 embedding/bm25 text | ❌ 不使用，重新解析 entities | ✅ 消费 embedding text |
| Imports 提取 | ✅ tree-sitter 解析 | ❌ 重新 `AstParser::parse_with_tree()` | ✅ 从 summary 获取 |
| Doc comment 解析 | ✅ 嵌入 NL text | ✅ 重新 `DocCommentQuality::evaluate()` | ✅ 从 summary 获取 |
| Relation data | ❌ 不涉及 | ❌ 不使用 | ✅ `RelationEnhancer` 附加 |

`rule_based.rs:467-498` 中，每次 `generate_summary_text()` 都重新创建 `AstParser` 解析整个文件的 imports，而 AST-to-NL 管线在 chunking 阶段已经完成了这项工作。

### 改进方向

Summary 应消费 `ChunkedResult[]` 的 NL 描述作为输入数据源：

```
当前: Summary 输入 = ParsedFile.entities + doc comments + 重解析 imports
改进: Summary 输入 = ChunkedResult[].text (NL descriptions) + RelationIndex
```

收益：
- **消除重复工作**：AST-to-NL 已产出高质量 NL text，summary 无需重头推导
- **内容更丰富**：NL descriptions 是对代码行为的自然语言描述，7B+ 模型可以在此基础上做更高层次的综合
- **可附加关系数据**：结合 `RelationIndex`，summary 可以包含跨文件上下文（如 "被 15 个调用者使用"）

架构变化：

```
当前:
  ParsedFile → SummaryGenerator → FileSummary (独立推导)

改进:
  ParsedFile → AST-to-NL → ChunkedResult → SummaryGenerator (消费 NL text)
                                          ↗
                              RelationIndex (附加调用关系)
```

## Export 对 Summary 的依赖分析

### 全量索引路径（正确）

`orchestrator.rs:698-838` 中批次内执行顺序：

```
1. 生成 summary → file_summary_map[file_path] = FileSummary
2. export_file(chunks, file_summary_map.get(file_path))
3. FileAggregator.aggregate(chunks, summary) → 写入 doc.imports/exports/summary
```

具体的传递链：

```rust
// orchestrator.rs:740-741 — 构建 summary map

    file_summary_map.insert(pf.path.clone(), summary.clone());

// orchestrator.rs:838 — export 时传入 summary

// aggregator.rs:256-260 — 写入 FileNlDocument
```

### 热更新路径（有缺陷）

`NlDocumentUpdateProcessor` (`export_processor.rs:263-327`) 中有两条路径：

**优先路径：direct export（绕过 summary）**
```rust
// export_processor.rs:268-272
self.handle_file_update_direct(&parse_result.file_path, &processing_result.groups)
```
直接从 `EntityGroup[]` 生成文档，不携带 summary 信息。文档头部缺少 imports/exports/summary_text。

**fallback 路径（依赖 summary）**
```rust
// export_processor.rs:302-306
let summary = self.extract_summary_from_parse_result(parse_result);
// 依赖 parse_result.file_summary — 因 SummaryUpdateProcessor 是死代码，永远为 None
```

**受影响字段**（hot update 下 export 文档头部缺失）：

| 字段 | 来源 | 热更新状态 |
|------|------|-----------|
| `doc.imports` | `s.imports` | ❌ 缺失 |
| `doc.exports` | `s.exports` | ❌ 缺失 |
| `doc.summary` | `s.summary_text` | ❌ 缺失 |

根因：`SummaryUpdateProcessor` 死代码 → 热更新不生成 summary → `parse_result.file_summary` 永远为 None → Export 无法获取 summary header。

修复前置条件：先解决 `SummaryUpdateProcessor` 未注册问题，确保热更新时 summary 能正确生成并附着到 `ParseResultWithChanges.file_summary`。
