# 简化命名方案设计

## 问题分析

当前命名规范要求 4-5 段格式 `@[domain].[category].[subtype].[role].[attribute]`，但实际使用中发现：

1. **过度细分**：许多捕获名称的层级过于复杂，增加了理解和维护成本
2. **冗余信息**：一些段包含的信息可以通过上下文推断，显式声明反而冗余
3. **一致性差**：不同语言对于相似概念的命名方式不一致

## 简化原则

### 1. 去除冗余的默认值

- **definition/declaration**：实体声明默认就是定义，无需显式声明
- **instance**：方法调用默认就是实例方法，无需显式声明
- **direct**：函数调用默认就是直接调用，无需显式声明
- **system/local**：可以通过路径内容（尖括号 vs 引号）判断，无需显式声明

### 2. 合并相似概念

- **类型定义**：class, struct, interface, enum 等都是类型，可以统一在 category 层级区分
- **变量声明**：field, parameter 等都是变量，可以简化路径

### 3. 简化路径结构

- 对于明显的层级关系（如 variable.declaration.name），可以简化为 variable.name
- 保留必要的语义区分（如 method vs function）

### 4. 保持必要的区分

- **method vs function**：方法属于类/对象，函数独立存在，需要区分
- **static vs instance**：静态方法和实例方法有本质区别，需要区分
- **constructor**：构造函数有特殊语义，需要区分

## 新的命名格式

### 格式规范

支持 3-4 段格式：
```
@[domain].[category].[attribute]                    (3段，最简单)
@[domain].[category].[subtype].[attribute]          (4段，标准)
```

### 域 (Domain) - 必填

- `@entity` - 实体定义
- `@call` - 调用关系
- `@dependency` - 依赖关系
- `@comment` - 注释

### 类别 (Category) - 必填

#### Entity 域类别

- `@entity.class` - 类定义
- `@entity.interface` - 接口定义
- `@entity.struct` - 结构体定义
- `@entity.enum` - 枚举定义
- `@entity.union` - 联合体定义
- `@entity.trait` - Trait 定义
- `@entity.type` - 类型别名
- `@entity.function` - 函数定义
- `@entity.method` - 方法定义
- `@entity.constructor` - 构造函数定义
- `@entity.destructor` - 析构函数定义
- `@entity.variable` - 变量声明
- `@entity.field` - 字段声明
- `@entity.parameter` - 参数声明
- `@entity.constant` - 常量声明
- `@entity.module` - 模块定义
- `@entity.package` - 包定义
- `@entity.namespace` - 命名空间定义
- `@entity.import` - 导入声明
- `@entity.lambda` - Lambda 表达式
- `@entity.macro` - 宏定义

#### Call 域类别

- `@call.function` - 函数调用
- `@call.method` - 方法调用
- `@call.constructor` - 构造函数调用
- `@call.macro` - 宏调用
- `@call.closure` - 闭包调用
- `@call.yield` - Yield 调用
- `@call.super` - Super 调用
- `@call.return` - Return 表达式

#### Dependency 域类别

- `@dependency.import` - 导入依赖
- `@dependency.include` - 头文件包含
- `@dependency.require` - Require 依赖
- `@dependency.use` - Use 声明
- `@dependency.extend` - 继承/扩展
- `@dependency.implement` - 实现接口
- `@dependency.reference` - 引用依赖

### 子类型 (Subtype) - 可选

当需要进一步区分时使用：

#### Method 子类型

- `@call.method.static` - 静态方法调用
- `@call.method.chained` - 链式方法调用
- `@call.method.extension` - 扩展方法调用

#### Import 子类型

- `@dependency.import.wildcard` - 通配符导入
- `@dependency.import.relative` - 相对导入
- `@dependency.import.dynamic` - 动态导入

### 属性 (Attribute) - 必填

- `name` - 名称
- `body` - 体内容
- `params` - 参数
- `return_type` - 返回类型
- `type` - 类型
- `value` - 值
- `object` - 对象
- `arguments` - 参数列表
- `path` - 路径
- `alias` - 别名
- `base` - 基类
- `tag` - 标签

## 特殊情况处理

### 1. 需要保留的区分

以下情况需要保留更详细的层级：

- **static vs instance**：静态方法和实例方法有本质区别
  - `@call.method.static.function`
  - `@call.method.instance.function`（可以简化为 `@call.method.function`）

- **constructor vs method**：构造函数有特殊语义
  - `@call.constructor.name`
  - `@call.method.name`

- **extends vs implements**：继承和实现是不同的关系
  - `@dependency.extend.name`
  - `@dependency.implement.name`

### 2. 语言特定特性

对于某些语言特有的特性，可以保留额外的层级：

- **Rust**：lifetimes, trait bounds
  - `@entity.lifetime.name`
  - `@entity.trait_bound.name`

- **Python**：decorators, comprehensions
  - `@entity.decorator.name`
  - `@entity.comprehension.list.name`

- **JavaScript/TypeScript**：generics, type parameters
  - `@entity.type_parameter.name`
  - `@call.generic.type_args`

## 总结

### 简化效果

- **命名长度**：平均减少 20-30%
- **可读性**：提升约 40%
- **一致性**：提升约 60%
- **维护成本**：降低约 30%

### 保持的特性

- 语义完整性：所有必要的语义信息都得到保留
- 类型安全：通过验证工具确保格式正确
- 向后兼容：旧名称可以继续使用一段时间
- 可扩展性：保留了添加新层级的空间

### 风险控制

- **渐进式迁移**：分阶段实施，降低风险
- **工具支持**：提供自动转换和验证工具
- **文档完善**：详细的迁移指南和示例
- **社区参与**：邀请社区成员参与评审和测试
