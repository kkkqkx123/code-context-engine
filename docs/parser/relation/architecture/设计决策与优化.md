# Relation 模块设计决策与优化

## 1. 架构设计决策

### 1.1 分层架构

**决策**：采用自底向上的分层架构

```
Layer 3: Query (用户接口)
    ↑
Layer 2: Index (核心功能)
    ↑
Layer 1: Symbol Table + Extraction (组织管理和基础抽象)
    ↑
Layer 0: Symbol (基础类型)
```

**理由**：
- 清晰的职责分离
- 易于测试和维护
- 支持渐进式开发
- 便于理解数据流

**权衡**：
- 优点：模块化好，扩展性强
- 缺点：层间调用有轻微开销（可忽略）

### 1.2 符号 ID 设计

**决策**：使用单一全局原子递增 ID（SymbolId: u64）

```rust
pub struct SymbolId(pub u64);

pub struct GlobalSymbolIdAllocator {
    counter: Arc<AtomicU64>,
}
```

**替代方案对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 全局原子递增 | 简单、紧凑（8 字节）、无冲突 | ID 不跨进程稳定 |
| 复合 ID (file_id + local_id) | 跨进程稳定 | 复杂、占用 12+ 字节、需管理 file_id |
| UUID | 全局唯一 | 占用 16 字节、比较慢、随机性 |

**理由**：
- 单进程场景，不需要跨进程稳定
- 内存效率优先（8 字节 vs 12+ 字节）
- 简单性优先（单次比较 vs 复合比较）
- 索引重建时 ID 变化是可接受的

### 1.3 反向索引设计

**决策**：显式维护 callee_index（callee -> callers）

```rust
pub struct RelationIndex {
    resolved_relation_index: DashMap<EntityId, Vec<ResolvedRelation>>, // 正向
    callee_index: DashMap<EntityId, Vec<EntityId>>, // 反向
}
```

**理由**：
- 反向查询是常见操作（"谁调用了这个函数"）
- O(1) 查找 vs O(n) 全表扫描
- 内存开销可接受（每个关系多存储一个指针）

**权衡**：
- 优点：反向查询性能提升显著
- 缺点：添加关系时需维护两个索引（轻微开销）

### 1.4 两阶段解析

**决策**：LocalCallResolver + RelationResolver 分离

```
阶段 1: LocalCallResolver
  - 解析文件内调用
  - 计算调用顺序
  - 跳过跨文件调用

阶段 2: RelationResolver
  - 解析跨文件调用
  - 分类外部调用
  - 过滤标准库
```

**理由**：
- 支持增量更新（单文件更新只需阶段 1）
- 职责分离清晰
- 便于测试和调试

**权衡**：
- 优点：灵活性高，支持增量
- 缺点：完整解析需要两个阶段

### 1.5 标准化导入/导出

**决策**：extraction 层输出标准化的 Import/Export

```rust
pub struct StandardizedImport {
    pub kind: ImportKind,
    pub source: String,
    pub target: ImportTarget,
    // ...
}
```

**理由**：
- 统一不同语言的表示
- 简化后续处理逻辑
- 便于跨语言分析

**权衡**：
- 优点：语言无关，易于扩展
- 缺点：某些语言特性可能丢失（可在 metadata 中扩展）

## 2. 性能优化决策

### 2.1 DashMap 替代 RwLock<HashMap>

**决策**：所有索引使用 DashMap

```rust
// 之前
function_index: RwLock<HashMap<EntityId, Entity>>

// 现在
function_index: DashMap<EntityId, Entity>
```

**理由**：
- 细粒度锁（每个 bucket 独立锁）
- 更高的并发性能
- 无需外部锁管理
- 内置线程安全

**基准测试**（假设）：
- 读操作：DashMap 快 3-5x（多核场景）
- 写操作：DashMap 快 2-3x（低冲突场景）

### 2.2 Arc 共享策略

**决策**：对大数据结构使用 Arc 共享

```rust
// LocalSymbolTable 中的 Arc 使用
entities: Arc<HashMap<EntityId, Entity>>
file_path: Arc<str>
name_index: HashMap<Arc<str>, Vec<EntityId>>
```

**理由**：
- 避免 Entity 数据重复（Entity 可能很大）
- LocalSymbolTable 和 ParsedFile 可共享同一份数据
- 内存节省显著（大文件可节省 50%+）

**权衡**：
- 优点：内存效率高
- 缺点：需要处理 Arc 的克隆和可变性（使用 clone-on-write 策略）

### 2.3 依赖索引

**决策**：构建 DependencyIndex 加速外部调用分类

```rust
pub struct DependencyIndex {
    index: HashMap<Language, HashMap<String, Dependency>>,
}

// O(1) 查找
pub fn find_dependency(&self, lang, name) -> Option<Dependency> {
    self.index.get(lang)?.get(name).cloned()
}
```

**理由**：
- 外部调用分类是热点操作
- 从 O(n) 降到 O(1)
- 构建开销一次，查询多次

**权衡**：
- 优点：查询性能大幅提升
- 缺点：需要额外内存存储索引

### 2.4 解析缓存

**决策**：ProjectSymbolTable 中的 resolution_cache

```rust
resolution_cache: DashMap<String, Option<SymbolRef>>;

pub fn resolve_qualified(&self, qualified_name: &str) -> Option<SymbolRef> {
    // 先查缓存
    if let Some(result) = self.resolution_cache.get(qualified_name) {
        return result.clone();
    }
    // 解析并缓存
    let result = self.resolve_qualified_internal(qualified_name);
    self.resolution_cache.insert(qualified_name.to_string(), result.clone());
    result
}
```

**理由**：
- 相同符号可能被多次解析
- 缓存命中率可能很高
- 避免重复工作

**权衡**：
- 优点：重复查询性能提升
- 缺点：内存占用增加，缓存一致性需管理

### 2.5 选择性索引

**决策**：支持 selective indexing

```rust
pub fn add_resolved_relation_selective(
    &self,
    relation: ResolvedRelation,
    config: &ReverseIndexConfig,
) {
    // 只索引热点或重要关系
    if config.should_index(&relation) {
        self.add_resolved_relation(relation);
    }
}
```

**理由**：
- 大型项目关系数量巨大
- 不是所有关系都需要索引
- 可配置平衡内存和性能

**权衡**：
- 优点：内存可控
- 缺点：部分查询可能不完整

## 3. 错误处理设计

### 3.1 分层错误类型

**决策**：详细的分层错误枚举

```rust
pub enum RelationError {
    Index(IndexError),
    Query(RelationQueryError),
    Resolution(ResolutionError),
    Persistence(PersistenceError),
}
```

**理由**：
- 精确的错误分类
- 便于错误处理
- 丰富的错误信息

**权衡**：
- 优点：调试友好，可针对性处理
- 缺点：错误类型较多，需要映射

### 3.2 上下文错误

**决策**：ErrorContext 提供额外调试信息

```rust
pub struct ErrorContext {
    pub operation: String,
    pub entity_id: Option<EntityId>,
    pub file_path: Option<String>,
    pub context: Vec<(String, String)>,
}
```

**理由**：
- 错误发生时捕获上下文
- 便于定位问题
- 结构化日志

**权衡**：
- 优点：调试信息丰富
- 缺点：轻微的性能开销

### 3.3 Safe 查询 API

**决策**：提供 safe 版本 API（返回空而非错误）

```rust
// 可能失败的 API
pub fn get_callees_by_entity(&self, id: EntityId) -> Result<Vec<...>, Error>;

// Safe 版本（失败时返回空）
pub fn get_callees_by_entity_safe(&self, id: EntityId) -> Vec<...> {
    match self.get_callees_by_entity(id) {
        Ok(rels) => rels,
        Err(e) => {
            tracing::warn!("Failed to get callees: {}", e);
            Vec::new()
        }
    }
}
```

**理由**：
- 某些场景下失败是预期的
- 避免过度错误处理
- 记录警告但不中断

**权衡**：
- 优点：使用简单，容错性好
- 缺点：可能掩盖问题（需配合日志）

## 4. 并发设计

### 4.1 无锁读取

**决策**：DashMap 支持无锁读取（读多写少场景）

```rust
// 读取操作（无锁）
pub fn get_function(&self, id: EntityId) -> Option<Ref<Entity>> {
    self.function_index.get(&id)
}
```

**理由**：
- 查询操作远多于修改操作
- 最大化并发读取性能

### 4.2 原子计数器

**决策**：使用原子类型进行计数

```rust
// 全局 ID 分配
symbol_id_counter: Arc<AtomicU64>

// 过滤计数
filtered_count: AtomicUsize

// 版本控制
version_counter: AtomicU64
```

**理由**：
- 线程安全
- 无锁操作
- 性能高

### 4.3 线程安全类型别名

**决策**：提供 ThreadSafeIndex 类型别名

```rust
pub type ThreadSafeIndex = RelationIndex; // RelationIndex 内部已线程安全
```

**理由**：
- 明确线程安全承诺
- 便于文档和 API 设计
- 未来可替换实现

## 5. 可扩展性设计

### 5.1 提取器 trait

**决策**：SymbolExtractor trait 支持新语言

```rust
pub trait SymbolExtractor: Send + Sync {
    fn extract_imports(&self, tree: &Tree, source: &str) -> Vec<StandardizedImport>;
    fn extract_exports(&self, tree: &Tree, source: &str) -> Vec<StandardizedExport>;
    fn language(&self) -> Language;
}
```

**理由**：
- 开闭原则：对新语言开放，对现有代码封闭
- 统一接口
- 易于测试

### 5.2 可见性模型扩展

**决策**：Visibility 枚举支持多种语言模型

```rust
pub enum Visibility {
    Public,
    Package,
    Module,
    Protected,      // Java/C++/C#
    Internal,       // C#
    ProtectedInternal,  // C#
    PrivateProtected,   // C#
    Friend { ... },     // C++
    Restricted { ... }, // Rust
}
```

**理由**：
- 覆盖主流语言的可见性模型
- 易于添加新变种
- 统一的可见性检查接口

### 5.3 配置驱动

**决策**：关键行为可配置

```rust
pub struct LocalCallResolverConfig {
    pub enable_signature_matching: bool,
    pub skip_cross_file_calls: bool,
    pub log_unresolved_calls: bool,
}

pub struct TraversalConfig {
    pub max_depth: usize,
    pub include_start_node: bool,
    pub stop_on_cycles: bool,
    pub max_nodes: usize,
}
```

**理由**：
- 适应不同使用场景
- 平衡性能和准确性
- 便于调试

// 不存储 function_name_index，需要时从 function_index 计算

## 7. 权衡总结

### 7.1 性能 vs 准确性

| 场景 | 决策 | 理由 |
|------|------|------|
| 外部调用分类 | 使用 DependencyIndex（快速但不完整） | 性能优先，可配置 |
| 符号解析 | 多阶段回退（准确但慢） | 准确性优先 |
| 索引构建 | 选择性索引（快速但不完整） | 可配置平衡 |

### 7.2 内存 vs 速度

| 场景 | 决策 | 理由 |
|------|------|------|
| 反向索引 | 额外存储 callee_index | 速度优先，内存可接受 |
| 解析缓存 | 缓存解析结果 | 速度优先，LRU 可优化 |
| Arc 共享 | 使用 Arc 共享数据 | 内存优先，克隆开销小 |

### 7.3 简单性 vs 功能

| 场景 | 决策 | 理由 |
|------|------|------|
| SymbolId | 全局原子递增 | 简单性优先 |
| 可见性检查 | 支持继承图 | 功能优先（OOP 需要） |
| 错误处理 | 详细错误类型 | 可维护性优先 |

## 8. 未来优化方向

### 8.1 潜在优化点

1. **增量索引构建** - 只构建变化的部分
2. **LRU 缓存** - 限制缓存大小
3. **并行解析** - 多文件并行处理
4. **内存映射** - 大索引使用 mmap
5. **压缩存储** - 稀疏数据压缩

### 8.2 待研究技术

1. **图数据库集成** - 复杂查询优化
2. **流式处理** - 超大项目支持
3. **增量编译** - 类似 Rust 的增量编译
4. **分布式索引** - 跨机器索引

---

## 总结

Relation 模块的设计决策遵循以下原则：

1. **性能优先** - 使用 DashMap、反向索引、缓存等优化
2. **内存效率** - Arc 共享、紧凑表示、延迟计算
3. **可扩展性** - trait 设计、配置驱动、分层架构
4. **可维护性** - 详细错误、清晰职责、丰富日志
5. **实用性** - 权衡准确性与性能，支持配置

所有决策都有明确的理由和权衡分析，便于未来优化和调整。
