# tree-sitter 查询漏抽问题清单（2026-11-10）

来源：libref 引入 Rust、Go、C# 支持时，以 cce `cce-parser` 的 scheme 查询为基准做子集改写；改写前用各语言真实语法树对 cce 查询原文做了命中验证，发现以下四处漏抽。均已用最小源码复现，现象稳定，与窗口或版本无关。

## 1. Go 分组导入零命中（严重）

cce 的 Go 依赖查询把导入规格锚定为导入声明的直接子节点。实际语法树中，括号分组导入的规格挂在中间的规格列表节点下，只有单行导入才是直接子节点。实测单行导入命中一次，分组导入命中零次。分组导入是 Go 仓库的主流写法，意味着绝大多数真实文件的导入关系整体丢失，下游的包引用消解与模块边会系统性缺失。

建议：导入规格不锚定父节点，直接匹配规格节点本身（规格节点只出现在导入上下文中，不会误伤）。

## 2. C# 普通 using 零命中（严重）

cce 的 C# 依赖查询要求 using 指令具备名称字段。实际语法树中，只有别名形式（等号左侧）带有该字段；普通单命名空间与限定命名空间形式均无字段。实测两种普通形式均零命中，只有别名形式命中。后果是几乎所有 C# 文件的命名空间依赖丢失。

附带问题：别名形式的别名标识同样满足名称字段约束，会被同时捕获为命名空间名与限定名，别名与真实路径混在一起，下游需额外清洗。

建议：普通形式改为无字段约束的子节点匹配；别名形式用等号存在性加以区分，避免别名被误标为命名空间。

## 3. C# this 前缀调用零命中（严重）

cce 的 C# 调用查询要求成员访问的宿主表达式为具名节点。实际语法树中 `this` 为匿名 token，不满足该约束。实测 `this.H()` 独立语句命中零次，而 `obj.M()` 正常命中。类内经由 `this` 的自调用是 C# 最常见的调用形态之一，该形态整体丢失会直接拉低方法间边召回。

建议：增补不约束宿主的成员调用形态（函数名捕获足以归属同文件同名方法），或显式兼容匿名宿主。

## 4. Rust 非路径别名与单标识导入漏抽（中等）

cce 的 Rust 别名形态要求路径为限定路径节点，但实际语法树中作用子句的路径可以是普通标识（如列表项别名、单标识别名）。实测 `use foo as bar` 与 `use plain` 均无任何别名捕获，只有路径加列表的外层整体命中（内层逐项未展开）。后果是短路径别名导入的调用无法展开，影响关联函数与重导出项的消解。

附带缺口：路径加列表形态只捕获列表整体，不展开逐项，别名构建层拿不到列表内每一项的本地名与完整路径。

建议：路径位置放宽为任意具名节点；列表形态增补逐项捕获（普通项与别名项分别处理）。

## 5. 次要观察（非缺陷，按需处理）

- C# 对象单次调用会被直接、成员、静态三形态同时命中，靠根区间合并去重，计数层若按命中数统计会虚高，建议以合并后为准。
- Go 选择子表达式同时作为实体捕获，对只需要定义的消费方是噪声，对引用追踪有用，保留与否取决于消费方口径，建议文档注明。
- C# 类、接口、结构体、记录的模式均未捕获体节点，签名合成会吞入整个类型文本；如消费方需要签名，建议补体捕获（体字段经核实存在）。
