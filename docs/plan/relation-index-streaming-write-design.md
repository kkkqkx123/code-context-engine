# 关系索引流式快照写出设计方案

## 目标与边界

本方案落地分析文档中“下一阶段执行顺序”的第一步与第二步：取消规范快照的全量二次物化，
把构建产物改为磁盘支撑的组件工件，并在阶段指标中暴露写出批次、写出缓冲峰值与发布后运行时条目数。

不变量：

- 快照指纹、input 指纹、版本号、canonical 内容与改动前逐字节一致。
- manifest 的 `Building -> Ready -> Active` 状态机、CAS 检查、原子事务与失败标记语义不变。
- 不截断关系、不丢边、不关闭 WAL、不放宽事务边界。
- 不引入版本化模块或兼容层；只保留一条正式发布路径。

峰值内存仍由构建期 `RelationIndex` 主导，本步骤消除的是写盘阶段的第二份大对象。
分片查询索引属于后续步骤，在本设计中只定义接口边界，不在本次实现中启用。

## 总体数据流

```text
RelationIndex（唯一构建期内存图）
    -> 逐组件流式序列化（files / entities / relations / dependencies）
        -> 临时目录中的 JSONL 行式工件（每组件一个文件）
        -> 同时写入外部排序器，产出两个指纹
    -> CanonicalSnapshotArtifact（句柄 + 计数 + 指纹 + 输出目录）
    -> 存储后端按批次读取工件，逐表写入已分配的 Building epoch
    -> manifest 标记 Ready，publisher 激活并发布运行时视图
```

构建器永远不会同时持有完整的 `CanonicalRelationSnapshot` 与 `RelationIndex`。
工件是临时文件，随句柄一起释放，不进入持久化快照，也不改变 SQLite 中“只存组件表、不存 DTO blob”的既有模型。

## 关键组件

### 规范快照工件

工件由四个行式文件与一个头部组成。头部携带 schema/parser/resolver/path 版本、配置指纹、
CAS 基epoch和构建诊断；行式文件保存规范化后的 canonical 组件。实体 ID 是唯一被指纹排除但必须持久化的字段，
因此实体行使用带显式 `entity_id` 的工件行结构，避免指纹序列化规则影响读回语义。

工件提供三种读取方式：全组件批次迭代、仅文件批次迭代、逐文件回调。前两者供存储后端按批次写入，
逐文件回调供需要文件与实体同时存在的 exports 写入。读取器是单向、有界的，不缓存历史批次。

### 外部排序指纹

现有指纹等价于对固定顺序的 payload 做 SHA-256，其中四个组件列表和 input 列表都需要先按既有规则排序。
新实现把每个组件的排序键与序列化结果写入外部排序器：

- 内存缓冲按字节上限分块，块内稳定排序后溢写到临时文件；
- 最终通过带序号的 k 路归并得到与旧 `sort_by_key` 完全一致的顺序；
- 按旧 payload 的字段顺序拼接头部、各组 JSON 数组与结尾大括号，增量喂给 SHA-256。

`callee_symbol` 在指纹载荷中置空，与旧实现的排除规则保持一致；工件行本身仍保留该字段，
因此冷加载读回的 canonical 内容不变。外部排序的内存上界由显式字节参数表达，不随项目规模增长。

### 流式 canonical 导出

`RelationIndex` 新增直接导出工件的方法，按文件记录、实体、实体边、文件边、依赖的顺序遍历现有 DashMap。
符号键降级逻辑复用快照视图中的既有实现，但不构造查询优化索引或传递依赖索引，避免导出阶段再产生 O(边数) 副本。
文件级边继续使用 `<file>` 占位键，实体边与文件边的生成规则与 `to_canonical_snapshot` 保持一致。

### 持久化写入

`MetadataStorage` 的整快照写入端口改为接收工件句柄，SQLite 与 PostgreSQL 两条分支都按批次消费：

1. `Building` 状态校验后，按批次写文件行；
2. 按批次写实体行，并在批次内回填 parent；
3. 写关系行前按需插入文件级占位实体；caller/target 通过唯一索引查询符号 ID；
4. 写依赖行，随后再扫一遍文件行补写 exports；
5. 用工件计数与两个指纹把 epoch 一次性标记为 `Ready`。

不再构建全项目的路径到行号、符号键到行号哈希表；跨批次引用通过快照表的唯一索引解析，
查询次数增加但内存与批次大小成正比。重复键由唯一约束直接转成 uniqueness/validation 错误，缺失引用转成 validation 错误。
两个后端在同一事务内完成写入与状态迁移，失败时由上层标记 `Failed`。

### 发布编排

publisher 不再接收已物化的 canonical 快照，而是接收工件句柄；CAS 从工件头部读取基 epoch，
完整性判断改用工件计数。`publish` 与 compaction 共用这条路径；测试和运维入口仍可从已有快照构造工件，
但这不是完整构建路径的一部分。工件在 publication 返回后释放，运行时仍持有零拷贝共享的只读索引。

## 容量指标

阶段记录新增三个字段，与 `rss_after_relation_kb` 同表输出：

- `canonical_write_batches`：流式导出的组件写入批次数；
- `canonical_write_buffer_peak_bytes`：外部排序缓冲与写出窗口的峰值字节；
- `published_snapshot_entries`：发布后运行时视图可见的文件、实体、关系条目总数。

字段贯穿 orchestrator 阶段结构、HTTP 结果模型与性能基准表头，便于用同一份 TSV 对比改动前后的 RSS 与容量上界。

## 验证口径

- 工件指纹与 `CanonicalRelationSnapshot::fingerprint` / `input_fingerprint` 在含文件、实体、关系、依赖的夹具上逐字节相同，且分块大小变化不改变结果。
- SQLite 冷加载读回的关系、实体 ID、build metadata 与发布前一致；publisher 的 CAS、幂等、delta 链与冷路径测试保持通过。
- manifest 失败与重试路径保持原有语义，写入失败仍标记 `Failed`。
- 50,000 文件档复测时观察 `rss_after_relation_kb` 与新增三个容量字段；若峰值仍由构建期关系图主导，进入分片查询阶段。

## 后续阶段接口边界

分片查询阶段将在已完成工件的基础上进行，不改变本阶段的工件格式与指纹：

- 已激活 epoch 的组件行按文件路径或符号前缀划分分片，运行时只装载命中分片并保留有界 LRU；
- 热更新 delta 叠加在已装载分片上，查询融合结果不变；
- `RelationSnapshotIndex` 的写入接口只保留“构建期唯一所有者”语义，冷加载不再要求全量 DashMap；
- 分片容量由显式参数表达，不保留“小项目全量载入、大项目分片”双路径。

## 明确不做

- 不在缺少分片查询方案时把构建中间态表当作可查询数据源。
- 不把快照写入恢复失配数据伪装成容量优化。
- 不调整 batch size、spool 上限或 manifest 保留期来替代结构性改造。
- 不改变 `SnapshotDelta` 语义与已有恢复用例。
