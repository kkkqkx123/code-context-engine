# 写路径规模化后续改进方案

## 依据与范围

本文承接 `docs/plan/write-path-scale-remediation.md` 与
`docs/issue/performance-writepath-remaining-2026-11-23.md`，只处理写路径提交边界聚合之后仍然成立的问题。
前一阶段的向量与 BM25 跨批次聚合、BM25 暂存提交、实体 ID 游标增量加载和批次子阶段拆分已经落地，
本文不重做这些内容，也不新增版本化模块或兼容路径。

devs 上的实测（`full_pipeline_stages.tsv`、`service_remote_backend_index_stages.tsv`）显示：
50,000 文件完整流水线墙钟约 752 s，其中向量阶段约 542 s；5,000 文件服务档向量阶段约 24 s，
规模曲线仍偏超线性。WAL flush 已降到 10 次、提交等待约 0.7 s、HNSW 构建为 0，
剩余成本不在向量引擎提交，而需要继续拆到嵌入调用、点构造、chunk/实体映射落库和工作单元记账。
同时完整流水线 TSV 的向量计数器为 0，与服务路径不一致，不能据此推断引擎未落盘。

## 改动顺序

### 1. 向量阶段子项计时与容量计数

在 `IndexStageTimings` 中增加向量阶段的可测子项：嵌入调用、点构造、派生元数据落库、
工作单元记账、微批数量、chunk 记录数和实体映射行数。计时在 `StorageCoordinator` 内部以累计计数器的形式采集，
全量索引开始时清零、批次循环结束后一次回填指标，不改动各存储后端的契约。

派生写入聚合窗口的暂存记录峰值作为容量上界指标一并输出；它只随向量聚合窗口大小增长，
不随项目文件数增长。指标同时进入 API DTO、服务索引阶段 TSV 与完整流水线阶段 TSV；
列变化时由报告工具按新表头重建趋势文件，不把不同结构的行写进同一个文件。

### 2. 向量派生写入并入同一提交边界

当前向量点已经跨编排批次缓冲到 512 点，但 embedding 微批仍各自执行一次 chunk/实体映射 SQLite 事务，
向量 flush 与派生写入不在同一边界。把点缓冲扩展为“暂存写入”：同时持有待写点、chunk 记录、
实体映射和微批工作单元哈希；达到点阈值或运行结束时，先 flush 向量点，再一次提交派生元数据，
最后才把该窗口的工作单元标记为 `Committed`。

暂存写入在内部合并同一实体的映射并去重点 ID，合并窗口受 512 点阈值约束。
失败文件仍立即保留失败状态；提交失败时向量工作单元保持 `Running`，批次检查点不越过失败窗口。
重放是覆盖已有确定性点 ID，不产生重复数据。热更新与死信重试继续使用单次调用入口，
不共享完整索引的跨批次暂存窗口。

### 3. 计数口径核对

在基准说明中明确：向量计数器来自本地引擎 collection 指标快照的前后差值，
远端后端没有对应本地计数器，相关列保持 0 是定义行为而非写入失败。
完整流水线基准若快照不可用，须在指标列或日志中显式标记，不允许用 0 代替未知值；
本轮不修改引擎持久化和回收口径。

已定位到完整流水线计数器为 0 的直接原因：专用夹具没有给索引编排器配置 embedder，
`stage_vectors_batched` 走了仅持久化 chunk 元数据的分支，`total_vectors` 统计的是 chunk 行数。
夹具改为在回路端口启动 mock 嵌入服务，并把同一个 provider 显式交给索引编排器，
使完整流水线真正生成并写入向量；查询夹具仍沿用原有配置，不自动注入 embedder。

## 失败与可见性语义

- 数据落盘、派生元数据提交和工作单元标记三者在同一边界推进。
- 向量点 flush 失败：派生元数据不提交，工作单元保持 `Running`，检查点不前进。
- 派生元数据提交失败：点可能已经落盘，但工作单元仍为 `Running`，重放覆盖同一点 ID 并补齐映射。
- 工作单元标记失败只记录告警；已落盘数据不回滚，下次读取到 `Running` 会重放同一微批。
- 文件最终状态只在所有派生写入成功后写入，失败文件状态不被批量逻辑吞掉。

## 测试与验收

- 新增暂存写入的单测：覆盖点阈值触发、跨微批映射合并、哈希只在提交后登记和容量峰值统计。
- 在 devs 上执行 workspace check、CLI/server 构建、clippy、库测试和相关集成测试。
- 采集 500 与 5,000 文件档的阶段 TSV，确认新增子项可解释向量阶段时间；
  与上一轮同档位对比时保持机器、构建模式和后端组合一致。
- 四档服务矩阵错误数为 0，索引结果与向量/BM25 数量一致；远端分支的本地引擎计数器按定义保持 0。
- 趋势文件表头变更时确认工具重建表头，不保留旧列数据。

## 执行结果

devs 上以同步包 `cce-src-3f059c45-writepath-followup.tar.gz` 部署后，
`cargo check --workspace --all-targets`、`cargo build -p cce-cli -p cce-server`、
`cargo clippy --all-targets --all-features`、`cargo test --workspace --lib` 均通过；
检查点恢复 13/13、向量写入 4/4、BM25 对齐 6/6、相关 e2e 查询 9/9 通过。
检查器另修复了 `cce-scanner` 基准夹具中生命周期不匹配的既有编译错误。

5,000 文件完整流水线改为回路 mock 嵌入后，向量阶段可解释子项为：
嵌入 5.66 s、点构造 0.19 s、chunk/映射落库 2.33 s、工作单元记账 0.02 s；
向量事务 10 次、写入 5,000 点、WAL flush 10 次，BM25 提交 1 次。
暂存窗口峰值 7,756 条派生记录，随 512 点阈值有界。
四档服务矩阵同档位墙钟 59.3–67.1 s，错误数为 0，远端分支的本地引擎计数器按定义保持 0；
服务路径本地分支同样记录到 10 次 flush、5,000 点。服务在数据清理后全部停止，端口关闭。

向量阶段仍有约 15 s 未归入上述四项（含批量间等待和后端调用返回后的簿记），
50,000 文件档与关系快照容量 SLA 尚未在本轮复测。
下一阶段的拆分、内存治理、故障注入与覆盖补齐方案见
`docs/plan/write-path-scale-next-phase.md`。

## 明确不做

- 不关闭 WAL、不降低同步级别，也不跳过 flush。
- 不通过调大 `scan_batch_size` 或 `embedding_batch_size` 掩盖提交频率问题。
- 不改变召回、查询融合或确定性点 ID 的生成方式。
- 不修改生产 provider 限流默认值，不引入旧路径兼容层。
