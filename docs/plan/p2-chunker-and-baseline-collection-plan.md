# P-2 chunker 并发与待采集基线：数据收集、修改方向与后续改进

> 输入：根目录 `perf-analysis.md`（T-2/T-3 已测，T-1/T-4~T-10 待采集）、`docs/benchmark/perf-overhead-design.md`（P→T 映射与实施顺序）。
> 本次工作：重跑 T-3 采集本机基线，抽查 T-7/T-8 验证收集链路可用，其余待采集基线给出逐项收集方案；核对 P-2 描述与当前代码的一致性并确认修改方向。

## 一、核心结论先行

1. **P-2 描述与当前 `FileProcessor` 代码不一致**：全量索引热路径上不存在全局 chunker `Mutex`。`GroupChunker` 及其下属 splitter/overlap/estimator 全是构造后不可变、`&self` 方法，天然可经 `Arc` 共享；`FileProcessor::clone` 对 chunker/converter/grouper 都是 `Arc::clone`（共享只读），协调器是深拷贝后装入新 `Mutex`（各任务独享），热路径 `process_code_file_with_mode` 全程不进 chunk 缓存。因此“锁分片/去锁 chunker”对此路径无对象。
2. **唯一真实存在的 chunker 锁在热更新导出路径**：`NlDocumentUpdateProcessor` 持有 `Arc<tokio::sync::Mutex<GroupChunker>>`，但其 `process_operation` 是顺序循环逐文件处理，锁从未被并发争抢；它属于可直接移除的冗余异步锁，而非性能瓶颈。
3. **T-3 四轮数据一致指向“核数封顶 + 执行器阻塞”，而非互斥锁**：串行→并发加速比始终落在约 1.4×~3.7× 区间，且并发度超过工作线程数后（k=8→64）不再变化。本机（5 核）两轮新数据为 2.27× 与 1.79×。天花板来自 tokio 工作线程数与 CPU 密集型解析/分块直接跑在 async 任务上，而非某把锁。
4. **待采集基线中 T-7/T-8 本次已验证可采集且信号清晰**：快照发布与全量重建均随实体规模近似线性放大（10k→100k 约一个数量级以上），`from_index_shared` 零拷贝路径与深拷贝路径的数量级差成立。其余 T-1/T-4/T-5/T-6/T-9/T-10 给出逐项收集命令与降载手段，本机不再逐个重跑（见第四节）。

## 二、P-2 代码现状核查

核查范围为全量索引批处理实际走的路径（`index/orchestrator/batch.rs` 的 `process_batch_with_mode`）与其调用的 `index/file_processor` 三个文件，以及热更新导出路径。

- 批循环对批内每个文件 `tokio::spawn` 一个任务，任务内先拿信号量许可，再调用所属克隆体的处理方法。克隆体来自 `self.file_processor.clone()`。
- 该 `clone` 实现中，协调器是加锁取出内层值、克隆后装入全新 `Mutex`（任务间不共享）；预处理器、转换器、分块器、文档管道路由、各类指标全是 `Arc::clone`（共享只读）；分块缓存 `chunk_cache` 是共享的异步读写锁，但代码文件的完整处理路径不经过该缓存（缓存仅服务热更新的已解析复用与文档分块入口）。
- `GroupChunker` 的全部对外分块入口均为共享引用方法，内部逐调用新建 `GroupTracker` 等局部状态，不存在跨文件可变共享；下属的文本切分器、重叠管理器、词元估计器同样只读。因此 `Arc<GroupChunker>` 并发调用无需任何锁。
- `ParseCoordinator` 的解析入口要求可变借用，故 `FileProcessor` 用同步互斥体包裹。但由于克隆语义是每任务独享，批处理并发下该锁基本无竞争。它只在“同一处理器实例被多任务直接共享而不克隆”的用法下才会成为串行点，当前批循环不属于此用法。
- 基准 `chunker_concurrency.rs` 头部注释仍称“全局 `Arc<Mutex<GroupChunker>>`＋共享解析协调器”，与上述现状不符，需要随本次结论修正，否则后人会按错误的锁假设去做锁分片。
- 导出处理器（`export_processor.rs` 及其 `export/export_staging.rs` 的兜底分块函数）是全仓库唯一用锁包裹分块器的生产代码，锁为异步互斥体。但其调用方是顺序循环，不构成并发瓶颈；修改价值在于消除不必要的异步锁持有，而非提升吞吐。

## 三、T-3 本机重测与分析

### 3.1 数据对照

负载口径与历史一致：合成 Small 工程取前 200 文件走完整读盘→解析→分组→转换→分块流程，运行时为 8 工作线程。TSV 现累计四轮：

| 轮次 | serial（200 文件） | bounded_k8 | unbounded_k64 | 加速比（unbounded/serial） |
|---|---|---|---|---|
| 历史轮（文档已收录） | 962.6 ms | 700.2 ms | 700.9 ms | 约 1.37× |
| 历史轮（TSV 有、文档未收录） | 357.6 ms | 96.3 ms | 104.6 ms | 约 3.42× |
| 本机轮 A | 451.3 ms | 173.2 ms | 198.5 ms | 约 2.27× |
| 本机轮 B | 466.3 ms | 292.9 ms | 260.6 ms | 约 1.79× |

criterion 侧 `unbounded_64files`（64 文件子集）在本机约 53~83 ms 量级，历史文档值为约 225 ms，绝对值随机器与负载噪声浮动较大，但相对关系（k=8 与 k=64 基本持平）四轮一致。

### 3.2 如何解读

- 轮间绝对耗时浮动可达约 2~3 倍（本机串行 451~466 ms 相对稳定，并发轮 173~293 ms 浮动明显），说明该基准对机器负载敏感。做回归判断时应看“加速比区间＋饱和形态”，而非单轮绝对毫秒数。
- 四轮共同形态是 k=8 即达顶、k=64 无增益。结合工作线程数为 8，这是典型的“并行度被执行器线程数封顶”。若瓶颈是某把全局锁，同样会呈现此形态，但代码核查已排除热路径锁的存在；更直接的解释是 CPU 密集工作以 async 任务形态占用工作线程，超额任务只增加调度开销。
- 因此 P-2 的后续投入应从“找锁拆锁”转向“执行器与并发度治理”（见第五节）。原文档按 Amdahl 定律指向锁的推断在本机代码现状下不再成立，特此修正。

### 3.3 收集方法（T-3）

- 正确命令为 `cargo bench -p cce-orchestrator --bench chunker_concurrency`（设计文档中所写的 `cargo run -p ... --bench ...` 并非合法 cargo 语法，按字面执行会报参数错误）。
- 输出两部分：控制台与 TSV 的一次完整场景手动计时（serial/bounded/unbounded 三行），以及 criterion 对 64 文件子集的 10 采样分布。以后回填基线时以 TSV 的加速比与 criterion 的中位数为准，criterion 打印的回归提示对比的是本机 `target/criterion` 历史残留，不必当作跨机器回归结论。
- 落盘位置为 `crates/app/cce-orchestrator/benches/results/chunker_concurrency.tsv`，该目录被版本忽略，仅 `.gitkeep` 入库，基线数字需人工抄入基线文档。

## 五、确认的修改方向

以下按“做”与“不做”分列，避免把精力投到已不存在的锁上。

### 5.1 不做的事项

- 不对 `FileProcessor` 的分块器做锁分片、锁拆分或每文件独立分块器池：热路径本就没有锁，增加池化只会引入配置与一致性成本。
- 不把解析协调器的同步互斥体改为分片锁：当前克隆语义下它不是共享瓶颈；若未来改为单实例多任务共享，才值得重新评估。
- 不为追求 k=64 的数字去调大并发：超过工作线程数的任务只增加调度开销，四轮数据已反复证明无收益。

### 5.2 要做的事项（按优先级）

1. **修正基准注释与文档口径**：将 `chunker_concurrency.rs` 头部关于全局分块锁的描述改为“当前热路径无锁，并发天花板来自执行器线程与阻塞式 CPU 任务”，并同步更新 `docs/benchmark` 下的 P-2 表述，防止后续优化走错方向。
2. **移除导出路径的冗余异步分块锁**：分块器共享引用即可并发调用，把 `NlDocumentUpdateProcessor` 与兜底分块函数的异步互斥体改为直接共享只读实例，持有方式与其他调用方一致。此为纯简化，不预期吞吐变化。
3. **把 CPU 密集阶段移出 async 工作线程**：解析、分组、转换、分块均为阻塞式 CPU 计算，应经专用的阻塞池或并行执行器承载，避免占满 tokio 工作线程后请求侧与进度上报被饿死。这是 T-3 加速比逼近核数的正道。
4. **收敛并发度到核数**：批处理的 `max_concurrency` 默认值与基准的 bounded 档应以逻辑核数为基准设定，允许小幅超配但不再以 64 这类远超核数的并发作为优化目标。
5. **收窄分块缓存的写锁范围**：热更新复用路径目前对缓存是“读命中即写锁、未命中再写锁”的两段式，可改为读锁探测加写锁回填，并保持按输出模式隔离键的现有正确行为。此项预期收益小，列为顺手优化。
6. **补齐 T-8 的 TSV 落盘**：`snapshot_cost` 是目前唯一只打印控制台与 criterion 而不追加 TSV 的基准，应补上与其他基准一致的追加写，否则基线无法回填。

### 8.2 T-3 前后对照（200 文件）

改前本机两轮（k=8 workers，`process_file_complete` 全程跑 worker）：串行 451.3/466.3 ms，并发最优 173.2/260.6 ms，加速比约 1.79×~2.27×。

改后三轮（workers=核数 5，`process_entry_blocking`）：

| 轮次 | serial | bounded（k=5） | unbounded（k=64） | bounded 加速比 |
|---|---|---|---|---|
| 改后 A | 385.7 ms | 121.7 ms | 134.2 ms | 3.17× |
| 改后 B（高负载） | 548.1 ms | 348.7 ms | 750.1 ms | 1.57× |
| 改后 C | 493.5 ms | 186.2 ms | 135.6 ms | 2.65× |

中位数：串行约 494 ms，并发最优约 186 ms，加速比约 2.65×，约为 5 核理想值的 53%（改前约 40%）。方向与结构目标一致，但受验证期系统负载波动影响，单轮噪声大（B 轮负载下无界 64 线程池被显著放大到 750 ms，恰好反证生产必须以信号量封顶并发——无界场景作为护栏的意义正在于此）。bounded 与 unbounded 全程基本持平，超核并发依然无增益，符合预期。

criterion `unbounded_64files`（64 文件子集）：改后均值约 40~86 ms，与改前同口径区间重叠；无界场景本就不承诺增益，未将其作为回归指标。
