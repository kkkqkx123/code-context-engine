# 写路径规模化下一阶段设计方案

## 依据与范围

本文承接 `docs/plan/write-path-scale-followup.md` 的执行结果与
`docs/issue/performance-writepath-remaining-2026-11-23.md`，只登记仍未关闭的事项。
提交边界聚合、派生写入同边界、向量阶段首轮子项拆分、完整流水线计数口径修复均已完成，不再重复实施。
本阶段继续在现有模块上修改，不新增版本化模块、兼容层或生产默认配置开关。

## 现状判断

5,000 文件服务档的向量阶段已降到约 20 s，其中嵌入 0.9 s、点构造 0.17 s、
chunk/映射落库约 2.7 s、工作单元记账 0.03 s；仍有与向量阶段总量同量级的时间未归因。
已知缺口包括：向量 flush 墙钟未单独计时、每个微批逐一查询工作单元状态、
实体 ID 游标扩充与批间等待未计时、暂存推入与阈值提交边界的成本未拆分。
50,000 文件档向量阶段约 542 s，占总墙钟约 72%，不能只凭 5,000 档结果推断已收敛。

50,000 文件档关系构建前后 RSS 从约 1.5 GiB 升至约 9.2 GiB。现有
`build_and_publish_relations` 的两条回放路径都会保留全量 `ParsedFile`：内存缓存分支调用
`collect_all()` 持有全部解析结果，磁盘回放分支先用 `for_each` 把全部文件收集进 `Vec`
再构建符号表。缓存启用条件只看编码后体积与条目数，无法约束解码后的常驻内存。
这比最终关系快照本身更符合“批次结束后才突增”的观测形态，应作为内存治理的第一目标。

四类崩溃边界尚无专门故障注入用例：向量 flush 前失败、flush 后标记前失败、
BM25 提交前失败、提交后派生写入失败。现有检查点、向量写入与 BM25 对齐测试验证了机制，
但没有覆盖这些具体时点的状态与重放行为。

## 任务一：向量阶段剩余拆分与提交前查询收敛

先在现有计数器上补齐可解释性：向量 flush 墙钟、微批推入与暂存耗时、
实体 ID 游标扩充耗时、工作单元预查询耗时与次数、批间延迟与重试退避耗时。
计时仍由存储协调器内部累计，全量索引开始清零、批次循环结束回填阶段指标，
并同步到 API DTO 与两份阶段 TSV；表头变化时由报告工具重建趋势文件。

再把每个微批一次的工作单元哈希查询收敛为每次写入遍历一次该阶段的工作单元列表，
在内存中按哈希索引后判断跳过或重放。向量与 BM25 两条路径使用同一语义，
不得因为优化跳过对账，也不得把 `Running` 记录误判为 `Committed`。
实体 ID 游标沿用递增方式，只补计时，不在缺少证据时重写加载策略。

验收：medium 档向量阶段未归因部分降到可解释范围；50,000 文件档向量阶段绝对耗时下降、
规模曲线较上一轮更接近线性；WAL flush 次数、工作单元状态和索引结果不变。

## 任务二：关系阶段峰值内存与容量归属

修改现有关系构建与符号表构建接口，使符号表注册、实体注册和关系解析都能按 spool 顺序逐文件推进。
取消内存缓存回放分支与磁盘回放分支中的全量文件收集，统一为磁盘 spool 上的多阶段流式回放：
每次只持有一个解析文件，三阶段顺序保持确定性，最终关系快照语义不变。
这不是新增替代模块，而是把现有构建入口改为流式接口并删除全量驻留路径。

在阶段边界采集结构容量：spool 条目数与编码字节数、符号表包/全局名称条目数、
关系索引函数节点、文件节点与边数、导出 spool 条目数、实体 ID 映射条目数、最终快照条目数。
容量以条目数和显式估算字节数同时输出，进入阶段 TSV；允许随文件数增长的结构与必须有上界的结构分别给出结论。
对最终关系快照只发布容量事实，不为了压低 RSS 截断关系或改变召回。

验收：50,000 文件档峰值 RSS 明显下降，或给出经实测支持的容量 SLA；
关系快照与上一轮逐字节一致；关系阶段耗时不出现数量级回归；阶段 TSV 能定位剩余内存归属。

## 任务三：提交边界故障注入测试

在存储协调器写入边界增加仅测试使用的失败注入点，采用枚举与计数器表达，不使用动态分发，
不进入生产配置。注入点覆盖：向量 flush 前、flush 后工作单元标记前、
BM25 提交前、提交后派生元数据写入失败四个时点。
每个用例必须断言数据是否已落盘、工作单元是否仍为 `Running`、批次检查点是否停在失败窗口之前，
以及恢复重放后点 ID 覆盖而不重复、派生映射不丢失、文件状态不被批量逻辑吞掉。
测试目录与远端对象按 `docs/spec/testing.md` 隔离并在作用域结束时清理。

## 任务四：工程前置条件与覆盖缺口

将根 `Cargo.lock` 纳入版本基线，固定已完成解析的依赖集，在本地和 devs 上都以
`cargo check --locked` 作为验收命令；不保留机器间首次解析产生差异的状态。

服务基准脚本在运行前检查文件句柄上限与磁盘可用容量，不满足前置条件时直接失败并给出原因；
不以降低持久化、刷新间隔或文件句柄要求换取通过。

ES、Qdrant 与生产 provider 限流只做独立 SLA 观测：提高冷查询采样数、记录首字节延迟、
JVM 堆与进程 RSS、限流预算与实际等待，不改变生产默认值，也不把 ES 当成 Tantivy 等价替换。
恢复失配输入补齐文件列表哈希、磁盘内容与版本字段三类夹具；
50,000 文件远端四档矩阵按容量条件执行，未执行时记录明确跳过原因。

## 执行顺序

1. 先完成任务一的计时与查询收敛，用同档位数据确认向量阶段剩余成本来源。
2. 再执行任务二的流式回放改造，避免在全量驻留状态下继续叠加容量指标。
3. 任务三与任务一、二的交界改动同步补充，每次提交边界调整都必须带故障注入用例。
4. 最后处理工程前置条件与独立 SLA 覆盖，避免把环境问题混入写路径性能结论。

所有编译、单测与基准仍在 devs 完成；日志与 TSV 取回 `.bench_logs/`，
结论和未关闭项回写对应 issue 文档。

## 执行结果

devs 上以同步包 `cce-src-3f059c45-nextphase.tar.gz` 部署，全量重新解压后
`cargo check --locked --workspace --all-targets`、`cargo clippy --locked --all-targets --all-features`
与 `cargo test --locked --workspace --lib` 均通过；检查点恢复、向量写入、BM25 对齐与相关 e2e 查询均通过。
新增四个提交边界故障注入用例，验证 flush 前、flush 后标记前、BM25 提交前、提交后派生写入失败的状态与重放。

50,000 文件完整流水线墙钟从上一轮约 752 s 降到 439 s；向量阶段从约 542 s 降到 252 s。
新增计时把向量阶段全部归因：嵌入 61.7 s、flush 8.2 s、暂存推入 7.1 s、派生元数据 21.5 s、
实体 ID 游标 2.7 s、批间等待 151.7 s、工作单元 0.02 s；批间等待是首个需要单独治理的剩余项。
工作单元预查询从每微批一次收敛为每编排批次一次，50,000 档为 500 次。

关系构建改为 spool 上的流式多阶段回放后，50,000 档峰值 RSS 仍约 9.6 GiB，并未下降；
但容量指标显示批次结束 1.4 GiB、关系结束 9.3 GiB，关系索引 1,349,968 个节点按实测
每节点约 6 KiB 估算约 8.3 GiB，与增量吻合。全量驻留已移除，剩余内存属于最终关系索引容量，
按容量 SLA 继续治理；本轮不通过截断关系降低 RSS。

medium 服务矩阵四档错误数为 0，墙钟 59.3–65.6 s；向量阶段约 20 s 已由各子项完整解释，
远端分支本地引擎计数器按契约保持 0。服务已停止、运行数据已清理、端口已关闭。
根 `Cargo.lock` 已取消忽略，服务脚本新增文件句柄与磁盘容量前置检查。

## 明确不做

- 不关闭 WAL、不降低同步级别、不跳过 flush，也不伪造缓存命中或计数器。
- 不通过调大 `scan_batch_size`、`embedding_batch_size` 或改变 mock 限流掩盖提交频率问题。
- 不改变召回口径、查询融合语义、确定性点 ID 与关系快照内容。
- 不新增版本化模块、旧路径兼容层或生产环境的失败注入开关。
- 不在缺少阶段与容量数据时继续调整持久化或索引参数。
