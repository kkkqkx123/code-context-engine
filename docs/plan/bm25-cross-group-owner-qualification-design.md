# BM25 独立成员属主限定修复方案

## 1. 背景

Jackson-core 转换结果已确认以下改动有效：

- 同名重载方法可以获得各自独立的实体边界，不再因重载名坍缩到首个匹配位置而缺失成员数据。
- BM25 路径在实体边界之后允许退化为行边界，方法签名块不再直接进入词元硬切。
- 容器组中的 BM25 续写段会重复自身覆盖成员的属主身份。

但转换结果同时暴露出剩余问题：大型类拆分出的独立方法组仍然只有裸方法标题。例如 `ByteQuadsCanonicalizer` 的四个 `findName` 重载已经成为独立且未中切的块，但标题和关键词中没有 `ByteQuadsCanonicalizer`。对于 `ByteQuadsCanonicalizer.findName` 一类限定查询，干净的独立方法块仍缺少类名与方法名的强共现。

## 2. 根因

### 2.1 普通切块路径没有继承组历史

`chunk_single_path()` 只把历史 `GroupTracker` 传给 header 路径。普通独立组在不需要切分时使用新建立的空 tracker，在需要切分时也重新建立空 tracker。

结果是：

- `cross_group_parent()` 无法从 tracker 中解析父组。
- 即使分组阶段已经建立正确的 `parent_group_id`，BM25 标题生成仍然拿不到父组名。
- 普通路径最终块关系由后续统一补写，所以标题限定失效没有表现为关系字段缺失，而是直接表现为标题和关键词缺少父类。

### 2.2 续写身份只使用当前组名

`continuation_identity()` 通过 `group.name` 推导属主。独立方法组的 `group.name` 本身就是方法名，不是类名。

因此即使标题和关键词后续能够取得父组，独立方法组的续写段仍可能只重复 `method findName`，无法形成完整的 `Class.method` 身份。

### 2.3 `parent_group_id` 存在语义不一致

`parent_group_id` 的约定应为组标识，但部分分组路径写入了父实体名：

- `nested.rs` 将父实体名称直接写入 `parent_group_id`。
- `pipeline.rs` 中针对类型别名实现的分支将实现块名称写入 `parent_group_id`。

转换器的层级关系以及 `GroupTracker::lookup_identity()` 都按组标识查找，名称值无法解析。即使修复 tracker 传递，这些分组形态仍然不会得到正确的跨组限定。

### 2.4 成员标题优先使用了当前组名

`bm25_title_for_ids()` 对容器组成员优先组合 `group.name` 和成员名。当合并组或碎片组的 `group.name` 是某个成员名，而真正的属主来自父组时，可能生成成员之间的错误组合，而不是父类限定后的成员名。

## 3. 目标

本方案修复独立成员和跨组子组的属主识别，使 BM25 的检索锚点与实际 AST 所有权一致。

具体目标：

- 独立类成员组的 BM25 标题使用 `Class.method`、`Class.field` 等父属主限定形式。
- 对应关键词同时包含成员名和父属主名。
- 独立成员组的 BM25 续写段重复限定后的成员身份，而不仅是裸成员名。
- 跨组标题、关键词、续写身份使用同一套属主解析规则，避免三处行为漂移。
- `parent_group_id` 在所有内置分组路径中保持组标识语义。
- 父组解析不依赖父组必须在子组之前完成切块。

## 4. 非目标

- 不改变已经验证有效的重载边界定位算法。
- 不改变 BM25 实体边界到行边界的退化顺序。
- 不修改向量路径的文本结构和摘要规则。
- 不修改词元预算、块大小上限和源位置覆盖计算。
- 不为了本问题引入文件名词干作为独立方法组的默认父类。
- 不在本方案中重新设计大型 Class 组与独立 Method 组的文本重复关系。
- 不直接以基准指标为依据调整 BM25 字段权重。

## 5. 设计原则

### 5.1 属主只来自真实所有权

限定顺序为：

1. 当前组已明确属于容器，且容器名表示真实类型时，使用容器名。
2. 当前组是跨组子组时，使用父组的非模块类型名。
3. 模块、包、命名空间只作为层级容器，不作为成员检索属主。
4. 没有真实父类型时，保留现有模块词干限定，但仅限自由函数。

独立 Java 方法组属于第 2 类，应使用其 Class、Interface 或 Enum 父组。不能因为 Java 文件通常与公共类同名，就把文件名词干当作普遍父类。

### 5.2 身份解析不依赖处理顺序

父组的名称和类型应在分组阶段即可确定。BM25 生成时可以通过文件级组集合预先登记身份，使父组即使尚未进入切块序列也能被解析。这样可避免当前“必须前面已记录”造成的隐性顺序约束。

### 5.3 一处解析，多处复用

标题、关键词和续写身份不应分别猜测父组。应由组级上下文统一计算一个可选的属主限定名，然后三个消费点共享同一结果。

## 6. 修改方案

### 6.1 规范父组标识

为 `EntityGroup` 增加按实体标识生成组标识的统一辅助逻辑，内置分组构造器和层级解析共用同一规则。

需要调整：

- `nested.rs` 不再把父实体名写入 `parent_group_id`，改写为父实体对应的组标识。
- `pipeline.rs` 的类型别名实现分支需要保留目标类型别名实体标识，并让方法组的 `parent_group_id` 指向该类型别名所属组。
- 其他已经使用组标识的父链接保持现有语义。

如果某个父实体没有形成可检索组，则不应伪造 `parent_group_id`。此类场景由分组阶段记录一个可选的父实体展示名，或明确保留为无限定独立组；不应通过模糊字符串回退掩盖所有权信息缺失。本方案优先修正已有父组可定位的场景。

### 6.2 预先登记文件级组身份

在 `GroupTracker` 中区分两种登记：

- **身份登记**：记录组标识到组名、组类型的映射，不创建前后继关系。
- **处理登记**：现有行为，既记录身份，又把当前组加入处理序列。

`chunk_groups_builtin()` 在逐组转换前先遍历本文件所有组，执行身份登记。随后正常执行逐组处理登记。这样：

- 子组可以解析后续才会处理的父组。
- 前后继关系仍保持真实处理顺序。
- 跨组父限定不再受分组向量的偶然顺序影响。

单组公共入口如果没有文件级上下文，则继续使用调用方已有 tracker；不能创建空 tracker 来假装不存在历史关系。

### 6.3 向普通切块路径传递历史

扩展 `ChunkInput`，使其显式携带当前文件的 `GroupTracker` 引用。

需要删除两处新建空 tracker 的逻辑：

- 未超限的单块分支。
- 已切分后的 `from_segments()` 分支。

调用方：

- `chunk_group()` 在记录当前组后，将 `self.tracker` 引用传入两条路径。
- `header_chunk.rs` 的独立 header 分支将外部 tracker 引用传入普通路径。
- header 参数结构中的重复 tracker 字段可以取消，统一使用 `ChunkInput` 的 tracker，避免两个 tracker 引用发生漂移。

### 6.4 统一计算组级属主

在 chunk builder 中增加统一的属主解析逻辑，输入为当前组、tracker 和文件路径，输出为可选属主限定名。

规则：

- 如果父组存在且父组类型不是模块类，返回父组名。
- 如果当前组是容器组且容器名非空，返回容器名。
- 如果当前组是自由函数且没有父组，继续返回文件词干。
- 其他情况不返回属主。

标题、关键词和续写身份都调用该规则，不再各自依赖 `group.name` 或直接调用父组查询。

### 6.5 修正 BM25 标题

`bm25_title_for_ids()` 改为：

- 先取得当前内容实体的本地名。
- 如果本地名已经带限定，保持不变。
- 否则使用统一属主规则形成限定名。
- 对合并组中的多个成员，不应继续简单把 `group.name` 当作父类；当存在真实父组时，父组优先于当前组名。

这样大型类拆分出的 `findName` 标题会变成 `ByteQuadsCanonicalizer.findName`，已经位于容器组内的成员标题保持现有正确形式，不会叠加成重复限定。

### 6.6 修正 BM25 关键词

`bm25_keywords_for_ids()` 使用同一属主：

- 保留成员本地关键词。
- 对容器成员和独立跨组成员，都加入真实父类或父模块中的类型名。
- 包、模块、命名空间仍不加入，避免把路径信息误当成检索属主。

目标是独立方法块至少同时具备 `findname` 与 `bytequadscanonicalizer` 两个可检索词，而不依赖体积庞大的原始 Class 碎片。

### 6.7 修正续写身份

`continuation_identity()` 不再只按 `group.name` 推导：

- 使用统一属主生成限定名。
- 独立方法续段应输出 `method ByteQuadsCanonicalizer.findName` 形式。
- 容器组成员续段继续输出原有 `Class.member` 形式。
- 首段已经以限定名开始时继续跳过重复身份。
- 无可归因实体时的组级回退也使用限定后的组名。

### 6.8 保持向量路径行为

向量路径已有独立的父级文本增强逻辑，本方案只把 tracker 历史和属主解析补回 BM25 块生成阶段，不把限定名写回实体原始名称或分组名称，避免向量摘要出现重复前缀。

### 6.9 恢复 BM25 文本的行结构

BM25 清洗统一改用保留换行的空白归一化，常规组模板各部分之间改用换行分隔。分词器把换行视为普通分隔符，索引词项流和词数预算不变；行切分策略因此获得真实可用的换行，超限单行大段转为行边界切分，极端超长单行仍由强制硬切兜底。向量清洗器与向量模板不受影响。

## 7. 对检索行为的影响

### 7.1 限定查询

`ByteQuadsCanonicalizer.findName` 等查询可命中干净方法块的标题、关键词和正文，不再只能依赖噪声较多的 Class 原始碎片。类名和方法名在标题中形成明确短语信号，预期会提升精确限定查询的排序质量。

### 7.2 裸方法查询

标题改成限定形式后，原本可能作为完整标题词出现的裸方法名会进入带点整体词和子词拆分流程。但正文签名和关键词仍保留方法名，因此仅按方法名检索不会因为标题限定而失去核心词项。风险应通过 jackson-core 导出和基准确认，不应据此提前放宽父类限定。

### 7.3 类名单独查询

更多方法块会在标题和关键词中携带类名，可能增加类词项的文档频率。这有利于 `Class.member` 共现，也可能稀释类摘要块相对方法块的区分度。字段权重保持不变，由基准结果判断是否需要后续调整。

### 7.4 模块父级

包和命名空间仍被排除，不会产生 `package.Class` 之类的过度限定。

### 7.5 文件词干限定

不扩大到方法、构造器或字段。文件词干只适用于没有真实父类型的自由函数，避免一个文件定义多个类型时生成错误属主。

## 8. 对现有切分结果的影响

属主限定部分不应改变下列指标：

- `split_reason` 的生成条件。
- 每组的边界数量和切分层级。
- `chunk_id` 与源位置范围。
- 向量块的正文。

行结构恢复部分会刻意改变 BM25 的切分理由分布：原来被迫硬切的单行大段转为行边界切分，块数量可能随之小幅变化，但词数预算、块大小上限和源位置覆盖规则不变。变化应集中在：

- `bm25_title`
- `bm25_keywords`
- BM25 续写段身份前缀
- BM25 碎片的 `split_reason` 由硬切转向行边界

如果重生成后向量块数量或向量文本发生变化，说明修改越过了 BM25 范围，应回退对应改动并重新定位。

## 9. 组描述超限问题的根因与处理

### 9.1 根因：BM25 清洗阶段抹掉了全部换行

Jackson-core 中 Class 组出现大量 `HardLimit` 的直接原因不是切分策略，而是 BM25 文本在进入切块器之前就已经失去行结构：

- BM25 模板输出经过统一清洗，清洗规则把所有空白字符折叠为空格，模板内各部分之间、文档行之间、内联代码片段之间的换行全部消失。
- 每个 header/member 转换结果因此变成一个单行大段，组装时只在块与块之间保留双换行分隔。
- 行切分策略只能在换行处下刀，单行大段超过预算后唯一出路是按字符预算强制硬切，于是出现 `class ByteQuadsCanonicalizer.` 身份头之后直接中切代码的现象。

继续在切分层级上加策略无法稳定改善，因为可用的换行根本不存在。修复点应在文本生成侧，而不是切分侧。

### 9.2 处理方案：恢复 BM25 文本的行结构

改动限定在 BM25 路径，不触及向量路径：

- BM25 清洗改为保留换行的空白归一化，只压缩行内多余空白。分词器把换行当作普通分隔符，索引词项流不变，词数预算不变，只有切分点会移动到行边界。
- 常规组模板的各部分之间改用换行分隔，使签名行、文档行、成员表各自成为独立的行单元。成员表和类型表内部保持单行信号形式。
- 内联代码片段原本就带有换行，清洗保留后自然成为可切分行。

预期效果是 Class 组碎片的 `HardLimit` 大幅转为 `LineBoundary`，同时块数量、词数预算、标题关键词规则保持不变。若重生成后仍有个别超长单行（如压缩代码），强制硬切作为兜底保留。

### 9.3 与属主限定修复的关系

行结构恢复与属主限定是正交改动，但建议同一批次落地：干净方法块的标题限定解决“找不到”的问题，行结构恢复解决“Class 碎片噪声”的问题。两者都不改变切分预算与向量文本，基准重跑时可以一次性评估。

## 10. 测试方案

### 10.1 分组阶段

- 验证 nested 组的 `parent_group_id` 指向父组标识，而不是父实体名。
- 验证类型别名实现的方法组能够解析到目标类型别名组。
- 验证没有父组时不会写入无效父标识。

### 10.2 tracker 阶段

- 身份登记不产生前后继关系。
- 父组排在子组之后时仍能解析父组名和类型。
- 模块类父组被正确排除。

### 10.3 chunk builder 阶段

- 独立方法组标题生成 `Class.method`。
- 独立方法组关键词包含父类名。
- 已经带限定的标题不重复叠加。
- 自由函数无真实父类型时仍使用文件词干。
- 独立方法组续写段身份包含父类限定。
- 容器组成员不出现 `member.member` 或父名重复。

### 10.4 chunker 集成

- 普通独立组经过 `chunk_groups_builtin()` 后获得父组限定。
- header 路径和普通路径使用同一文件级 tracker。
- `related_groups` 只表达实际处理序列，不因身份预登记而扩展关系。
- BM25 与向量两条路径的块数量保持原测试结果。

### 10.5 BM25 行结构

- 清洗后多行文本保留换行，单行超长输入仍被压缩为空。
- 常规模板各部分分行，成员表与类型表保持单行。
- 行级单测构造超限单行大段，验证切分理由从硬切变为行边界。
- 向量路径文本不受清洗改动影响，由既有向量单测覆盖。

### 10.6 Jackson-core 导出

重新生成 BM25 转换结果并检查：

- 四个 `ByteQuadsCanonicalizer.findName` 重载块仍分别为独立、未中切块。
- 四个块的标题均为 `ByteQuadsCanonicalizer.findName`。
- 四个块关键词同时包含方法名和类名。
- `JsonParser` 独立方法块获得正确的父类型限定。
- 包和模块父级没有进入标题。
- 已存在点号限定的标题没有重复叠加。

## 11. 验收标准

必须同时满足：

1. 独立类成员的干净 BM25 块自身具有父类名与方法名的直接共现。
2. 重载边界修复和 BM25 行边界修复的结果不回退。
3. 所有 `parent_group_id` 内置写入值均为组标识。
4. 父组解析不依赖父组先于子组完成切块。
5. 标题、关键词、续写身份三者属主一致。
6. 向量块数量和向量文本不因本方案改变。
7. Jackson-core 相关目标块的人工抽查结果符合预期。
8. 解析器、分组器和切块器定向测试通过。

## 12. 建议实施顺序

1. 先规范分组阶段的父组标识和组标识生成。
2. 增加 tracker 的身份预登记，并补充顺序无关解析测试。
3. 将历史 tracker 传入普通 `chunk_single_path()`，删除空 tracker 回退。
4. 提取统一属主解析逻辑，并迁移标题、关键词、续写身份三个调用点。
5. 恢复 BM25 清洗的换行保留，并让常规模板各部分分行。
6. 更新定向单元测试和导出检查。
7. 重新生成 Jackson-core BM25 结果，只做人工结构检查。
8. 最后重跑 jackson-core 检索基准，评估剩余 Class 碎片是否需要另立方案。

## 13. 风险与回退点

最高风险是 BM25 标题词形变化导致裸方法查询短期波动。出现退化时应优先检查正文与关键词是否仍保留方法名，不应立即取消父类限定或扩大文件词干回退。

次高风险是合并组成员标题的属主选择。需要确认父组优先规则只修正真实所有权，不把临时合并组名误当成类型属主。

分组父标识修改涉及跨 crate 类型约定，若测试暴露出缓存或导出兼容问题，应直接修正写入语义，不保留名称值和组 ID 值混合的兼容分支。
