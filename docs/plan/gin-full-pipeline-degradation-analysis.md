# gin 基准 full-pipeline 下滑分析与分阶段修改方案

## 1. 背景与数据来源

分析对象为 gin fixture 的三方对比：`direct_chunking`、`full_pipeline`、`full_pipeline_raw_source`，检索器为 `emb` 与 `BM25`，截断位以 `top5` 为主，辅以按查询类型聚合。

数据来源：

* 基准指标：`crates/app/cce-e2e-tests/outputs/benchmark/gin/` 下的聚合指标、按查询类型聚合、逐查询明细、相关性明细、运行清单与测试污染诊断。
* 横向对照：同目录下 `express`、`flask`、`jackson_core`、`mediatr`、`once_cell`、`ripgrep` 的 `aggregate_metrics_top5.md`、按查询类型聚合与运行清单。
* 转换结果：`crates/app/cce-e2e-tests/outputs/scenarios/go/chunks/gin/` 下 `emb` 与 `bm25` 两路分块文本。
* 原始代码：`crates/app/cce-e2e-tests/fixtures/go/review/gin/`，重点为 `gin.go`、`tree.go`、`context.go`、`routergroup.go`。

## 2. 指标分析

总体上 `full_pipeline` 相比 `direct_chunking` 出现小幅但稳定的下滑，而 `full_pipeline_raw_source` 在向量侧回救甚至反超，说明问题集中在转换文本而非切分位置本身。

核心对照（`top5 / impl_only`）：向量侧 `direct` 召回约 0.69、精确率约 0.17，`full` 召回约 0.67、精确率约 0.14；`raw_source` 召回与 `full` 持平，但精确率回升到约 0.19，综合值超过 `direct`。BM25 侧 `full` 与 `raw` 完全一致，召回与 `direct` 持平，精确率从约 0.16 降到约 0.15。

按查询类型拆分后下滑来源清晰：向量侧模糊查询召回从约 0.80 跌到约 0.60，精确率从约 0.21 跌到约 0.12，是整体下滑的主要驱动；限定查询召回从约 0.90 升到 1.00，语义查询召回从约 0.50 升到约 0.55。BM25 侧模糊与限定查询小幅下跌，语义查询小幅上涨。`raw_source` 主要修复模糊查询向量侧，从约 0.60 回到约 0.73。

逐查询明细显示跌点集中在易混淆查询：分发请求到处理器的语义查询在 `full` 向量侧从命中跌到零命中、`raw` 回到满命中；路由树处理器查找、纯文本错误响应、渲染响应等查询在 `full` 下丢失，`raw` 下部分恢复；树查找、处理器路由类模糊查询在 `full` 自然语言向量下丢失、在 `raw` 下回到高位。限定查询基本稳定，说明符号名完整出现时两路都能命中。

运行清单显示向量块数量从约 308 膨胀到约 843，BM25 块从约 1660 微降到约 1545。测试污染诊断显示 `full` 向量侧约四分之三为测试块，`direct` 向量侧约六成为测试块。按变体过滤后测试块已被排除，因此测试污染不是本次 `impl_only` 下滑的直接原因，但它解释了语料膨胀与排序噪声的背景。

## 3. 转换结果分析

向量侧自然语言转换存在三类失真。

第一是核心方法被打碎。路由查找核心方法约 247 行被拆成四个连续片段，标题均为结构续写加片段编号；请求分发主干被拆成处理上下文存根、尾部片段与本体三处，其中存根只有方法签名几乎无函数体；路由注册方法被拆成两块；上下文结构体被拆成方法名录加两个续写片段，名录只有签名列表而无实现。直接分块的命中位置多为文件级或大范围粗块，单个向量内保留完整方法与注释。

第二是模板噪声稀释语义密度。每个局部变量都附带类型与赋值来源复述，每个循环变量都复述迭代来源，加上数据类通用套话。判别性正文被大量重复句式淹没，近似兄弟节点的文本趋同。

第三是续写块丢失判别头信息。续写片段标题不再携带完整方法签名，只有结构名加片段编号，查询中的方法名无法在该块内直接对应，只能依赖相邻块，在 top5 截断下容易掉出。

BM25 侧保留源码但切分过碎。小结构体被拆成包声明、单个字段、类型别名、方法各一块，每块不足 30 词；大方法按硬截断从表达式中间断开，出现以运算符残片开头的新块。查询需要的共现关系被拆散，例如渲染方法与上下文归属、处理器与路由树路径不再同块；标题与关键词过于泛化，难以补偿这种共现损失。

## 4. 原始代码分析

gin 属于小词表高混淆框架，这是失真被放大的前提。上下文对象约 50 个方法大多经由统一渲染入口，渲染类查询必须靠参数与被调渲染器类型区分；引擎的上下文处理、服务入口与请求分发三者互相调用且共享路由树查找、链式调用与写回逻辑；路由节点的注册、插入、取值、通配符查找共享路径、处理器、通配标志与索引词表；小函数如错误响应、固定路径重定向只有十余行，极易被大块淹没或被碎块孤立。

原始注释本身具有判别价值，例如外层树遍历说明、优先尝试非通配子节点的策略说明。直接分块保留了这些注释，而自然语言转换将其丢弃或改写为结构复述。

## 5. 根因总结

过切分破坏判别上下文是首要原因。能区分查询的完整体被拆成续写片段，单块只剩通用循环与赋值模板，语义相近的兄弟节点在向量空间不可分。

自然语言归一化抹掉模糊查询信号是第二原因。模糊查询依赖表面形态，下划线、大小写与符号名被改写后，模糊召回大幅下跌；同切分下用原文做向量即回救，证明切分位置不是主因，文本形态才是主因。

BM25 词频与共现被稀释是第三原因。过碎小块使判别词不再同块出现，硬截断进一步破坏短语完整性，标题关键词过泛无法补偿。

## 6. 横向对照：下滑是语言相关的，不是全局的

| 项目 | 语言 | full_pipeline 相对 direct 的表现 |
|---|---|---|
| express | JS | 向量与 BM25 均大幅提升 |
| flask | Python | 召回微降，精确率大涨，综合值提升 |
| mediatr | C# | BM25 提升，向量召回提升、精确率微降 |
| ripgrep | Rust | BM25 提升，向量召回提升、综合值微降 |
| jackson_core | Java | 向量综合值持平微升；同切分原文向量崩盘，说明自然语言文本必不可少 |
| gin | Go | 向量与 BM25 综合值均下滑；同切分原文向量回救，说明自然语言文本是损失源 |
| once_cell | Rust | 向量崩盘式下滑，BM25 提升；与 gin 同构 |

结论：gin 与 once_cell 同属一类失败——小词表、高符号混淆或小而精的库中，自然语言归一化抹掉了向量检索依赖的表面标识信号；jackson 则相反，原文在解析器切分位置下对向量完全不可用，自然语言转换是收益源。因此修复必须针对高混淆符号场景做减法（去噪声、保标识、合碎块），而不是改动对其他语言有益的转换主体。

## 7. 分阶段修改方案

阶段一：混合主题小块不再 claims 主题纯度，允许救援合并。`merge_strategy` 的自包含豁免原本保护低于阈值的小主题块不被合并，但 gin 的续写块（约 108 词元，含通用续写头加两个方法残片）因此永远无法与其邻块合并。调整为：豁免只适用于单内容实体的纯主题块；携带多个内容实体的块本身已是混合主题，合并不会稀释任何纯主题。合并上限保持不变，超长方法不会被重新拼回。改动落在合并策略模块，附单主题仍受保护、多实体可合并两组单测。

阶段二：变量关系描述与签名去重。gin 包级块中每个局部变量同时出现关系复述与完整赋值签名，两者携带同一调用标识。改动后当签名已包含关系核心标识时跳过关系行；循环迭代标记予以保留，因其是行为判别信号。改动落在向量模板的关系描述生成，附冗余跳过与循环标记保留两组单测。

阶段三（验证性质）：确认 BM25 跨组小块合并生效。结构体块与字段块各仅约 10 词，低于 80 词阈值，跨组链式合并应将其拼合；若在现行代码复现中仍分离，则按同一切换思路处理 BM25 侧。本阶段先以单测锁定链式合并行为，基准重跑时再确认。

## 8. 验证方法

用现有 gin 基准重跑三基线对比，验收口径为模糊查询向量召回与精确率回升、总体向量综合值不低于直接分块、限定与语义查询不回退；抽查路由查找、请求分发、渲染响应三个代表查询的命中排名是否回到前五；检查续写碎块比例、无签名块比例是否下降；同步确认 express、flask、jackson、once_cell 四个对照项目不回退；最后执行全量编译检查与格式化。

## 9. 非目标

不引入新的召回算法与权重调优，不改动混合融合逻辑；不处理测试污染过滤策略的变更，本次变体过滤语义保持不变；不重做历史数据的兼容，开发期数据按需重新生成。
