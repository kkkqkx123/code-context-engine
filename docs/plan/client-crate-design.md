# CCE 客户端 crate 设计（cce-client）

本文回答两个问题：CCE 是否应该提供官方客户端 crate，以及它应当长什么样，才能同时服务 CCE 自己的 CLI、
未来的 GPUI 客户端，以及外部消费方（当前是 wf-agent 的 code-context 集成）。

## 1. 现状盘点

盘点以改造前的代码为准（相关模块已在本次改造中删除，故表格同时说明去留）。

| 位置 | 改造前内容 | 问题 | 现状 |
|---|---|---|---|
| `cce-api` | wire 模型、路径模板、查询参数结构、错误码与错误体、utoipa 注解 | 只有"契约零件"，没有"一次调用"的完整表达：路径常量、参数、请求体、响应类型四者靠调用方自行配对 | 保留并补齐：查询参数结构补上序列化能力，路径只留模板与一处占位符展开 |
| `cce-transport` | reqwest 管道（get/post/put/delete/delete_with_body/get_text）、统一 300s 超时、令牌解析、`GraphQuery` 查询串构造、4 个 ingest 便利方法 + 1 个聚合检索方法 | 通用管道 + 少量特例；错误用 `anyhow` 承载，状态码只能靠文本映射；超时一刀切；查询串参数名由调用方重复书写 | 已删除，职责并入 `cce-client` |
| `cce-cli/src/client.rs` | `CliApi` 扩展 trait：21 个 typed 方法 | 调用面锁在 CLI crate 里；只覆盖 21 个操作，CLI 其余命令仍在命令层手拼 URL 与查询串（约 40 处通用 `get/post/put/delete` 调用） | 已删除，命令层改用 `cce-client` 类型化方法 |
| `cce-gateway/src/client.rs` | `GatewayClient`：包一层 `SharedHttpClient`，再加一个通用 `post` 与 4 个 ingest 方法 | 与 transport 的 ingest 方法重复，同一端点两份包装 | 已删除，gateway 直接用 `cce-client` 的 ingest 方法 |
| `cce-mcp` | 只复用 `cce_api::models` 的类型，直接调 orchestrator（进程内） | 合理：本地调用不该走网络 | 不变 |
| `frontend` | `openapi-typescript` 从 `tools/openapi-codegen/openapi.json` 生成 `schema.d.ts`，`openapi-fetch` 调用 | 唯一有"契约漂移守卫"的消费方（`contract:check`，但只校验路径集合，不校验参数类型） | 保留，参数类型随本次契约修正同步更新 |
| `wf-agent`（本项目外部） | 在 `wf-integration` 里手写 code-context 的请求构造、响应解码与错误分类 | 服务端契约之外又抄一遍客户端解码，漂移没有任何编译期或测试期提示 | 迁移目标 |

## 2. 结论

**需要提供 `cce-client`，并让它取代 `cce-transport`。** 缺的不是模型，而是"每个 operation 唯一一处调用方式"
的归属。改造前 `(路径, 查询参数, 请求体, 响应类型)` 这个四元组在 CLI 命令层、gateway、transport、前端生成物和
wf-agent 里各有一份，其中 Rust 侧的绝大多数不在任何契约测试覆盖之内。

对原稿设计的评审结论是"方向成立、若干决策需修正"，修正项如下（下文各节已按修正后的结论书写）：

1. **模块表必须与路径常量闭合。** 原稿模块表漏掉了 `config`、`qdrant`、`retry_queue`、`metrics` 之外的
   `logs` 一类端点，若照此实现，守卫测试就得为"已存在但没有客户端方法"的端点维护例外清单，方向反了。
   修正：模块按资源切分并覆盖全部路径常量，例外清单只保留真正没有 Rust 消费方的端点（日志文件管理，
   见第 5 节），并写明原因。
2. **请求标识头没有接收方。** 原稿要求客户端生成 `x-request-id` 以"让两侧日志按同一标识对齐"，但服务端
   既不记录也不回显该头，对齐承诺不成立。修正：本轮不发该头，错误里保留"方法 + 路径 + 状态 + 错误码 +
   信息"，这些才是真能定位问题的事实；若将来需要贯穿标识，必须客户端与服务端同批实现。
3. **错误分类不能把 5xx 归入"不可达"。** 5xx/429/408 有响应、有错误码，是服务端明确作答；把它们与"连不上"
   混为一类会让消费方丢失状态码。修正：以"是否收到响应"划第一刀，再按状态码分三类，状态码始终保留。
4. **错误码 → 分类映射不该在客户端再写一遍。** 服务端已用一张表把错误码映射成状态码；客户端再维护码表就是
   第二份真相。修正：客户端只按状态码分类，错误码作为不透明字符串透传。
5. **"数字 id 同时接受数字与十进制字符串"不是既有契约事实。** 契约里的 id 一律是字符串（稳定符号 id），
   没有任何端点接受两种拼写。修正：删除该要求，解码交给 serde 的严格规则。
6. **"能力探测"方法属于策略，不属于客户端。** 需要多个请求并解释结果的方法会把判定逻辑搬进客户端。
   修正：客户端只提供单次请求的类型化方法（例如健康检查），能力判定留在消费方。
7. **查询串不该由客户端逐字段拼。** 参数名已经在 `cce-api` 的查询结构上声明了一次；再在客户端写一遍就是
   两份。修正：客户端直接接收 `cce-api` 的查询结构（补上序列化能力），由 HTTP 层编码。
   该修正暴露了一个既有缺陷：`excluded_files` 原先被客户端发成重复键，而服务端用 `serde_urlencoded`
   解码、无法接受重复键，参数实际不可用；现改为逗号分隔字符串，与服务端其它列表参数一致。

## 3. 目标与非目标

目标：

1. 每个对外 operation 在 Rust 侧只有一处调用方式，路径、查询参数、请求体与响应类型绑定在一起。
2. CCE 自己的一等消费者（CLI、未来 GPUI 客户端）共享同一套调用面，不各自维护薄封装。
3. 外部消费者（wf-agent）可以直接依赖该 crate，从而把"上游响应形状"从文档假设变成编译期事实。
4. 客户端与 `cce-api`、OpenAPI 快照三者之间可被自动校验，漂移在测试阶段暴露。

非目标：

1. 不把策略搬进客户端：重试、断路器、健康缓存、项目/索引生命周期、并发与批量调度都属于消费方。
2. 不做本地（进程内）实现与远程共用一套 trait：本地调用继续走 orchestrator，避免为对称性引入 `dyn` 双实现。
3. 不在本轮引入 API 版本协商；兼容判定的位置留给消费方的健康检查。
4. 不生成新的前端产物：前端继续由 OpenAPI 生成 TypeScript 类型，与 Rust 客户端是同一份注解的两个投影。

## 4. 分层与依赖方向

```
cce-api（契约事实：模型 / 路径模板 / 错误码，零 IO）
      ↑
cce-client（调用面：每个 operation 一次调用 + 解码 + 错误分类 + 超时）
      ↑
消费方：cce-cli、cce-gateway、cce-desktop(GPUI，未来)、wf-agent（外部）
```

- `cce-api` 保持无 IO、无 reqwest 依赖。
- `cce-client` 取代 `cce-transport`：管道、令牌解析、错误类型一并迁入，然后删除 `cce-transport`。
  不保留"旧管道 + 新客户端"两份（仓库本身不承诺向后兼容）。
- `cce-server` 不依赖 `cce-client`；服务端只依赖 `cce-api` 的模型与注解。
- 依赖方向不得回指，客户端不得依赖 orchestrator / server / storage。客户端只认 HTTP 与契约模型。

## 5. 模块划分

按资源切模块，与 OpenAPI 的 tag 对齐，一个模块内三种东西：请求构造、解码、typed 方法。方法集合覆盖
`cce-api::paths` 中全部路由常量，唯一的例外见本节末尾。

| 模块 | 覆盖 |
|---|---|
| `project` | 项目列表/创建/详情/更新/删除、项目索引、项目配置读写与重载、LLM 配置概览/更新/测试 |
| `index` | 全量索引、增量索引、单文件解析、摘要生成 |
| `search` | 单查询、聚合查询、实体检索 |
| `tools` | 折叠（单个/批量）、压缩（单个/批量）、诊断、关键词检索、符号、引用、定义 |
| `graph` | ego / path / subgraph / components / export / impact / entity-impact / cycles / structural / module |
| `entity` | 函数详情、调用/被调用、调用链、调用路径、类继承与实现、分类统计与分类明细 |
| `dead_letters` | 列表、重试、确认 |
| `storage` | 清空/删文件/删实体/批删、索引统计、存储状态 |
| `watch` | 启停与状态 |
| `health` | 健康、三路服务诊断、重试队列读写、准入计数 |
| `metrics` | 指标文本、指标 JSON、历史、清理 |
| `config` | 服务端配置信息、校验、重载 |
| `qdrant` | 被托管进程的状态与启停重启 |
| `ingest` | manifest / batch / commit / event（服务端按 `admission` feature 注册，客户端无条件提供） |

日志文件管理端点（`/api/logs` 一族及其 WebSocket 通道）**不在客户端覆盖范围**：它们是 Web 控制台专用的
文件管理界面后端，没有 Rust 消费方，其载荷也未在 `cce-api` 建模；为它们补方法会要求先造出没有消费方的
契约模型。该例外在守卫测试中以显式清单声明，清单项若与路径常量失配则测试失败。

每个模块的解码函数是纯函数：输入一段固定报文（fixture），输出 typed 结果或协议错误。这样协议漂移先在
单测里失败，而不是在消费方的运行期表现为"空结果"。

## 6. 设计决策

1. **一个 operation 只有一处调用面。** 路径取自 `cce-api::paths` 的模板常量，占位符展开只有一处实现
   （`paths` 提供的项目作用域展开 + 客户端内部对单段标识符的百分号编码）。客户端不写字面量路径，
   `paths` 也不再提供"每个端点一个构造函数"的平行入口，避免同一路径两条拼装路径。
2. **契约缺口补在 `cce-api`，不补在客户端。** 客户端不定义自己的 wire 结构：缺模型就把模型加进
   `cce-api`（连同 utoipa 注解），否则客户端会长出第二份"看起来一样"的结构体，漂移问题原样回来。
3. **契约守卫。** 守卫测试读取 `cce-api/src/paths.rs` 的源码，枚举全部路由常量，要求每个常量要么在客户端
   源码中出现引用，要么在"不覆盖"清单里；清单项若已不存在于常量集合，同样失败。这样"新增端点忘了加客户端
   方法"会在测试阶段失败，而不是等着某个下游手抄。
4. **客户端不下策略。** 客户端只做"一次请求"：连接、超时、解码、错误分类。重试/退避/断路器/健康缓存
   归消费方。同一份客户端可被并发克隆使用（克隆共享连接池）。
5. **错误模型类型化，不吞状态码、不读文本。** 四个类别：
   - `Unavailable`：没有可用响应（连接失败、超时），或状态码属于可重试集合（5xx、429、408）；
   - `Unauthorized`：401/403；
   - `Rejected`：其余 4xx，原样重试不会成功；
   - `Protocol`：2xx 但报文与声明的响应类型不符。
   分类只由"是否有响应 + 状态码"决定，服务端错误码与信息作为字段透传；仅当响应体不是契约错误体时，
   才把原始文本作为诊断信息保留（不解析、不猜测）。
6. **2xx + `success:false` 是业务答复，不是错误。** CCE 有"命令被正确执行但结果是拒绝"的端点（死信重试、
   确认、部分配置操作）。这类响应原样返回，由调用方判断；只有 HTTP 层失败才是错误。
7. **解码严格且前向兼容。** 缺必备字段即协议错误（serde 的报文里带缺失字段名）；未知字段一律忽略。
   可选字段用 `Option` 表达，禁止用默认值伪造缺失语义。id 一律按契约中的字符串处理。
8. **超时分层。** 两类预算：交互级（一次请求/响应往返，默认 300s）与长任务级（全量/增量索引、摘要生成、
   项目索引、清空与批删、死信重试、ingest 提交、进程启停、LLM 探测、指标清理，默认 1800s）。
   长任务预算可由消费方在构造期覆盖（CLI 的 `--timeout-secs` 即映射到该开关）。每个方法按类别固定使用
   对应预算，客户端不内置重试，因此超时语义就是"这一次调用的上限"。
9. **凭据只声明环境变量名。** 沿用现状（`CCE_API_TOKEN`）并保留显式 token 参数（优先级高于环境）；
   令牌在构造期解析一次，挂在客户端默认头上，一处生效覆盖全部端点。值不进入 `Debug`、日志与错误文本。
10. **本地调用不走客户端。** MCP 与未来的嵌入式用法继续直接调 orchestrator。客户端是为"远程服务"定义的，
    不试图让本地与远程共享一个 trait（避免 `dyn`，也避免把网络语义渗进本地路径）。
11. **两个投影，一份事实。** Rust 侧的契约事实是 `cce-api` 注解；OpenAPI 快照从服务端注解生成，前端类型
    从快照生成。客户端只允许使用 `cce-api` 类型，因此三者不会各自漂移。GPUI 客户端复用 Rust 客户端，
    不再新增第三条调用实现。
12. **crate 位置与命名。** `crates/app/cce-client`，与 `cce-api`、`cce-cli`、`cce-gateway` 同层。
    未来 GPUI 应用作为同层的新 crate，只做视图与交互状态，数据访问全部经由 `cce-client`。
13. **feature 与目标环境。** 默认特性只含 JSON 通道；文本导出（Prometheus 指标）作为同一 crate 的非
    JSON 通道方法，不额外开 feature。`admission` 只影响服务端注册，客户端方法集合与之解耦。
14. **查询参数复用 wire 结构。** 客户端方法的查询参数就是 `cce-api` 里对应的 `*Query` / `*Params` 结构，
    参数名与默认值只有一处声明；客户端只负责把它们交给 HTTP 层编码，列表类参数统一用逗号分隔字符串。

## 7. 各消费方的迁移方式

1. **落地 crate**：`cce-transport` 的管道、令牌解析、错误类型迁入 `cce-client`，`cce-transport` 及其依赖
   声明删除；工作区成员表随之更新。
2. **CLI**：删除 `cce-cli/src/client.rs`（`CliApi` trait 与 21 个方法），命令层改为调用客户端方法；命令行
   特有的输出格式化、表格渲染与面向用户的错误文案留在 CLI，错误直接按 `ClientError` 的 `Display` 呈现。
   原先手拼查询串的地方改为构造 `cce-api` 的查询结构。
3. **gateway**：删除 `GatewayClient` 包装（5 个方法、CLI 里 2 处构造点与同步链路对它的引用），直接使用
   客户端的 `ingest` 方法；同步/监听循环仍留在 gateway。ingest 提交不再发送占位空对象请求体。
4. **补全其余 operation**：CLI 覆盖不到的端点（分类统计与明细、qdrant、配置信息/校验/重载、指标清理、
   LLM 配置、项目配置读取）随模块一次补齐；守卫测试保证"要么有方法、要么在显式清单里"。
5. **wf-agent**：以路径依赖或 git 依赖引入 `cce-client`，删除 `wf-integration` 里手写的 code-context 请求体
   与解码，只保留自己的活状态（端点/健康/能力/项目供给/断路器）与维护面编排。迁移完成后，wf-agent 侧
   "上游响应形状是假设前提"这条风险项应当消失，改为编译期绑定。
6. **GPUI 客户端**：直接依赖 `cce-client`；交互状态（面板、缓存、轮询节奏）留在应用层。

## 8. 验收标准

- `cce-client` 单测：错误分类（不可达/超时/5xx/429/408 → 可重试，401/403 → 凭据，其余 4xx → 拒绝，
  报文不符 → 协议）、令牌不回显、超时分层常量生效、路径与查询串编码、信封错误体与裸错误体的解析。
- `cce-client` 集成测试（本地 stub 服务）：实际发出的方法、路径、查询串编码、请求体、Bearer 头，
  以及 503/404/200-报文不符 三类错误分类；文本通道返回原始报文。
- 契约守卫：`paths` 常量与客户端调用点的对应关系测试通过；"不覆盖"清单无失效项；OpenAPI 快照与
  路由/注解一致性测试保持通过。
- CLI 与 gateway 迁移后行为不变：命令级用例（本地 stub 服务）通过，退出码不回归。
- 前端 `schema.d.ts` 与快照的路径集合仍一致（`contract:check`），列表参数类型随契约修正更新。
- `cargo clippy --all-targets --all-features` 零新增告警；`cargo fmt` 干净。

## 9. 风险与未决项

- **发布方式**：开发阶段建议 path 依赖（两仓库同时改最省事）；若 wf-agent 需要独立构建，再决定 git 依赖
  与 tag 策略。这一决定不影响 crate 边界。
- **长任务预算默认值**：索引与 ingest 提交的 1800s 上限是保守估计，需要与服务端实际耗时分布对齐；
  调整点只有一处常量，且消费方可覆盖。
- **能力探测的落点**：没有版本端点时，能力判定由消费方用健康检查 + 项目端点自行组合（wf-agent 已按此
  实现）。上游补版本端点后，客户端只增加一个读取版本的方法，判定仍留在消费方。
- **契约变更的连带更新**：查询参数类型变化会同时影响 OpenAPI 快照与前端生成物，二者必须与 `cce-api`
  同批更新，否则 `contract:check` 与 TypeScript 类型检查会滞后暴露问题。
- **本地与远程的对称性**：MCP/嵌入式用法不经过客户端，意味着"同一操作两套调用路径"。这是有意的：
  本地路径不引入网络语义，客户端只为远程定义。若未来需要统一，应当先统一 orchestrator 的入参模型，
  而不是给客户端加本地实现。
- **验证基线**：`cargo clippy --workspace --all-targets --all-features`（无排除）与 `cargo fmt --check`
  零告警零差异；`cce-config`、`cce-orchestrator`、`cce-server-shared`、`cce-server`、`cce-api`、
  `cce-client`、`cce-cli`、`cce-gateway`、`cce-mcp`、`cce-metrics`、`cce-parser` 的测试全绿（含 stub
  全链路用例、契约守卫与 OpenAPI 快照守卫）；前端 `contract:check` 与 `svelte-check` 通过。`cce-e2e-tests`
  属外部子模块，需要真实服务与较多磁盘，未在本轮执行。
