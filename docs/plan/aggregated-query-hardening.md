# 聚合查询子查询加固设计

## 背景

当前 `/api/search/aggregated` 由调用方显式给出多条子查询，服务端并发执行完整检索管线后按统一对齐键合并。现有实现已经具备共享 epoch view、有界并发、阈值后移、合并后单次关系扩展和两级结果缓存，但存在四类问题：

1. 响应字段把“请求条数”当成“实际执行数”，缓存命中时也不区分聚合层和子查询层；结果对象中的耗时在缓存命中时仍是上次计算耗时。
2. 部分子查询失败的降级结果会写入聚合缓存；关系快照版本未进入聚合缓存键；聚合过滤条件以调试字符串参与键计算，脆弱且不可靠。
3. 子查询分数被当作 `[0,1]` 证据使用，但权重上界和零权重没有约束；重复子查询会被当成独立证据；rerank 在每条子查询上重复执行，跨查询分数可比性不足。
4. 端到端测试没有真正调用聚合路径，效果基准缺少真实墙钟延迟和更完整的子查询组合，性能基准没有覆盖聚合 API。

本设计只修改原始模块，不新增并行实现。

## 目标

- 响应字段准确表达计划数、实际执行数、成功数、缓存层级和本次请求耗时。
- 聚合缓存只保存完整成功的结果；关系快照变化时聚合展开结果不被错误复用。
- 子查询计分有明确定义的值域和权重边界；无效子查询在计划阶段被合并或拒绝。
- rerank 与结果过滤从每条子查询上移到合并后的全局阶段，只执行一次。
- 补齐聚合路径的单元测试、端到端测试和基准观测。

## 非目标

- 不实现服务端自动查询拆分。调用方仍然显式给出子查询文本、来源和权重。
- 不改变 hybrid fusion 的算法；它是单查询内的路径融合，与跨查询聚合是两个层级。
- 不实现跨后端数据迁移，也不改变索引格式。

## 修改顺序

### 1. 观测语义

将单一且含义模糊的 `sub_queries_count` 替换为四个明确字段：`planned_sub_queries` 表示请求中的子查询条数，`executed_sub_queries` 表示本次真正发起检索管线的数量，`succeeded_sub_queries` 表示成功返回候选列表的数量，`sub_query_cache_hits` 表示其中由子查询缓存直接满足的数量。`from_cache` 继续只表示聚合层缓存命中，并在文档中明确。

`elapsed_ms` 在返回边界根据本次调用的起始时间计算，不允许把缓存条目里的历史耗时直接返回。HTTP handler 继续保留自己的墙钟计时；引擎结果对象也要对缓存命中给出本次耗时，供 MCP、内部评测和基准使用。

### 2. 缓存正确性

聚合结果只有在全部子查询成功时才允许写入缓存。部分失败仍按既有契约返回成功响应，但结果对象携带降级标记，缓存层根据该标记跳过写入。

聚合缓存键显式加入关系快照版本：当请求启用了关系扩展时，关系图版本变化必须产生新的缓存键。过滤条件从调试字符串改为逐字段结构化哈希，避免格式变化导致键漂移。

### 3. 子查询计划与计分

子查询权重限定为大于零且不超过一。零权重没有贡献却要付完整检索成本，因此直接拒绝；超过一的权重会破坏 Noisy-OR 的 `[0,1]` 证据假设，也在 Max 策略下破坏全局阈值语义，因此同样拒绝。

完全相同的子查询按文本、来源和权重折叠，只执行一次。重复子查询不应被当作多条独立证据，否则 Noisy-OR 会人为抬高同一实体的分数。

所有贡献分在进入合并前统一归一化到 `[0,1]`。Noisy-OR 保持累积公式；Max 也使用同一套分数清洗规则，确保两种策略都在相同值域内工作。

### 4. 后处理位置

子查询阶段关闭 rerank 和结果过滤插件，只负责召回、基础融合和候选脱阈。合并完成后，以原始请求文本作为 rerank 上下文执行一次 rerank 与结果过滤，然后应用唯一一次全局阈值、排序和截断。关系扩展继续只作用于最终 Top-N。

这样既减少 N 倍后处理成本，也避免不同子查询上 rerank 分数分布不一致导致的跨查询加权失真。

### 5. 测试与基准

修复 e2e 助手中空转的聚合调用，使其真正进入 `search_aggregated`。补充参数校验、重复折叠、部分失败不缓存、关系版本变更、缓存命中计时和子查询并发确定性测试。

效果基准中把墙钟计时放在调用外侧，避免复用缓存条目中的历史耗时；union 基线应用与 merged 结果相同的阈值。聚合效果报告的每行新增 `wall_ms`、`reported_ms`、`executed` 和 `cache_hits`，用于区分真实请求耗时与缓存条目内的历史耗时。

新增 `examples/aggregated_search_perf.rs`，在小型固定 fixture 上扫描子查询数与请求并发矩阵，区分冷/热缓存，并把 p50、p95、吞吐和子查询执行数写入 `outputs/benchmark/aggregated_search_perf.tsv`。

## 验收标准

- 缓存命中请求报告 `executed_sub_queries = 0`，但仍报告原始 `planned_sub_queries`。
- 部分失败结果不会在后续相同请求中直接命中缓存。
- `expand=true` 时关系快照版本变化使聚合结果重新计算。
- 相同子查询只执行一次；非法权重在 API 和引擎两层被拒绝。
- rerank handler 在一条包含 N 条子查询的聚合请求中只收到一次调用。
- 聚合 API 的单元与端到端测试全部通过；基准输出包含本次请求的真实墙钟时间。
