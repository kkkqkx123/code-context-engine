# 向量路琐碎片段治理：价值门与广播去重设计（2026-11-12）

前序命题工作完成后，chunk 审查暴露了一个更基本的问题：
向量语料中约两成 chunk 是单行裸身份（无文档、无事实、无调用、无签名），
它们不可能提供任何语义，只消耗预算并参与排序。
本文档先给度量与机制分析，再给设计。
只动向量路，词项路逐字节一致仍是硬护栏。

## 1. 度量

### 琐碎 chunk 普查（向量路，无命题、无长句、无调用行的 chunk）

- Go：1274 个 chunk 中 253 个琐碎（约百分之二十），占行数约百分之十。
- C++：3560 个中 913 个（约百分之二十六），占行数约百分之二十四。
- Rust：2359 个中 443 个（约百分之十九），占行数约百分之二十二。
- Python：434 个中 55 个（约百分之十三），占行数约百分之十二。

重灾区是 C 头文件：单个头文件内 32 个琐碎 chunk，
极端如 12 个 token 的 include-guard chunk
（`macro _dash_mpd_h_.` 加一行文件角色行）。
这类 chunk 在向量空间中只有身份词加文件词，
不可能回答任何语义查询。

### 文件角色行广播

`In file X.` 占向量总行数约一成（Go 约百分之九，C++ 约百分之十二），
高于任何单个命题动词的份额；单个文件内出现数十次
（如某源文件 33 次）。该行来自更早的文件角色行改动，
属预存问题，但正文缩短后其密度被动上升：
成员数不变，代码行减少，文件词权重相对升高。
后果是文件级查询词命中该文件的每一个 chunk（包括琐碎 chunk），
真正的函数块要与数十个同文件琐碎块竞争。

### 命题点火率佐证覆盖偏斜

命题行占向量总行数：Go、C++、Python 约两成，
Rust 仅约百分之六点六。Rust 以引用表达式为主，
而引用类型在渲染映射中被整体丢弃，
引用密集区的查询信号恰好落空。这与读流搜索 gap 未动吻合，
属相关证据而非定论。

## 2. 机制分析

琐碎片段来自三件事的乘积：按实体切分把极小成员独立成块，
模板对每个成员逐段发射身份加文件角色行，
以及全程没有任何价值门。切分优化的是纯度，
但纯度只对有信号的成员有意义；
对无信号成员，独立成块等于批量生产近 identical 向量。

此前验证看不见它，原因有三：
判定集从不以琐碎实体为目标，召回指标只看命中不看语料噪声，
词项路靠词面精确命中本来就不受影响。
预算浪费是确定的，排序伤害是结构性风险
（文件词 crowd-out 机制如上），边界排名波动可能已有贡献。

需要诚实承认的方向问题：按实体切分优化了错误目标。
它保证了“有信号成员不被稀释”，却没回答“无信号成员凭什么进向量”。
命题工作与此正交：无事实实体在命题前后逐字节一致，
既没造成琐碎问题，也没解决它。
根本缺的是一道价值门，而不是更细的切分或更多的句子。

## 3. 设计

指导划分：向量路只承载命题性文本（语义检索），
词面精确导航归词项路（已有能力，无需重复建设）。
琐碎成员的名字仍在词项路可发现，分组头仍列成员清单，
向量路删的是排序噪声，不是可发现性。

### D1 向量路成员准入

在模板现有的向量路成员过滤处（与 import、样板过滤同一位置）
扩展一条：成员同时满足以下全部条件时，不发射其向量成员块，
词项成员块保持不变。判定只用该成员自身信息，不跨实体、不查索引。

- 无文档注释。
- 无调用行（自身不调用任何外部目标）。
- 无变量关系元数据（非派生变量、非构造器关联）。
- 无命题产出（无可映射事实，或映射后头部与尾部皆空）。
- 不是带实现体的函数类（纯原型声明，或根本不是函数类）。
  非函数类不设初始化器兜底：
  模块级变量的调用初始化若有语义，由调用目标元数据覆盖保留；
  否则其名与字面量仍在词项路，足以精确导航。

前四条任一不满足即保留；最后一条专为调用相关实体设兜底：
保证任何有实现体的可调用定义都不可能被丢弃：
调用点活在调用者体内，调用者必有实现体；
单行委托函数虽可能零命题（如隐式返回的尾调用），
但其定义体非空，照样保留；
纯原型声明与裸身份（宏简写、枚举变体、字段、无文档常量、守卫宏）
五条全中，才允许消失。函数原型声明同理，有文档才留。

### D2 chunk 级文件角色行去重

同一 chunk 内完全相同的 `In file X.` 只保留首次出现。
同文件同行，信息无损，逐成员复述纯属浪费。
位置在 chunk 最终文本装配处，与模板解耦。

### D3 组头成员名单兜底

类型组头已有方法签名清单与字段清单，
被掏空的合并组其向量 chunk 自然消失，词项侧保留。
是否需要补一行成员名单，先不断言：
G1 判定目标经核查全部是函数或方法（四项目），
预测零回归，若预测失败则回退并补名单。

### D4 命题模块配合

沿用命题噪声文档的拆分与守卫表设计，不重复。
新增一项先行度量：统计独立数据引用事实的占比，
用以坐实“引用丢弃无害”的假设；若占比不可忽略，
再设计引用句式，否则维持现状。

### 非目标

不动词项路任何逻辑，不动切块分组逻辑
（只在向量文本发射层过滤，chunk 结构自然收缩），
不删除任何源码信息（信息仍在词项路与组头），
不做跨实体信息收集。

## 4. 验证计划

- 计数目标：media 向量琐碎 chunk 由约九百降至接近零，
  `In file` 行数下降约八成，Rust 命题点火率回升。
- 硬预测：G1 全项目零翻转（目标全是函数或方法，且经核查皆有实现体），
  任一翻转即回退且可精确归因。
- 保持项：media 差距翻转保持，词项行零变化，
  单视图不新增确定性回归。
- 数值走固定向量 A/B 或两次重嵌取均值，
  落抖动带记为未证实。

## 5. 小实体是否完全交由词项路：全量丢弃与打包二选一

理论上成立：孤立定义本身不包含语义。
有真实语义必有正式使用，使用处活在调用者体内（调用者必有实现体，必保留）；
被调用的小函数自身若有实现体也在保留之列；
嵌套实体已由分组与组头清单处理，不在本节范围内。
因此向量路删去纯声明，删的是排序噪声，不是可发现性：
名字精确导航本就归词项路（子词切分与精确拼写是其优势区间）。
作为附带收益，嵌入请求量下降约一成三至两成六
（与琐碎 chunk 占比同量级，media 约九百 chunk、约四分之一行数）。

### 5.1 函数定义与函数调用为何丢不掉

五子句门中前四条任一满足即保留，
第五条（有代码体）是专为调用相关实体设的兜底：

- 调用点是调用者体内的语句，调用者必有实现体，整体保留，
  调用事实（调用句、派生句、调用行）不受影响。
- 单行委托函数即使零命题（如隐式返回的尾调用在 Rust 提取中无对应事实，
  实测如字面策略的匹配函数），也因定义体非空而保留，走原有原文回退。
  该提取缺口记为提取层后续事项，不影响门的安全性，
  因为门不依赖事实存在，只依赖定义体存在。
- 模块级变量初始化中的调用由调用目标元数据覆盖，保留。
- 纯原型声明（无体函数）允许消失：其名与签名仍在词项路，
  且经核查八个项目的 G1 目标全部是带实现体的多行定义，
  无一是原型或裸身份。
- 有文档的原型、宏、常量不受影响，文档即保留条件。

### 5.2 两种处置对比

方案甲（默认推荐）：达到丢弃条件的成员在向量路直接不发射。
代价是约三十个纯声明文件（经核查全为 C 头文件、测试媒体桩与若干示例小文件）
在向量侧消失；词项侧完整保留，可发现性不受影响。
文件级语义查询本来就不应命中只有声明的文件，
消失的是噪声席位而非答案。

方案乙（回退选项）：同一组内连续的丢弃 run 合成一段，
一段只保留一个文件角色行加裸身份行，
提供最低限度的文件级嵌套痕迹；
长度为一的孤立单行直接丢弃（单独成段无意义）。
代价是多一处成段逻辑；收益是文件 footprint 保留与误删安全网。
仅当方案甲被证实有害（文件消失导致可验证回归）时启用。

### 5.3 判定方法

硬预测仍以 G1 零翻转与差距翻转保持为准，另加一项：
抽查文件级查询在方案甲下的表现，
若纯声明文件的消失带来可复现的命中丢失，则切方案乙。
两种方案共享 D2（文件角色行去重）与全部验证口径；
任一硬预测失败即回退，回退即恢复发射（开关式，无需数据迁移）。
