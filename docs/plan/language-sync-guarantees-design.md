# 语言同步保证设计方案

## 1. 背景与问题

语言分发散落在至少六处，每处都有通配回落，新增语言时静默降级，无人知晓。

* 解析门禁有两个定义：`Language::is_supported_for_ast`（二十四个变体，含前端七语言与插件语言）是流水线的真正门禁；`cce-parser-core` 的 `AstParser::is_supported`（十六个，不含前端与插件语言）是重复的窄定义，已被诊断工具引用，对前端文件会误报不支持。
* 标准库识别覆盖十六个解析语言加 JS 家族，前端模板语言无分支。
* 调用裁剪裸方法表缺 C 与 Dart，目前靠识别器全覆盖隐式成立，无人锁定。
* 去噪画像只有 Rust 特化，其余全保守关闭，这是合理的，但无人声明。
* 插件语言走全部回落分支。实体级标准库已有 `LangHeuristics` 扩展点兜底，但调用级识别、裁剪表、去噪画像没有插件扩展点；`LanguageRemap` 复用宿主语法却拿不到宿主语言的分发表，是明确的缺口。

## 2. 原则

* 编译期强制不可行：语言枚举含插件变体与数据格式变体，通配臂去不掉；且各层支持语义本就不同，不应强求同一集合。
* 用测试断言做保证：规范列表定义一次，各层期望表引用它，新增语言时测试变红，强制开发者逐层确认。
* 插件语言无法静态枚举，约束放在注册时警告与降级语义锁定，外加复用关系的继承。

## 3. 阶段一：统一支持定义

`AstParser::is_supported` 改为委托 `Language::is_supported_for_ast`，删除窄定义。诊断工具对前端文件的误报随之修复。两处原有单测保留，语义不变。

## 4. 阶段二：规范列表与三层期望测试

* 在类型层新增可解析语言规范列表，作为 `is_supported_for_ast` 的唯一实现依据，插件变体因动态性另行处理。
* 标准库识别测试：规范列表中每个有分支的语言配一个哨兵调用断言为真；模板语言断言为假并注明其嵌入块以降级后的宿主语言重新进入各层。
* 调用裁剪测试：期望表覆盖规范列表，C 与 Dart 显式记空并注明依赖识别器覆盖。
* 去噪画像测试：期望表锁定 Rust 全开、其余关闭，新增语言时必须更新期望表并给出理由。

## 5. 阶段三：插件语言约束

* 在类型层新增有效语言解析：插件变体若登记了复用目标则映射到宿主语言，否则保持自身。非插件语言走无锁快路径。
* 调用级识别、裁剪表、去噪画像内部先解析有效语言再分发，复用插件自动继承宿主行为，原生插件保持保守回落。调用方无需改动。
* 补冒烟测试：原生插件语言确认保守降级不断言崩；复用插件确认行为与宿主一致。
* 注册时警告：语言插件缺少 `LangHeuristics` 配套能力时记警告并在文档中说明能力矩阵，暂不硬性失败，保持能力可选组合。
* 文档明确插件语言在各层的默认行为与已知限制（调用级识别无插件扩展点）。

## 6. 验证

每阶段独立合入：全量单测、裁剪与格式检查。阶段间无依赖堆积，任一阶段可独立回滚。
