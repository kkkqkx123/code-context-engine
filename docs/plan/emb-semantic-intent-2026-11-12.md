# emb 语义鸿沟：意图缺失与稀释的优化方案（2026-11-12）

## 1. 背景与基线

上一轮三处改动复验后部分回退：撤销加法别名，仅保留去可见性修饰与循环变量合一两处纯删除。当前线上数据即该状态产物，以其为本轮真正基线并重建备份。

语义题上 emb 落后 BM25 的全部 gap（emb 未命中而 BM25 命中，impl_only 全管线口径）：gin 四题（G2Q1 分发请求、G2Q6 请求体绑定、G2Q14 模板渲染、G2Q15 格式化输出），once_cell 一题（G2Q7 无标准库临界区实现），ripgrep 一题（G2Q20 读流搜索），media_server 三题（G2Q3 包序列化、G2Q10 分发、G2Q15 会话头解析）。flask 语义题 emb 全胜，是天然对照组。

另有方法论基线：重嵌本身带有约一到四个查询的抖动带，文本零变化的对照基线在重嵌后同样翻转。本轮任何结论必须能排除抖动解释。

## 2. 病因分析

逐题对照目标源码区间与向量块文本后，病因按主次排列如下。

### 2.1 意图真空（主因，约七成 gap）

无文档注释或文档为空话时，向量文本等于身份行加调用表加原始函数体。原始代码只描述做法（赋值、分支、位运算），从不陈述意图。稠密向量把几百 token 的做法平均成一团代码 soup，与自然语言查询无法对齐；BM25 靠标识符碎片命中故不受影响。

证据：ripgrep 读流搜索目标无文档，文本是身份行加十五个原始符号的调用表加原始代码，查询词 stdin 与 stream 全词缺席；三个 C 语言目标整块几乎全是内存拷贝与指针运算，没有一句解析或序列化；请求分发目标四百余 token 全是赋值分支，文本从未出现分发与匹配；请求体绑定目标的文档是正确的废话，真正语义只存在于一行被原样保留的源码里。

反证：flask 目标全部携带完整文档字符串，命题天然存在，语义题全胜。模板改写救不了意图真空，因为输入里就没有意图。

### 2.2 同块兄弟稀释（兼因）

目标实体只占块的约一到两成，其余是兄弟方法的文档与函数体。BM25 对长度不敏感，词命中即得分；稠密向量是平均池化，兄弟内容直接把目标向量拖走。模板渲染目标本身文本很好，却被排在两个长方法之后；请求体绑定目标是四方法块的尾巴，查询词反而把模型引向词面更像但答案错误的兄弟块，这是语义检索最不该输的输法。

### 2.3 文件与模块上下文丢失

查询的区分词存在于文件名与模块层级时，模板整体丢弃。无标准库临界区查询的两个关键词只存在于文件名后缀与 use 声明里，目标块文本一个词都找不到；读流搜索的流来源同样在方法之外。模型无法桥接文本中不存在的词。

### 2.4 同义鸿沟被代码淹没

分发目标块拥有全项目最好的两行自然语言（按类型分支到音视频与脚本处理），但查询说分发而文本说分支，查询说标签而文本只有类型字段。该由向量完成的同义桥接，被三百 token 的分支原始代码稀释到失效。

### 2.5 为何上一轮改动无效

三处改动全动的是身份行（占块约百分之五），而病因是缺失的命题（占比零，变不出来）、占主导的原始代码体、缺失的文件上下文。在错误的位置上抛光。

## 3. 设计方案

全部改动只动自然语言转换原模块的向量路，不新增模块，不动词项路，不动既有预算数值。新增上限一律用与现有锚点同量级的常量并在设计中记名。

### 3.1 向量侧函数体上限（主改动，对应病因一、二、四）

向量文本的函数体部分只保留控制流与行为事实片段（分支条件、调用点，即意图骨架），跳过无事实间隙的原始源码回填与尾部补全；无事实兜底的整段函数体截断到头部约一百五十 token。词项路保持全文回填不变，术语表仍用全量文本。

理由：全部九个 gap 块中，真正携带区分信号的永远在前几行，尾部全是实现噪音。把分母砍掉比给分子加词有效一个数量级；限定查询依赖的标识符本就活在身份行、签名与调用行，不在函数体中部。

### 3.2 调用行动词化与封顶（对应病因一的无文档情形）

调用表是无文档实体唯一的事实来源，但现状是原始符号堆砌（含自身引用噪音），且过长时成为跨块共享成分。向量侧将其封顶到八个目标（与分支锚点同量级），去自身引用噪音，去重，保留调用冒号的句子形状。词项路不动。

### 3.3 文件角色行（对应病因三）

在组头与各成员的向量文本各追加一行：文件词干的自然词，附带同组导入实体的外部 crate 根（去重封顶）。全部 token 取自文件自身，不虚构语义。成员块各自携带，不依赖组头复述。该行专治文件级寻址查询。

### 3.4 向量路按实体切块（延期，对应病因二、四）

把稀释连根拔起，但块数量与形状大变，对当前已通过查询的回归风险最大。待前三项落地后，若残留的失败仍被证实为兄弟稀释所致，再启动。本轮只把触发条件记为后续。

## 4. 变更范围与护栏

只改转换原模块内向量路三个位置：富化阶段的函数体上限、模板的调用行、转换器的文件角色行。词项生成、词项清洗、评测与对齐口径、既有预算数值一律不动。词项文本逐字节一致仍是硬护栏；新增单测覆盖上限开关、调用封顶、文件角色行三例。

## 5. 验证计划

形态验证先于数值验证：导出四语言，确认函数体收缩、文件角色行出现且去重、调用行封顶、无文档目标出现命题句；词项全项目逐字节一致。数值验证走完整链路：数据重生五个项目，离线评测全部跑通。回归门槛为三项目无严重退化且词项行零变化；期望为 gap 查询翻转。若翻转幅度落入抖动带，如实记为未证实，不硬凑结论。

## 6. 执行记录与多 K 复核

本轮改动三处，均为向量路：函数体只保留控制流与行为事实片段并跳过间隙回填，无事实兜底整段函数体截断到头部约一百五十 token；调用表封顶八个目标、去自身引用噪音、去重；每块追加一行文件名自然词。词项文本全项目逐字节一致，词项行零翻转，BM25 行零翻转。

形态符合设计：函数体大幅收缩，文件角色行出现且去重，调用行封顶。

### 6.2 逐查询翻转（top10，emb 单块）

语义题：六胜四负。media_server 包序列化由零翻正、G2Q6 由一到二，但 G2Q20 由二归零；ripgrep G2Q2 由二到一、G2Q7 由一到零；once_cell G2Q2、G2Q9 各加一；flask G2Q9 由零到一。gin 语义题零翻转。

fuzzy 题：media_server 两题由零翻正，ripgrep 一正一负，once_cell 两题由正归零，gin 一题由正归零。总体打平。

跨语言题：once_cell G4Q2 由零到三、G4Q4 由零到一，疑为文件角色行生效。

分组口径：media_server 净增，gin 与 ripgrep 各一胜一负，once_cell 两胜五负（fuzzy 与两处语义分组退化），flask 零翻转。

### 6.3 块形状诊断

full_pipeline embedding 的 duplicate_text_share 大幅下降：gin 0.103→0.006（126→7），media_server 0.023→0.003，ripgrep 0.005→0.002，flask 0.031→0.012，once_cell 0.086→0.065。raw_source 口径基本不变，证实去重来自 NL 侧而非源码侧。间隙回填的移除消除了兄弟实体共享同一段函数体所产生的近重复块，这是本轮最确定的结构性收益。

### 6.4 结论与方向判断

方向正确，实现需调。块变短后长尾判别力上升、近重复块大幅消除，说明意图优先的版式方向成立。但无事实兜底的头部截断过于激进：它把部分查询真正需要的深部 token 一并切掉，造成 top5 与个别语义题回归，且这些回归无法用抖动解释（G2Q20 由二到零是确定性损失）。间隙回填移除与头部截断应解耦评估：去重收益来自前者，回归风险主要来自后者。

建议下一步：保留间隙回填移除，将无事实兜底的截断预算放宽或仅对确有兄弟稀释的组启用；文件角色行保留（跨语言题已见效）；调用行封顶保留但需固定向量复测。语义鸿沟未闭合的根因仍是同块兄弟稀释，应转向按实体切块与组头减肥，而非继续在函数体长度上做文章。
