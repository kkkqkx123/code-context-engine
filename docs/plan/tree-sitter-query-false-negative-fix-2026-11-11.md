# tree-sitter 查询漏抽修复：分析与修改方案

日期：2026-11-11。针对《tree-sitter 查询漏抽问题清单（2026-11-10）》逐项复核，
外加全语言横向复核中发现的新问题。所有结论均用真实语法树加当前查询实测验证，
验证手段为新增的 `debug_issue_queries` / `debug_sweep` / `debug_probe` 示例程序
（解析片段打印带字段名的 AST，并用生产 `QueryLoader` 执行查询统计命中），
未直接阅读语法 JSON。

## 一、问题清单逐项复核结论

### 1. Go 分组导入零命中：确认，属实且严重

实测单行 `import "fmt"` 命中一次，分组 `import (...)` 命中零次。
根因是依赖查询与实体查询都把导入规格锚定为导入声明的直接子节点，
而分组形态下规格挂在中间的规格列表节点之下，单行形态才没有中间节点。
分组导入是 Go 主流写法，绝大多数文件的包引用边整体丢失。

修复方向：保留原有直接子节点形态，增补经由规格列表节点的 twin 形态，
根捕获仍落在导入声明上；别名、点导入、空导入三种子形态同样增补。
实体查询的导入形态同步增补，否则分组文件的导入实体同样缺失。

### 2. C# 普通 using 零命中：确认，属实且严重

实测普通单命名空间与限定命名空间形态零命中，只有别名形态命中。
根因是依赖查询与实体查询要求 using 指令具备名称字段，
而只有别名形态的别名标识带有该字段，普通形态的子节点均无字段。
附带问题同样确认：别名形态的别名标识同时满足名称字段约束，
被同时捕获为命名空间名与限定名，别名与真实路径混在一起，下游产生重复边。

修复方向：普通形态改用无字段约束的子节点匹配，并用字段缺席断言排除别名形态，
使普通与别名形态互斥；别名形态保留名称字段约束并要求等号 token 存在，
别名捕获改用惰性后缀命名，使其不再参与目标选取，下游只取真实路径。
横向发现的 `using static` 与 `global using` 形态同样零命中，
根因相同（限定名子节点无字段），一并纳入修复，目标仍为完整限定路径。

### 3. C# this 前缀调用零命中：确认，属实且严重

实测 `this.H()` 零命中，`obj.M()` 命中两次（静态形态与方法形态各一次，
下游按调用点去重后合并为一条边，无实质重复）。`base.M()` 同样零命中。
根因是调用查询要求成员访问的宿主表达式为具名节点，而该语法中 `this`
与 `base` 为匿名 token，不满足通配约束。横向验证其余语言的等价形态
（Java、JavaScript、Python 的 self、PHP 的 `$this`、C++ 的 this、
Rust 的 self）全部正常命中，C# 是唯一受影响语言。

修复方向：在调用查询末尾增补不约束宿主的成员调用形态，只捕获函数名与参数。
该形态对普通调用也会额外命中，但下游已按调用者加尾段名加区间重叠去重，
且新增形态排在最后，平局时原有静态优先的胜出顺序不变，现有边无变化。

### 4. Rust 非路径别名与单标识导入漏抽：确认，属实

实测 `use foo as bar` 与 `use plain` 无任何别名或路径捕获，
`use a::{b, c as d}` 只有列表整体命中且该整体命中无可用目标而被丢弃，
`use x::y::z` 正常。根因是别名形态要求路径为限定路径节点，
而作用子句的路径可以是普通标识；单标识形态根本没有对应模式；
列表形态没有逐项模式。

修复方向：别名形态的路径位置放宽为任意具名节点；新增单标识形态；
列表形态增补逐项模式（普通项、自引用项、别名项分别处理），
逐项模式同时携带列表前缀与项捕获，下游组合出完整路径后再建边。
组合逻辑只针对新增的列表项捕获，其余形态的目标选取规则与顺序不变。
原仅捕获整体的列表形态模式因已无下游消费而删除。

### 5. 次要观察：逐项确认

- C# 多重命中：下游去重已覆盖，计数以合并后为准，不做查询层改动。
- Go 选择子双实体捕获：实体层已按同区间去重保留一个，文档注明即可。
- C# 类型体节点缺失：确认类、接口、结构体均有体字段而查询未捕获，
  记录类型为无体特殊形态。与 Java、C++ 对照，两者都捕获类体，
  C# 属于不一致，补齐体捕获（记录类型体可选），对签名合成只有正向作用。

## 二、横向复核发现的新问题

以下均为同一切片实测确认的零命中或错误命中，按严重度排序：

1. Ruby 全部 require 系依赖与实体零命中（严重）。根因是谓词捕获名与
   根捕获名重名：同一模式内方法标识与整个调用节点使用同一捕获名，
   而字符串相等谓词在该捕获绑定多个节点时无法成立。受影响模式共十三处，
   覆盖实体查询的 require、require_relative、include，
   与依赖查询的 require、require_relative、load、include、extend、
   prepend、autoload、gem。JavaScript 与 Lua 的实体 require 存在同一写法，
   同样零命中；两者的依赖查询因使用了互异的函数捕获名而正常。
   修复方向统一为将参与谓词的方法捕获改用惰性后缀命名，根捕获不变。
2. PHP 单行 `use Foo\Bar;` 零命中（严重）。根因是单行形态的子句为裸限定名，
   而查询只覆盖裸名单与别名、分组三种形态。修复为增补裸限定名单行形态，
   目标取完整限定路径；分组子句的别名项目前被混记为普通项，
   一并拆分为普通项与别名项两种形态（别名项用字段缺席断言互斥）。
3. C 系统头文件 `#include <stdio.h>` 零命中（严重），且引号形态被两个
   完全相同的模式重复命中。根因是两个模式都只写了字符串字面量节点，
   系统头文件的节点类型不同。修复为其中一个改用系统头文件节点，
   顺带消除引号形态的重复命中。
4. Python 裸 `from . import sibling`（含括号多名形态）零命中（中等）。
   根因是相对导入模式要求相对前缀内含模块名，而裸形态只有前缀点。
   修复为增补以前缀为末子节点的相对导入形态（用子节点位置锚点表达
   仅含前缀，保证与带模块形态互斥），目标取导入名。
5. Scala 花括号重命名项 `c => d` 漏抽（中等）。根因是只有裸标识项模式，
   重命名节点未覆盖。修复为增补箭头重命名项形态，目标取原名。
6. Kotlin 别名导入 `import a.b as c` 产生两条同区间边（轻微）。
   别名被记为独立目标，与 C# 别名混记同类。但该语法的别名标识
   与单标识导入的标识在父节点下均无字段区分，位置锚点又会把匿名
   关键字计入首尾判定，查询语言表达不了仅含单子节点的约束，
   故维持现状，记为已知限制。
7. Java 静态星号导入丢失星号（轻微）。目标记为去掉星号的路径，
   属可接受近似，仅文档注明，不改查询。

## 三、修改范围

查询方案文件：go、csharp、rust、ruby、lua、javascript（实体 require）、
c、php、python、scala 的对应查询函数。Kotlin 别名维持现状（见上）。
下游逻辑仅一处：依赖提取增加 Rust 列表项的前缀与项组合，
只在新增捕获出现时生效。公共规则、去重器、实体分类不做改动。

## 四、验证方案

1. 复跑两个调试示例，全部用例达到预期命中，确认既有正常用例命中数不变。
2. 方案文件内既有语法测试保持通过，并新增命中断言测试，
   覆盖每个修复形态与互斥边界（别名单普通、带模块单裸前缀、空重命名等）。
3. 在解析器集成测试中新增回归测试文件，用生产协调器解析片段，
   断言实体与原始关系边，覆盖本轮全部修复语言。
4. 在端到端套件中新增回归用例：每语言一个最小工程夹具，
   包含本轮修复的用法与边界形态，用编排器建索引后断言关系边
   （文件级依赖边与可消解的同文件调用边均内联断言，不另存快照）。
5. 全量编译检查与格式化按仓库门禁执行。

## 五、风险说明

- 新增形态只增加命中，不删除既有命中；互斥断言只缩小原重叠形态的
  命中集合，且重叠部分原本经去重合并，边集不变。
- Rust 列表项组合为新增分支，无新增捕获的语言路径不受影响。
- C# 体捕获只影响无签名子捕获的回退路径，现有合成签名不变。
