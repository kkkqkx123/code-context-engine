# 现状盘点与差距

## CCE 现有能力

服务端与调用面已经闭环。`cce-api` 持有路径模板、线上传输模型与错误码注解，是契约事实；
`cce-client` 把每个操作收敛为唯一一次调用，绑定路径、查询参数、请求体与响应类型，调用方不再手拼
地址或手写解码；OpenAPI 快照与前端 TypeScript 类型是同一份注解的两个投影，前端有契约校验脚本。
命令行、网关与外部消费方都已收敛到该调用面上。

前端是 SvelteKit 单页应用，静态适配器发布。路由覆盖项目、索引、搜索、实体、图谱、工具、存储、
健康、指标、监视、配置、日志、运维（死信与重试队列）与摘要等页面；请求层按资源分模块，状态层按
资源分存储，预览模式通过构建模式切换真实客户端与本地 fixture，不污染默认构建。

桌面侧现状是空白。仓内已有 `crates/gpui-kit` 子模块（组件库、托盘、图形等能力齐备），但根工作区
成员表未包含它，也没有任何桌面应用 crate 消费它。`cce-client` 的设计文档已预留未来 GPUI 客户端
的位置，但尚未落地。

## linkrs-gpui 对照

linkrs 的桌面端可作为结构模板，而非功能模板。值得借鉴的是分层形状：应用入口负责初始化顺序
（主题、全局状态、运行时、会话、快捷键、心跳、托盘、主窗口）；全局界面状态只镜像渲染所需的
连接状态、身份与角色快照；真实会话对象由独立的连接存储持有；在 GPUI 执行器与 tokio 之间用一次性
通道桥接，后台请求在 tokio 上跑，结果回到界面线程；主题切换走统一入口，先切换基座主题再重写品牌
覆盖，避免覆盖被基座重载丢弃；视图按业务面板拆分，主窗口用侧边导航加可停靠面板承载它们；通用
展示收敛为页面头、页面体、卡片、表格、空态、浮层等小构件；托盘负责窗口关闭常驻与恢复；设置落盘
窗口几何、主题、密度、语言与最近连接；界面文案集中在消息目录，源码不出现非英文用户文本。

不可照搬的是业务语义。linkrs 是数据库客户端，核心是会话、空间、语句执行、游标分页、模式管理、
迁移、同步、事务、用户等；CCE 是代码库索引与检索系统，核心是项目、索引任务、混合检索、实体与
调用关系、图谱邻域、诊断与折叠压缩工具、存储与监视。两者的面板清单与服务划分没有对应关系，只有
分层手法可以迁移。

认证模型差异最大。linkrs 需要主机端口加用户名口令登录、会话存活探测、空间切换与角色门控；
CCE 只有基地址加承载令牌（显式令牌优先于环境变量），无登录会话与空间概念。桌面端因此不需要会话
管理器、登录视图、角色能力门控与会话过期回退，连接层简化为客户端句柄持有加健康探测即可。

## 差距清单

- 缺少样式单一数据源。CCE 前端样式变量分散在 `frontend/src/app.css`，无机器可读的跨端目录，
  桌面端若手抄色值必然漂移。
- 缺少桌面应用 crate 与其独立工作区配置、构建说明与系统依赖说明。
- 缺少连接、设置、主题、国际化、托盘、运行时桥接等基础层。
- 缺少前端路由到桌面面板的映射与分批范围，前端十余个页面不可能一次搬完。
- 缺少桌面侧的守卫：设计 token 一致性检查、契约漂移检查在桌面侧的对应位置。
