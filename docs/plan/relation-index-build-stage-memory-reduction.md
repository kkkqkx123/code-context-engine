# 关系索引构建期全量分片重构设计

## 目标

本设计取代此前围绕完整构建图做内存清理的增量方案。全量索引构建不再构造、共享或深拷贝完整的 `RelationIndex` 和 `ProjectSymbolTable`，改为从解析结果直接流式写入规范快照工件；解析与派生阶段只通过有界的磁盘支持视图访问实体、符号和关系。

必须同时满足：

- 峰值 RSS 相对 1,173,636 KiB 基线下降 50% 以上，关系阶段增量低于 500 MiB。
- 50000 文件档不再出现数 GiB 的构建期峰值。
- 快照 fingerprint、规范行内容、关系计数、查询结果、delta 合并结果与当前实现完全一致。
- 查询期保留分片 LRU 和显式上限；超限报错，不静默丢边。
- medium 冷查询 p95 不高于当前 146/168 ms 的 2 倍，热查询低于 1 ms。

## 当前结构的根本问题

发布后的查询索引已经分片，但构建期仍保留完整关系图：

- `IndexBuilder` 持有 `RelationIndex`，并把完整实体表、名称表、文件表、符号键表、ID 重映射常驻到发布前。
- `SymbolTableBuilder` 为每个文件保留模块表、局部符号表、类型上下文和跨文件传播器缓存。
- 流式 artifact 只是把规范行提前写出，没有减少构建期状态；最后清理容器也不能回退已经达到的 RSS 峰值。

因此清理容器、投影实体字段、删除失效索引都属于局部修补，无法改变峰值随项目规模线性增长的事实。

## 总体架构

### 构建期存储

每次全量索引操作创建独立临时 SQLite 库，与现有 parsed-file spool 同目录，操作结束无条件删除。它只服务本次构建，不参与发布。

临时库包含：

- 实体表：全局 ID、文件、稳定符号键、稳定 ID、名称、类型、跨度、父子关系、最小元数据和本地 ID 重映射。
- 路由表：名称、文件、稳定键、调用者到实体 ID 的索引。
- 关系表：按源文件分组的调用边、引用边和文件级边。
- 符号表：模块导出/导入/重导出、局部作用域链、类型成员索引、跨文件返回类型/参数类型/字段类型缓存。

写入与读取都按文件分组。规范 artifact 继续由 `StreamingSnapshotArtifactBuilder` 输出，临时库不进入发布产物。

### 构建期查询视图

定义两个有界视图替代完整内存结构：

- `BuildEntityView`：提供按 ID、名称、文件、稳定键、本地重映射查询实体和调用者。
- `BuildSymbolView`：提供导出候选、导入/重导出、局部作用域、类型成员、跨文件类型和重载查询。

视图内部使用临时库查询，配当前文件工作集缓存和全局路由缓存，两者都有条目数与字节上限。超限返回显式错误。

`RelationResolver` 和插件关系注入改为面向这两个视图，不再直接依赖 `&RelationIndex` 与 `&ProjectSymbolTable`。增量更新和测试仍可使用内存实现，但通过同一查询契约接入，不保留重复路径。

### 构建流程

1. 注册阶段：逐文件解析结果写入实体路由表和规范实体/文件/依赖行；不向完整 `RelationIndex` 写入。
2. 符号阶段：逐文件写符号与类型上下文；跨文件传播器直接写临时库；不保留每文件模块表和局部表。
3. 解析阶段：逐文件从视图载入当前工作集，解析关系并直接写规范关系行；跨文件目标按名称/稳定键查询临时库。
4. 派生阶段：基于临时库中的关系表派生隐式层级边，直接写 artifact。
5. 完成阶段：结束 artifact，发布 store-backed snapshot；删除临时库。

全程不构造完整 `RelationIndex`，也不把构建结果转换为完整图。

### 发布、冷启动与热更新

发布输入只有 canonical artifact。运行时仍由 store + epoch 构造 `RelationSnapshotIndex`，目录只保留描述符和聚合计数，路由查询走有界缓存。

冷启动 delta 链继续按 epoch 逐段叠加，不加载基线全图。compaction 从 base + delta 生成规范 artifact，不经过 `from_index_shared`。导出增强只使用已发布快照。

## 一致性保障

- 稳定符号键、规范行顺序和 fingerprint 输入保持原样；视图返回的实体字段必须与旧内存实现完全一致。
- 用同一份 fixture 比较磁盘构建 artifact 与参考 artifact 的双指纹和四类行数。
- 比较关系计数、ego 查询结果、hot-update delta 合并结果。
- 临时库写入失败、视图缓存超限、文件计数不一致均使 operation manifest 失败，不激活 generation。

## 风险与控制

- 随机查询代价：按文件预载工作集，索引覆盖所有路由列，复用 prepared statement。
- 缓存抖动：当前文件优先，跨文件只取命中实体；命中率和查询次数进入容量报表。
- 磁盘占用：临时库只存键和最小载荷，不存源码与 NL 文本；操作结束清理。
- 构建耗时：若 medium 关系阶段耗时超过当前 2 倍，先优化批量读取顺序和索引，不放宽内存上限。

## 验证

1. 回退所有增量式内存修补，恢复到全链路分片重构完成点。
2. 完成构建期存储与视图重构后，跑完整 workspace fmt/clippy/lib test 和 CLI/server 构建。
3. 在 devs 上用阶段 RSS 采样跑 medium/large `full_pipeline_perf`。
4. 跑 `relation_query_matrix` medium 确认冷/热 p95 与错误数。
5. 核对规范指纹、关系计数、delta 合并和导出结果。

只有峰值下降 50%、关系阶段增量硬上界、查询延迟和一致性全部通过，才认为本重构完成。

## 落地状态（devs 复测后）

已落地 `BuildEntityView`、`BuildIndexSink` 与临时 SQLite 关系构建库；实体、符号键、ID 重映射、文件、导入导出、依赖、关系边均不再以完整 `RelationIndex` 常驻。canonical artifact 由临时库按行写出，发布路径保持 store-backed snapshot。单测验证了磁盘 artifact 与参考 canonical artifact 的双 fingerprint 和行计数一致。

实测 medium 峰值下降 33.2%，large 下降 39.6%；medium 关系阶段增量 404,668 KiB，低于 500 MiB。large 关系阶段增量 4,090,268 KiB，峰值下降也未达到 50%。阶段 RSS 表明剩余增量集中在符号表构建：medium 符号阶段增加约 356 MiB，large 增加约 3.6 GiB。查询矩阵 cold p95 47 ms、warm p95 0 ms，未回归。

因此本轮只完成了关系构建存储的替换。`BuildSymbolView`、符号/类型上下文磁盘化与符号表工作集上限尚未实现，不能宣布全部验收项通过。下一步必须在符号表构建路径中落实同一临时库契约，再按相同口径复测 medium/large。

## 符号表磁盘化细化设计

### 边界与目标

关系边已经由构建期 SQLite 承载；剩余的线性增长来自 `ProjectSymbolTable` 为每个文件保留的 `LocalSymbolTable`。本轮只把文件级局部符号表移到同一临时库，不改写查询期快照，也不改变解析算法。

硬约束：

- 物化的局部表工作集最多 128 个文件、约 96 MiB；按 LRU 淘汰。
- 写入失败必须使构建失败，不能静默生成缺失符号的关系图。
- 同一文件的局部表在注册、跨文件传播、关系解析三次回放中必须解析为同一份数据。
- 增量构建的既有内存路径保持不变，不引入第二套解析逻辑。

### 存储结构

临时 SQLite 增加 `local_symbols(path, record_json)` 表。`record_json` 保存完整的局部表记录：文件路径、语言、实体集合、实体 ID 顺序、名称索引、按父作用域分组的索引、元数据缓存、最大作用域深度。共享的 `Arc` 实体容器在序列化时展开为值，反序列化后重新建立共享容器，保证 `resolve_by_scope` 与 `build_scope_chain_with_limit` 的输入完全一致。

`LocalSymbolStore` 与关系构建库共用同一个数据库文件，但持有独立连接，避免把局部表数据混入 artifact 写出路径。读取命中 LRU 时直接返回 `Arc<LocalSymbolTable>`；未命中时按 path 查询一行、反序列化、加入工作集。工作集按估算字节数淘汰，单条过大时仍可加载但不驻留，避免因为一个异常文件污染缓存。

### 模块表接入

`ModuleSymbolTable` 的局部表来源改为两种确定性状态：内存表，或指向磁盘库的文件路径加共享句柄。两种状态都通过同一个 `get_local_table()` 暴露为 `Arc<LocalSymbolTable>`，因此 `resolve_local_scope` 与 `get_scope_chain` 不需要分支逻辑，也不需要动态分发。

`SymbolBuildSession::add_file` 注册每个文件时先把局部表写入磁盘库，再把模块表指向该磁盘记录；非全量构建仍走内存表。写入错误通过 `Result` 冒泡到 finalize，转换为显式的 operation manifest 失败。

### 构建顺序

1. finalize 创建关系构建库，并取得局部表存储句柄。
2. 符号注册回放逐文件写局部表；全局导出、类型索引、简单名称索引继续在内存中聚合，但这些结构只保存小而固定的路由信息。
3. 跨文件传播与关系解析再次读取同一路径时，从有界工作集或磁盘恢复局部表，用完即由 LRU 淘汰。
4. artifact 写出仍只访问关系构建库的关系与实体表，不读取局部表。
5. spool 与临时库同时删除，磁盘数据不跨越操作边界。

### 一致性验证

- 单测覆盖局部表序列化往返后的实体数量、实体内容和作用域链。
- 已有 fingerprint 单测继续覆盖磁盘关系 artifact 与参考 canonical artifact 的双指纹和行计数。
- 复测时对比 medium/large 的关系计数、fingerprint 与查询结果；若出现偏差，优先检查 `local_symbols` 的 path 归一化与记录字段完整性。

### 已知边界

本轮磁盘化只覆盖文件级局部符号表。`PackageSymbolTable` 的导出/导入/重导出表与全局名称、类型索引仍常驻内存，这部分不随文件数线性增长到实体级别，但仍是后续可观察的占用来源。若阶段 RSS 仍不满足 500 MiB 硬上界，下一步应把模块表整体纳入同一临时库，而不是放宽工作集上限。

## 最终复测结论

局部符号表磁盘化上线后，medium 峰值下降 40.8%、关系阶段增量 324,500 KiB，达到 500 MiB 上界；large 峰值下降 49.1%，距离 50% 目标差约 1.7%，关系阶段增量 3,244,720 KiB，仍未达标。构建耗时未回归，查询 cold p95 51 ms、warm p95 0 ms。

剩余占用已定位到 `PackageSymbolTable` 的模块导出/导入/重导出表和全局名称/类型索引。要达到 500 MiB 硬上界，必须把这些结构也迁到构建期临时库，并让解析器通过有界 `BuildSymbolView` 逐文件加载，而不是继续放大工作集上限。本轮不声明全部验收通过。
