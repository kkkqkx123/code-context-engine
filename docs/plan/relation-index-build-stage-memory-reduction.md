# 关系索引构建期全量分片重构设计

## 目标

本设计取代此前围绕完整构建图做内存清理的增量方案。全量索引构建不再构造、共享或深拷贝完整的 `RelationIndex` 和 `ProjectSymbolTable`，改为从解析结果直接流式写入规范快照工件；解析与派生阶段只通过有界的磁盘支持视图访问实体、符号和关系。

必须同时满足：

- 峰值 RSS 相对 1,173,636 KiB 基线下降 50% 以上，关系阶段增量低于 500 MiB。
- 50000 文件档不再出现数 GiB 的构建期峰值。
- 快照 fingerprint、规范行内容、关系计数、查询结果、delta 合并结果与当前实现完全一致。
- 查询期保留分片 LRU 和显式上限；超限报错，不静默丢边。
- medium 冷查询 p95 不高于当前 146/168 ms 的 2 倍，热查询低于 1 ms。

## 当前结构的根本问题

发布后的查询索引已经分片，但构建期仍保留完整关系图：

- `IndexBuilder` 持有 `RelationIndex`，并把完整实体表、名称表、文件表、符号键表、ID 重映射常驻到发布前。
- `SymbolTableBuilder` 为每个文件保留模块表、局部符号表、类型上下文和跨文件传播器缓存。
- 流式 artifact 只是把规范行提前写出，没有减少构建期状态；最后清理容器也不能回退已经达到的 RSS 峰值。

因此清理容器、投影实体字段、删除失效索引都属于局部修补，无法改变峰值随项目规模线性增长的事实。

## 总体架构

### 构建期存储

每次全量索引操作创建独立临时 SQLite 库，与现有 parsed-file spool 同目录，操作结束无条件删除。它只服务本次构建，不参与发布。

临时库包含：

- 实体表：全局 ID、文件、稳定符号键、稳定 ID、名称、类型、跨度、父子关系、最小元数据和本地 ID 重映射。
- 路由表：名称、文件、稳定键、调用者到实体 ID 的索引。
- 关系表：按源文件分组的调用边、引用边和文件级边。
- 符号表：模块导出/导入/重导出、局部作用域链、类型成员索引、跨文件返回类型/参数类型/字段类型缓存。

写入与读取都按文件分组。规范 artifact 继续由 `StreamingSnapshotArtifactBuilder` 输出，临时库不进入发布产物。

### 构建期查询视图

定义两个有界视图替代完整内存结构：

- `BuildEntityView`：提供按 ID、名称、文件、稳定键、本地重映射查询实体和调用者。
- `BuildSymbolView`：提供导出候选、导入/重导出、局部作用域、类型成员、跨文件类型和重载查询。

视图内部使用临时库查询，配当前文件工作集缓存和全局路由缓存，两者都有条目数与字节上限。超限返回显式错误。

`RelationResolver` 和插件关系注入改为面向这两个视图，不再直接依赖 `&RelationIndex` 与 `&ProjectSymbolTable`。增量更新和测试仍可使用内存实现，但通过同一查询契约接入，不保留重复路径。

### 构建流程

1. 注册阶段：逐文件解析结果写入实体路由表和规范实体/文件/依赖行；不向完整 `RelationIndex` 写入。
2. 符号阶段：逐文件写符号与类型上下文；跨文件传播器直接写临时库；不保留每文件模块表和局部表。
3. 解析阶段：逐文件从视图载入当前工作集，解析关系并直接写规范关系行；跨文件目标按名称/稳定键查询临时库。
4. 派生阶段：基于临时库中的关系表派生隐式层级边，直接写 artifact。
5. 完成阶段：结束 artifact，发布 store-backed snapshot；删除临时库。

全程不构造完整 `RelationIndex`，也不把构建结果转换为完整图。

### 发布、冷启动与热更新

发布输入只有 canonical artifact。运行时仍由 store + epoch 构造 `RelationSnapshotIndex`，目录只保留描述符和聚合计数，路由查询走有界缓存。

冷启动 delta 链继续按 epoch 逐段叠加，不加载基线全图。compaction 从 base + delta 生成规范 artifact，不经过 `from_index_shared`。导出增强只使用已发布快照。

## 一致性保障

- 稳定符号键、规范行顺序和 fingerprint 输入保持原样；视图返回的实体字段必须与旧内存实现完全一致。
- 用同一份 fixture 比较磁盘构建 artifact 与参考 artifact 的双指纹和四类行数。
- 比较关系计数、ego 查询结果、hot-update delta 合并结果。
- 临时库写入失败、视图缓存超限、文件计数不一致均使 operation manifest 失败，不激活 generation。

## 风险与控制

- 随机查询代价：按文件预载工作集，索引覆盖所有路由列，复用 prepared statement。
- 缓存抖动：当前文件优先，跨文件只取命中实体；命中率和查询次数进入容量报表。
- 磁盘占用：临时库只存键和最小载荷，不存源码与 NL 文本；操作结束清理。
- 构建耗时：若 medium 关系阶段耗时超过当前 2 倍，先优化批量读取顺序和索引，不放宽内存上限。

## 验证

1. 回退所有增量式内存修补，恢复到全链路分片重构完成点。
2. 完成构建期存储与视图重构后，跑完整 workspace fmt/clippy/lib test 和 CLI/server 构建。
3. 在 devs 上用阶段 RSS 采样跑 medium/large `full_pipeline_perf`。
4. 跑 `relation_query_matrix` medium 确认冷/热 p95 与错误数。
5. 核对规范指纹、关系计数、delta 合并和导出结果。

只有峰值下降 50%、关系阶段增量硬上界、查询延迟和一致性全部通过，才认为本重构完成。
