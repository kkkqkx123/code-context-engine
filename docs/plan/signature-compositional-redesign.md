# 组合式签名重设计：分析与修改方案

本文是对已实现方案 `signature-extraction-fix-plan.md`（体切片加头清洗加 500 上限）的复盘分析与替代方案。前半部分逐条给出当前三个字符操作机制的具体反例，后半部分给出只用 tree-sitter 结构信息求解的修改方案。只写改什么、为什么、按什么顺序，不贴完整代码。

## 1. 现状问题分析

核心论点：签名边界是语法概念，字符操作处理的是文本。用文本启发式逼近语法边界，每种语言的字面量、注释、默认值写法都是新的反例来源，补丁永远收敛不了。下面每个机制各举至少一个必然触发的反例。

### 1.1 头清洗按行猜装饰器与注释，必然漏也必然误伤

现行清洗按行首前缀丢弃 `@`、`//`、`/*`、`*`、`<!--` 开头的行，存在四个确定性缺陷：

- 多行装饰器漏片段。装饰器带跨行参数时只有首行以 `@` 开头，后续行残留进签名。装饰器在各文法中是独立节点（装饰定义包裹结构），本可构造性排除，却用行前缀猜。
- `#` 注释行未处理。Python 多行定义头里的行内注释直接进入签名；且该缺口补不上——`#` 同样出现在字符串字面量里，行前缀判断在语法上分不清注释与代码，加一条前缀规则就会引入新的误伤。
- 全文空白归一篡改字符串语义。归一函数按全空白切分重拼，会把默认值里的连续空格压扁，签名中出现源码里不存在的代码。这不是边角情形，而是作用于每个含字符串默认值签名的系统性篡改。
- `<!--` 这类 HTML 方言出现在通用解析器里，本身就是启发式走到底的证据：每支持一种语言加一个前缀特例，永远补不完。

### 1.2 500 字符静默截断把正确性缺陷藏起来了

- 截断点落在词法单元中间，产物既不是合法头也不是可解析文本，下游无法区分"合法长签名"与"泄漏的函数体"，两种情形得到同一种处理。
- 更严重的是掩盖真实缺陷：Python 查询中有三个方法变体模式未声明任何体捕获，这些方法走退化路径拿到全文后再被上限削成断头签名，表现为"有点怪但能用"的数据。若没有上限，它们会以超长签名形式暴露，逼修复指向查询缺捕获。etch 上限掐死了这个失败信号。
- "定义头天生很短"的前提不成立，机器生成代码与长参数列表的合法签名超过上限并不罕见。

### 1.3 首个花括号截断是最简反例

退化路径在文本中找第一个 `{` 处切断。含字典默认值的 Python 参数在参数区内就出现花括号，签名被拦腰切断。任何"找第一个某字符"的逻辑都隐含"该字符只出现在目标位置"的假设，该假设对几乎所有字符都不成立。

### 1.4 体切片本身的残留问题

体切片比字符查找高一级（用的是捕获区间而非字符扫描），但仍是"区间猜测"而非"结构组合"：完全依赖各查询声明体捕获，缺体声明的模式退化为全文；且切片后仍需清洗，逃不掉 1.1 的全部问题。

## 2. 结构求解的证据：信息早已在查询里

Python 查询早已为函数与方法捕获名称、参数、返回类型、体四个独立部分，Rust 查询更进一步使用签名前缀命名。现状的症结只是命名约定：重组器只识别名字含签名中缀的捕获，Python 的参数与返回类型捕获因此被无视。信息是现成的，被挡在门外的是识别规则。tree-sitter 查询允许单个节点挂多个捕获，补别名零解析成本。

## 3. 修改方案：组合式签名

总原则：签名等于按源码序拼接已命名的结构部分；装饰器、注释、文档串构造性排除（不捕获即不进入）；文本操作只做部分之间分隔空白的归一化，永不触碰部分内部文本；删除静默截断，用可观测的抽取失败信号代替。

### A. 泛化签名部分的识别（对应 1.1、2）

- 在各语言查询中为已有结构节点叠加签名别名捕获（参数节点同时挂参数捕获与签名参数捕获，依此类推至名称、返回类型、类型参数、基类、修饰符）。推荐显式叠加而非放宽通用命名匹配：显式可逐语言审计验收，不会误收参数子结构等非签名捕获。
- Rust 现有签名前缀捕获保持不动，作为回归锚点。

### B. 组合规则取代清洗（对应 1.1、1.3）

- 签名按各部分起始字节排序后拼接，分隔处用单空格连接，各部分内部文本原样保留。多行装饰器、注释、文档串因从未被捕获而自然缺席，删除全部行前缀过滤逻辑。
- 修饰符按各文法字段显式捕获（异步、可见性、静态等），缺失则签名中不出现，不做文本前缀幸存假设。
- 删除花括号查找的退化函数。

### C. 回退语义与上限的替代（对应 1.2）

- 删除长度上限常量、截断函数与全文回退：无签名部分可组合时返回空并计数抽取缺失指标，把"缺失"变回可观测信号，而非削足适履的断头文本。
- 本就没有体的实体（模块、导入、宏定义等）签名即全文的现有行为保留，该情形下全文就是合法头，不经过任何截断。

### D. 查询侧补齐（对应 1.2、1.4）

- 补 Python 三个无体方法变体模式的体捕获与签名别名，这是当前唯一已知的查询缺口。
- 审计其余语言有体而无体捕获的模式；无体实体不在审计范围内。
- 体捕获起点继续作为辅助边界，仅用于"有体但查询尚未补签名别名"的过渡期模式，且同样不经过清洗与截断。

### E. 测试转向强断言（对应全部）

- 以真实解析端到端精确相等断言为主：各语言夹具的类与函数签名断言完整期望串，不再使用"不含某子串"类弱断言。
- 必备新增情形：含装饰器定义、多行参数头、字符串默认值连续空格原样保留、缺捕获返回空。
- 删除或改写依赖截断行为的旧单测；过渡期体边界行为单测保留至查询补齐完成。

### F. 输出重建与验收

- 污染的是落盘数据，修复后全量重建索引与复核导出物；开发期不做旧签名迁移与兼容。
- 验收：关系图快照签名长度分布不再出现千字符级函数或类签名；三个方法变体签名形态正确；Rust 图快照输出不变；抽取缺失指标为零或仅含已知无体实体之外的可解释项。

## 4. 与旧方案的关系

旧方案作为止血有效（体泄漏量级已收敛），但本分析证明其三个机制均存在确定性反例，不可作为终态。新方案删除旧方案引入的清洗函数、截断函数、上限常量与花括号退化路径，保留并推广其两级优先级骨架（结构重组优先）与体捕获复用思路。
