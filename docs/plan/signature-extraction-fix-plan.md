# 符号签名臃肿修复方案

> 已被 `signature-compositional-redesign.md` 取代：该方案的清洗、截断、花括号退化三个机制均存在确定性反例，终态改为组合式签名。本文仅保留为止血过程记录。

本文是对 `docs/issue/signature-bloat-review-2026-10-10.md` 全部 10 项的根因确认与修改计划。根因已定位到具体文件与行为，本方案只写改什么、为什么、按什么顺序，不贴完整代码。

## 1. 根因确认结论

签名生产链路只有三站：查询方案声明签名子捕获、捕获解析组装签名、下游原样透传。断点在第二站的回退分支。

- 全仓仅 Rust 查询方案声明了签名子捕获并走重组分支，其余 20 余个语言方案均无，全部落入回退分支。
- 回退分支的修剪函数只认识 `{`：有则截断取头，无则原样返回全文。Python（冒号加缩进块）、Lua 与 Ruby（`end` 块）等语言因此把定义头、文档串、完整函数体或类体一并装入签名字段。
- 装配点、图服务、结构化报告三处均为原样透传，无长度上限、无归一化，污染直达落库、图接口与复核产物。
- brace 语言当前输出干净只是分隔符巧合，不是处理正确。

否决“为每个语言补签名子捕获”的备选方案（即既有 `multi-language-signature-capture-design.md` 的八周计划）：改动面覆盖 20 余个查询文件与各语言文法细节，风险与验证成本过高，且不能给回退分支补上不变式。反之，各语言查询早已声明体捕获（函数体、类体、块），其字节区间天然标出体的起点，回退分支利用该信息即可对全语言一次修复，改动收敛在单个模块内。

## 2. 修改项（按依赖顺序）

### A. 回退分支改用体捕获定界（对应问题 1、2、3、5，最高优）

位置：捕获解析的签名节（`crates/parser/cce-parser/src/parser/extractor/capture/parser.rs` 的签名提取入口与修剪函数）。

- 保持两级优先级不变：签名子捕获重组仍为第一级，回退仍为第二级。
- 第二级不再以全文与 `{` 为输入：先取主捕获区间，再在同一匹配内寻找落在其区间内的体捕获（名称以体后缀结尾），取其中最早且严格大于主起始的体起点为头结束位；无符合体捕获时沿用主结束位。
- 头文本从源码按上述区间切片，而非从主捕获的缓存文本截取，保证体起点精确到字节。
- 对 brace 语言该行为与现有 `{` 截断等价（体起点即 `{` 处），属兼容收敛；对冒号与 `end` 风格语言则是从无处理变为正确取头。

### B. 头清洗：剥装饰器与注释行并归一为单行（对应问题 3、4、6）

位置：同模块的修剪函数，改为纯清洗函数。

- 按行切分后丢弃空行、装饰器行（行首为 `@`）与常见注释行（行首为 `//`、`/*`、`*`、`<!--`），保留预处理行（行首为 `#` 的行一律保留，避免误伤 C 系预处理指令）。
- 剩余行以单空格拼接并做空白归一，全签名为单行形态，与 Rust 重组分支的输出形态一致。
- 装饰定义的主捕获若从装饰器起始，清洗后签名不再含装饰器；文档串因位于体内自然被排除，与文档串独立通道不再重复。

### C. 签名长度上限（对应问题 7、9）

位置：同模块，新增常量并在两级分支出口统一收敛。

- 设定数百字符级的上限（以覆盖最长的合法多参函数头并截断一切体泄漏为准），按字符边界截断。
- 第一级重组输出同样经过归一与上限收敛，作为纵深防御；Rust 现有输出远短于上限，行为不变。
- 人名已有长度截断先例，签名补齐同类约束，下游的对齐键哈希、关键词提取、图负载不再接触多 KB 文本。

### D. 单测补齐（对应问题 10）

位置：同模块的测试节，不动其他语言的查询单测。

- 冒号块语言形态：多行参数函数取头到冒号结束，不含文档串与实现；类取头到冒号结束，不含方法体。
- 装饰器形态：含装饰器的匹配清洗后仅剩定义头。
- brace 形态：现有 `{` 截断行为保持，输出与改前一致。
- 无体形态：无体捕获时返回清洗后的全文（如模块与导入）。
- 上限形态：超长头被截断到上限以内。
- 子捕获形态：重组分支输出同样满足单行与上限。

### E. 输出重建与验收

- 本缺陷污染的是落盘数据，修复后需全量重建索引与复核导出物；项目处于开发期，不做旧签名迁移与兼容。
- 验收以输出复核方法为准：关系图快照按签名长度排序不再出现千字符级函数或类签名；结构化报告类表签名列不再命中体标记；Rust 图快照输出不变。

## 3. 验证计划（合并为两轮）

第一轮：`cargo clippy` 与 `cargo fmt` 检查通过后，运行签名所在模块的 targeted 单测（含新增用例）与实体提取相关单测。第二轮：抽查 Python 与 Rust 的解析产物签名形态是否符合预期（函数到头、类到头、无体标记）。每轮失败即停，不进入下一轮。不运行全量测试与全量基准，避免不必要的编译开销。
