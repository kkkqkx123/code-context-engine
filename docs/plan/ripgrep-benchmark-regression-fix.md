# Ripgrep 基准检索退化修复方案

## 背景

 ripgrep 基准对比显示语义查询召回大幅下降，且伴随 chunk 数量膨胀。`full_pipeline` 的 embedding 与 BM25 在 top-5 与 top-50 上同步下滑，说明不仅是排序窗口挤占，而是语义信号本身减弱。`direct_chunking` 的 BM25 路径膨胀最为明显。chunk 形态诊断未发现区间重复爆炸，问题集中在粒度过细与预算计量。

证据来自历史基线与当前输出的 chunk 数对比、按查询类型聚合指标、top-50 验证、chunk 形状诊断以及场景 chunk 文本转储。

## 目标

恢复语义查询的召回能力，同时将 chunk 数量回落到历史基线量级。精确评测与生产对齐的分组评测需要同步改善，避免以牺牲一方为代价提升另一方。修复后通过场景导出与基准输出确认效果。

## 原因分析

第一，BM25 预算计量单位发生变化。历史基线按空白词计数，当前按索引分词器产出的词条总数计数。分词器会对标识符做切分并保留原词与切分词，同一源码词会产生多个词条。源码密集的仓库因此被高估数倍，同样长度限制下切分更激进。自然语言文本受影响较小，源码路径受影响最大。

第二，分块主体可用预算收缩。术语预留与装饰文本在分块前扣除，正文可用上限低于历史硬限制。同样内容需要更多块才能容纳。

第三，BM25 分割路径变细。历史 BM25 对超限声明按行边界细分，当前统一走句子边界。句子边界包含换行与句点，方法级自然语言描述容易被拆成句子碎片，声明完整性受损。

第四，单实体小幅超限不再整体保留。历史对单个实体适度超限允许整体保留，当前超限即拆分。略超上限的方法被拆成大块加小尾，碎片数量增加。

第五，合并仍以补齐小块为主。同一实体的碎片可以向剂量上限打包，但不同实体之间只在某侧过小时合并。同一分组内多个方法各自成块，top-k 窗口容易被同一目标的多块占据。

## 修改思路

预算侧将 BM25 消耗改为按位置计数。同一源码词的原词与切分词共享位置，只计一次。英文场景下位置数接近历史空白词数，中文场景下仍保留词典分词粒度。分词用于检索不变，仅预算口径回归合理水平。

分割侧恢复 BM25 的粗粒度路径。实体超限时 BM25 按段落边界细分，不经过句子层。自然语言短描述不再因句点被拆散，声明保持完整。嵌入路径保持现有句子细分不变。

分割侧恢复单实体小幅超限整体保留。单个实体超限幅度有限时不再强制拆分，避免大块加小尾。只有大幅超限才继续细分。

合并侧保持现有同单元打包语义不变。本次不扩大跨实体合并，避免引入身份混淆。数量回归主要依靠预算与分割修复实现。

## 验证方法

先运行单元测试确认分块不变量成立，包含分区完整覆盖、单块上限、合并后不超上限。

再运行场景导出重新生成 ripgrep 分块输出，检查总块数、平均块大小、句子边界碎片占比是否回落，同一方法的碎片数是否减少。

最后重新生成基准输出，对比历史基线的 chunk 数与语义查询召回。重点观察 top-5 与 top-50 的语义类别，以及分组视图与精确视图的差距是否收敛。

## 风险与边界

预算口径调整会影响所有语言与仓库，不仅限于 ripgrep。需要确认中文分词场景不受损。

行级与段落级边界的选择是启发式，无法保证所有超限实体都有理想切分点。最终仍由硬切分保证上限。

本次不改动评测定义与去重语义，不新增方法级聚合块，不改动跨组合并策略。数量回归后若仍有语义缺口，再单独处理摘要文本质量。
