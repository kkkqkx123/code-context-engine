# P1 收尾清理与补充验证实施方案

本文为删除、增量、快照三条线闭环后的收尾工作方案，覆盖一个正确性缺口、两个性能/死代码项、任务三的取证埋点，以及文档同步。目标是在原模块内修复，不新增替代模块，不做兼容层，不保留旧路径。修复顺序遵循正确性优先于可靠性、可靠性优先于可误用性的原则。

所有改动仅在既有 crate 与文件内完成。涉及删除语义的改动以删除面自归一化为原则，即每个存储后端在自身边界完成路径归一化，与读取路径及其余后端保持一致。涉及跨 crate 的删除面，保证一批改动合并到尽量少的编译检查内完成验证。

## 任务 A：远端向量删除路径归一化

问题根因是 qdrant 删除面使用原始文件路径，而同仓读取已做归一化，其余后端删除亦各自在边界归一化，导致删除与读取在同一 crate 内不一致；在 qdrant 部署下，未归一化路径将零命中删除。

修改范围为 qdrant 操作层的四个删除面：单文件删除、单文件按轮次删除、按路径集批量删除、按路径集按轮次批量删除。改法为在每个删除边界对文件路径调用共享归一化函数，与本地后端写法对齐；批量删除在构建命中子句前逐路径归一化。这样编排侧批量删除与 HTTP 单文件删除两类调用方统一被覆盖，且无需改动任何调用点。

验证为在 qdrant 的测试替身中补充断言：以未归一化输入删除，与归一化形式删除命中同一批点。

## 任务三：暂存提交入口取证埋点

入口当前无条件触发全量重建，且全仓没有任何针对该入口的频率、成本、变更集规模埋点，导致"小且频繁"这一判定无法取证。本阶段只补埋点，不改路由；路由改造列为证据触发的后续阶段。

取证指标分两层。第一层为频率与成本，在提交处理入口增加一个作用域限定该路由的计数器与时长直方图，记录全量索引返回的文件数与墙钟耗时。第二层为变更集规模，这是决策关键数据：在提交处理入口调用全量之前，构造一个一次性的变更检测器运行只读的变更检测，将新增、修改、删除三类之和与未变更、总量之比记录为指标与日志。

变更检测为只读操作，落库哈希为一次批量查询，增量扫描有尺寸与修改时间指纹复用，成本远低于一次全量；使用一次性检测器避免扰动常驻检测器的扫描复用状态。全量路径在清单激活时才发布哈希，期间文件行哈希为空，故切换后的首次影子测量会把所有文件视为新增，这是一次性引导成本，不影响取证结论。

路由改造阶段在证据显示入口为高频率、小变更比时启动，方向为把该入口从全量索引改路由到已有的热更新协调器的检测到应用路径；次选为让全量批处理承认未变更文件。两个方向都不触碰关系终结阶段。

## 任务 B：本地向量原生批量删除

本地后端只实现了单文件删除，按路径集批量删除落到合约的顺序循环默认实现，导致本地候选批量删除退化为逐路径的线程切换与引擎扫描；远端已有原生批量。

修改范围为本地存储层覆写按路径集删除与按路径集按轮次删除两个方法，用单一过滤器表达组内且路径命中任一归一化路径，可选叠加类型与轮次约束，一次过滤器删除与一次线程池切换完成。空输入早返回零，与远端一致。结果须与逐路径顺序删除等价，满足合约契约。

验证为本地单测断言多个路径批量删除与逐路径顺序删除命中集与计数一致，覆盖空输入与路径重叠。

## 任务 C：死代码清理

分直接删除与决策两类。直接删除项为全仓零调用：跨四个 crate 的分块按文件删除通道（trait、SQLite 实现、PostgreSQL 实现与转发、编排分发共六处），分层快照的文件作用域视图及其类型与再导出，快照的受差异影响文件集合，热更新关系侧的增量符号指纹函数，以及一个仅含文档注释的空测试模块与其模块声明。这几项删除后，分块数据已由文件级联覆盖，文件作用域与差异影响集合已无任何消费方。

决策类为生产零调用但被测试或基准引用。深拷贝快照构造器被快照成本基准用作深拷贝与共享的对比基线，删之即删掉已消除深拷贝的性能证据，予以保留，仅保证其注释与现状一致。全文客户端的自持索引模式字段与访问器在生产已全部改读管理器模式，仅剩端到端测试引用，建议删除字段与访问器并同步调整测试调用点。构建器的清空方法与关系索引的清空方法在每轮新建、发布即退役的模型下生产零调用，建议删除两方法及其测试；相应地新补的名称倒排清空一并移除，不再为旧复用模型补漏。

清理按 crate 分批合并编译：存储侧一批，codegraph 与编排侧一批，各一次全目标裁剪检查。

## 任务 D：文档同步

将滞后于代码的表述修订对齐。写关系优化文档中"持有发布时的深拷贝产物"改为"持有发布时的共享产物"，相关闭环与遗留项表述改为已落地共享发布。共享所有权设计文档标注任务二已实现。关系终结线性分析文档标注任务一与任务二已完成，任务三按两阶段取证补充。删除增量快照设计文档的后续任务清单标注已完成项。

## 执行顺序

一、任务 A 正确性：qdrant 删除归一化及对应测试。二、任务三第一阶段取证埋点，不改路由。三、任务 C 死代码清理，先删零调用项，再处理决策项并同步测试，合并两次编译。四、任务 B 本地矢量批量删除及单测。五、任务 D 文档同步收尾。任务三第二阶段路由改造列为条件触发，待取证数据支撑后单独立项。

## 实施记录（已完成）

以下为各项任务的落地结果与验证状态。代码全部在既有模块内完成，未新增替代模块，未保留旧路径。新增测试均通过；各受影响 crate 组合的裁剪检查通过。

### 任务 A：qdrant 删除路径归一化（已完成）

- `crate-storage-vector-qdrant/src/operations.rs` 四个删除面（单文件、单文件按轮次、按路径集、按路径集按轮次）在构建过滤键前对路径调用 `cce_types::normalize_project_path`，与该仓读取及其余三家后端对齐。
- 新增两个替身断言测试：单删与批删的过滤器键均为归一化路径而非原始输入。通过。

### 任务 B：本地矢量原生批量删除（已完成）

- `crate-storage-vector-local/src/store.rs` 覆写按路径集与按路径集按轮次两个删除方法，用 `FilterCondition::match_any` 表达单一过滤（组内且命中任一归一化路径），一次 `delete_by_filter` 加一次线程池切换完成；空输入早返回零。
- 新增 `normalized_path_values` 辅助函数构建归一化路径的负载值。
- 新增两个等价性单测：批量删除与逐路径顺序删除命中集、计数一致；按轮次批量只作用于目标轮次。通过。

### 任务 C：死代码清理（已完成）

直接删除项：
- `chunks_delete_by_file`：trait、SQLite 实现、PostgreSQL 固有实现与转发、编排分发共五处一并移除；底层 `ChunkRepository::delete_by_file_path` 仍被单文件删除编排使用，予以保留。
- `LayeredSnapshotIndex::file_scoped` 与 `FileScopedSnapshot` 类型及其再导出。
- `LayeredSnapshotIndex::files_affected_by_deltas`。
- 热更新关系侧 `incremental_symbol_fingerprint`（原带冗余的空实现）。
- 仅含文档注释的空 `relation/tests.rs` 及其模块声明。

决策项：
- `RelationSnapshotIndex::from_index` 深拷贝构造器：保留，作为快照成本基准中"深拷贝对共享"的度量基线；其生产侧已零调用，深拷贝已由共享发布消除。
- `Bm25Client::schema` 字段与 `schema()` 访问器：删除。生产早已改读 `manager_guard.schema()`，该字段仅持一个与真实索引不符的默认模式。三处端到端测试改为从已持有的管理器守卫取模式。
- `IndexBuilder::clear` 与 `RelationIndex::clear`：删除。每轮新建构建器、发布即退役后生产零调用；随附的 `name_index` 清空补丁不再需要。删除专测 `test_clear`，将其余一处中途重置改为新建索引。

### 任务三：暂存提交入口取证埋点（第一阶段，已完成）

口径为只补埋点、不改路由。因全量路径无未变更过滤，影子测量需要第二次全量扫描与重哈希，成本不低，故将其设计为按需开关，默认零开销。

- `crate-index-options.rs` 新增 `IndexOptions::to_scan_options`，作为索引文件宇宙的唯一来源；`IndexOrchestrator::build_scan_options` 改为调它，消除两份扫描配置。
- `crate-hot_update-change_detector.rs` 新增只读的 `measure_index_change_set`：以 `IndexOptions` 对应的扫描选项构造一次性检测器，返回增量路径针对活跃世代本会处理的变更集，不写入任何存储。
- `cce-server` 提交入口新增三类指标：频率计数器与全量索引耗时直方图始终记录；变更集占比直方图与结构化日志仅在环境变量 `CCE_INGEST_COMMIT_SHADOW` 为真时记录，用于取一次证后关闭，避免常驻成本。
- 新增等价性单测：影子测量与直接用等价扫描选项构造的检测器分类一致。通过。
- 第二阶段路由改造（入口改走增量或让全量承认未变更）列为证据触发，待影子数据落在高频、小变更比区间时启动。

#### 实际取证结果（第二阶段前置，已完成）

用真实提交入口驱动取证，采集到可用数据，同时暴露并修掉一处埋点缺陷。

缺陷：影子测量原先把登记库（registry database）的句柄传给检测器。文件哈希、实体与活跃世代清单都在按项目数据库里，登记库只保存项目清单，因此展开的一直是空视图，任何项目都会稳定报出 `ratio_permille=1000`——测量结果恒定无效。已改为按项目句柄（`for_project`）后再测量。

- 十文件工程首次提交：`added=10 modified=0 removed=0 unchanged=0 changed=10 ratio_permille=1000`。符合预期：全新工程无基线，属一次性引导成本。
- 改一个文件后二次提交：`added=0 modified=1 removed=0 unchanged=9 changed=1 ratio_permille=100`。这是第二阶段真正要的数字。
- 两次提交各自 `indexed_files=10`，即为一处变更重扫并重写了全部十个文件；第二次提交后基线被重建，增量子路径仍与刚被全量重写的内容保持一致。
- 提交后按项目库展开正确：`own_epoch=1`、清单 `active`、`files(epoch, rows, null_hash) = [(1, 10, 0)]`、`visible_paths=10`、`stored_hashes=10`；第二次提交后 `own_epoch=2`、两代共存。零拷贝世代模型工作正常。
- 结论：二次及以后的提交变更集约为 `1/10`，而入口固定付出全量十文件代价——取证窗口内"高频、小变更比"成立。
- 修复回归测试：`crate-app-cce-server-tests-ingest_shadow_evidence.rs` 驱动真实提交入口，断言首次提交建立零变更基线、单文件编辑量出 `100 permille` 变更集、两次提交各自重扫全部十文件、提交后增量测量回到零变更。通过。
