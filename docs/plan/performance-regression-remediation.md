# 性能回归修复计划

依据快照：本地工作树 `4d0d34c5`（含本轮未提交改动）。问题分析见 `docs/issue/performance-benchmark-supplement-2026-11-19.md`。本文件只描述改什么、按什么顺序改、每步如何验收，不重复指标表格。

## 现状判断

五项待处理问题中，两项已有生产实现，不能再按旧结论改：向量写入已经通过 `VectorBatchWriter` 以 512 点聚合提交，BM25 每个批次调用已经合并为一次 Tantivy 提交。微基准中的 32 点写入和逐文档 commit 是对旧形态和极端调用方式的探针，不是当前完整流水线的真实调用形态。因此不能用“把 32 改成 512”作为修复动作，必须先把 121 秒拆解到阶段，再决定动哪里。

已确认的缺陷是 `SearchModuleConfig::default()` 的零超时，已修复并加断言，纳入回归检查范围而不是重复实现。

## 阶段一：补齐阶段级可观测性

目标是把一次完整索引和一次检索请求都拆成可比较的阶段，避免继续凭微基准猜测。

索引侧在 `IndexResult` 上增加阶段耗时与调用计数：扫描与文件记录、批次解析/分组/切块、实体落库、向量写入、BM25 写入、摘要、关系构建与发布、NL 导出、终局 manifest，以及批次数量和批次内剩余开销。编排器在每批次的对应调用点累计耗时；总耗时回填 `elapsed_ms`，不再恒为 0。完整流水线基准改为向新的阶段 TSV 追加数据，保留原有趋势文件格式。

检索侧在 `QueryResult` 与 API 响应上增加本次请求的密集检索、嵌入、向量搜索、BM25 检索、融合、后处理耗时，以及是否来自缓存。密集检索策略内部拆分嵌入调用与向量引擎搜索；混合路径并行采集两路耗时。服务检索矩阵把阶段数据写入新 TSV，保留原延迟趋势文件。

验收：devs 上编译通过；500 与 5000 文件阶段 TSV 各一行；检索矩阵能显示冷请求约 100 ms 落在哪个阶段；配置超时回归测试通过。

## 阶段二：写路径与批处理修复

以阶段一的实测结果为决策门槛。

若写入阶段占比不足主要部分，则保持 `VectorBatchWriter` 的 512 点聚合和 BM25 单次提交不变，不为未证实的猜测引入二次批量层；只补充提交次数、批次数等计数，确认当前实现确实走了聚合路径。

若某一写入阶段成为主因，则优先在该阶段所属模块内增加有界聚合：跨批次积累待写向量或文档，达到阈值或操作结束时统一提交；工作单元标记必须仍在数据落盘后推进。禁止通过增加重复回退路径掩盖失败，禁止通过降低持久化保证换取指标好看。

若批次内剩余开销（状态跟踪、检查点、SQLite 事务）占比最高，则收敛每文件的状态写入为每批次一次，并保留失败文件的独立状态语义。

验收：同一台 devs、同一档位复测，5000 文件墙钟与阶段 TSV 对比阶段一；索引结果与错误数不变；重启恢复回归用例通过。

## 阶段三：检索冷路径修复

以阶段一采集的阶段耗时定位约 100 ms 冷启动悬崖：

- 若耗时在嵌入调用，处理查询嵌入缓存或 HTTP 连接复用，不改变检索语义；
- 若在向量引擎检索，检查首次索引加载或 HNSW 图构建，改为服务启动/索引发布时预热；
- 若在融合或标注，收敛一次性初始化到引擎构建阶段，避免按请求重复支付。

无论落点如何，修复必须保持现有“双路都成功才返回”的语义和缓存语义；不允许通过降级单路或吞掉错误改善延迟。

验收：devs 重跑检索矩阵，冷/热 p50 与 p99 同阶段一对比，错误数为 0；hybrid 冷请求不再出现约 100 ms 的整批尾部。

## 阶段四：配置默认值审计与收尾

对带 `serde(default)` 的顶层配置模块检查 Rust `Default` 与反序列化默认是否一致，至少覆盖 search、orchestrator、indexer、cache、hot update。发现不一致时直接修正 Rust `Default` 并加断言；不为旧值保留兼容路径。

收尾更新 `docs/issue/performance-benchmark-supplement-2026-11-19.md` 的结论和 `docs/tests/` 的运行说明，把“生产批大小 32”这类与当前代码不符的描述纠正为实测结论；所有新基准命令统一使用 `cargo bench`。

## 明确不做

- 不引入外部网络依赖、真实远程向量库、真实 LLM 或插件执行成本；
- 不新增“v2”模块，不把优化实现拆成并列新模块；
- 不改动召回率/重排质量评测口径；
- 不处理与本轮性能问题无关的已有 staged 删除文件。

## 执行方式

本地只做源文件修改与 `rustfmt`；按 `docs/dev/devs-sync.md` 以 `scp` 增量同步到 `devs:/data/kkkqkx/cce/repo`，在 devs 上编译、定向测试与复测。日志和 TSV 取回 `.bench_logs/`，最终结论回写 issue 文档。

## 执行结果与决策记录

阶段一已完成。`IndexResult::stages` 与 `QueryResult::stages` 均已落地，完整流水线和检索矩阵各自写入新的阶段 TSV。首次 5000 文件阶段数据把 92.2 秒中的 68.9 秒归到批次内剩余开销，检索冷请求的约 100 ms 主要落在嵌入调用。

阶段二已完成，但收益有限。新增了投影批写接口，全量索引期间把文件级状态投影延迟到批次边界提交，并补了落盘测试；5000 文件耗时从 92.2 秒降到 90.8 秒。它修正的是提交放大风险，不是主要瓶颈，故保留实现但不作为性能结论。

阶段三已完成主要修复。继续拆分批次内开销后定位到关系符号表构建：5000 文件中有 71.9 秒耗在逐文件符号累积。批量化到最终一次性构建后仍慢，进一步定位到两处 O(N²)：`prune_file_symbols` 对没有删除符号的新增文件也全量重建全局索引，`add_file_to_project` 每文件全量重建重载集合。前者改为只在确有符号移除时重建，后者改为脏标记加一次惰性重建。修复后 5000 文件从 92.2 秒降到 39.4 秒，500 文件从 4.16 秒降到 3.73 秒，规模曲线恢复为近似线性。

检索冷路径已完成归因但未彻底消除。阶段指标显示 coordinator、epoch 视图加载、缓存键、改写、融合与后处理都接近 0，hybrid 冷请求的嵌入耗时为 58～72 ms，仍有部分请求时间无法归入已埋点阶段。下一步需要在嵌入提供者内部按请求记录连接建立与响应耗时；本轮不做无依据的连接预热或降级改动。

阶段四已完成。search 模块默认超时由手写 `Default` 修正为 30 秒并加断言；orchestrator 的 `BatchConfig` 默认值与 serde 默认一致，未发现新的偏差。

验收记录：devs 全受影响 crate `cargo check --all-targets` 通过；`cce-codegraph` 1058 个单测通过；关系查询、索引关系、恢复重放与配置默认值的定向测试通过；最终完整流水线 500/5000 文件均成功索引，错误数为 0。

## 剩余任务复测结果

嵌入诊断已落地。`EmbeddingTiming` 把单次请求拆成传输提供者耗时和批处理/弹性封装耗时，指标经 `QueryStageTimings` 进入检索阶段 TSV。hybrid 冷请求 c=1 的 `embedding_ms=55.50`、`embedding_provider_ms=55.25`、`embedding_overhead_ms=0.25`；warm 命中缓存后均为 0。结论是该 100 ms 冷请求主要来自嵌入传输本身，而不是 resilience、批处理或本地编排；不做连接预热或单路降级。

符号表构建再次优化。`build_into` 用一次批量构建替代逐文件增量累积，并把扁平索引插入改成按 `(simple_name, file_path)` 去重后按名称排序一次；相关阶段耗时进入 `full_pipeline_stages.tsv`。5000 文件符号表从 11.9 秒降到 1.12 秒，其中扁平索引从 4.07 秒降到 0.66 秒；50,000 文件符号表从 786 秒降到 14.4 秒。

Large 档位已接入 `full_pipeline_perf`，`CCE_PERF_SIZE=large` 生成 50,000 文件。最终复测中 5000 文件墙钟 26.8 秒，50,000 文件墙钟 1,473 秒、峰值 RSS 约 9.5 GiB；后者仍受向量写入 622 秒、BM25 写入 591 秒与批次剩余开销 87 秒限制，属于后续独立的写路径扩展性问题。

远程后端、真实插件和真实高亮需要外部服务与插件产物，离线 devs 环境无法执行；本轮只补齐可离线运行阶段的数据采集与 Large 档位，相关缺口保留在 `docs/tests/benchmark_gaps.md`。
