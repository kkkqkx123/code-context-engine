# 关系索引常驻内存收敛：缺口修补实施方案

## 范围

本文是 `relation-index-next-node-gap-fix-plan.md` 的落地细化：1、4、5、6、7、8、9、10 是代码修补，11 给出处理决定，2、3 用可执行复测与逐列对照补齐，另外把三份契约产物全部重出（第 6 节）并记下复测中暴露的两个阻断缺陷（第 10 节）。

不在本次范围内：large 档（5 万文件）复测，本机内存 8 GB 不具备执行条件；medium 档与两组真实语料已完整覆盖。

排序依据仍是「状态正确性优先、展示链路其次、语义与指标最后」。

## 1. 重建失败统一收口

### 现状问题

- `build_and_publish_relations()` 的多条早期错误路径（构建库创建、构建配置缺失、符号注册、spool replay）直接返回，既不通知 runtime，也不复位 orchestrator 的 rebuilding 标志。
- 批次阶段失败时关系阶段被整体跳过，`begin_relation_rebuild()` 已经把标记置位，于是标记永久悬挂。
- 发布失败路径清除了标记，但没有任何一层通知 runtime，`Updating` 状态同样悬挂。
- engine 的硬失败路径只清理操作队列。

### 修改

统一为「一个失败入口、一个复位点」：

- 发布器契约新增「重建失败通知」能力，默认实现为空，服务端实现翻译为 runtime 状态迁移。通知只在 runtime 处于更新态时生效，重复通知与迟到通知都是惰性的，因此多层调用不会互相污染。
- orchestrator 记录本次重建所属的 operation，并新增唯一的收口方法：清除 rebuilding 标记、保持无内存快照、清理 exporter 增强引用、向发布器上报失败原因。
- `execute()` 拆成外层收口 + 内层执行。外层在内层返回后检查重建标记：仍置位即代表「已宣布重建但没有产出 generation」，按返回结果（错误或未完成原因）收口。这样早期 `?` 返回、批次阶段失败、关系阶段被跳过三类路径自动被同一个点覆盖。
- 关系阶段自身只有在真的激活了新 generation 时才清除标记，其余情况保持置位交给外层收口。
- engine 的硬失败路径调用同一通知入口，覆盖执行器层面逃逸的失败。

### 行为变化

- 失败后 `relation_rebuilding` 立即为 false，runtime 从 `Updating` 进入 `Degraded`。
- 存在旧 generation 时继续对外服务旧数据；不存在时查询侧得到明确的不可用，而不是「重建中」。
- 失败后 orchestrator 不保留内存快照，与设计文档「失败路径无内存快照」一致。

### 验证

- orchestrator：新增发布器替身，断言收口后标记清除、无快照、失败原因已上报；重复收口不会破坏状态。
- runtime：新增「更新态收口」与「非更新态通知惰性」两条用例。
- 发布器：用真实 store + runtime 覆盖成功、发布失败后收口、直接中止三条路径。

## 2. 展示链路补齐

### 修改

- MCP health 输出增加 `relation_rebuilding`，与既有 `active_epoch`、`runtime_epoch`、`rebuild_required` 并列，字段语义不变。
- 健康响应模型增加可选的「关系重建诊断」段：列出当前正在重建的 project。该段为新增字段，既有字段结构不变。
- 服务端 health 处理器从引擎聚合重建中的 project 列表填入该段；引擎只扫描已缓存的 runtime，不为诊断而实例化运行时。
- CLI 的 `health check` 打印重建诊断（空闲/重建中及 project 列表），`status` 在服务状态后追加一行重建提示，JSON 输出随模型自动带上该字段。

### 行为变化

- CLI、MCP、HTTP 三端都能观察到 `relation_rebuilding` / 重建中的 project。
- 既有成功响应结构不变，只多一个诊断字段。

### 验证

- MCP：新增字段构造用例，断言重建标记与既有字段同时出现。
- CLI：断言重建中与空闲两种文本分支（函数级）。
- HTTP：health 处理器已带字段，随 CLI/MCP 用例间接覆盖。

## 3. 清理入口统一

### 现状问题

- 没有 `ProjectSymbolTable::clear()`，清理语义散落在 `rebuild_indices()` 与 `clear_cache()` 中。
- `clear_cache()` 不清理 `BuildSymbolView` 的两组 qualified LRU，导致磁盘模式存在「清了缓存但工作集还在」的分叉。

### 修改

- `clear_cache()` 除解析缓存、负缓存、通配符缓存与排序缓存外，一并清理磁盘视图的 qualified 工作集；持久行不受影响。
- 新增 `clear()` 作为唯一清理入口，语义是「清缓存与工作集，不清符号数据」，磁盘与内存模式一致，文档中明确其与 `rebuild_indices()` 的分工。
- `rebuild_indices()` 复用该入口，避免两处行为漂移。

### 验证

- 磁盘模式用例：插入 → `clear()` → 查询仍可解析（回源持久表）→ `rebuild_indices()` → 查询与命名空间投影仍可解析，且常驻工作集为空。

## 4. 磁盘索引重建语义修正

### 现状问题

- 磁盘分支先清空持久 qualified 表，再遍历**常驻** `simple_name_index` 重建；磁盘模式下该映射为空，等于把索引清空后什么都不写回。
- 命名空间键由 `module_path + simple_name` 重新推导，与插入时的原始 qualified name 不是同一条规则。

### 修改

- 抽出唯一的命名空间键推导函数，插入路径与重建路径共用，规则不可能再分叉。
- 磁盘分支改为「按持久表重建」：以持久化的 qualified 键为权威来源，按文件回填模块路径，重算命名空间投影；键直接写库，不把全量键回灌常驻 LRU，重建后清空工作集。
- 持久 global 键在插入时写入、删除时精确删除，因此重建不再需要「先清空再推导」，也就不会出现清空后无源可依的情况。

### 行为变化

- 磁盘模式下重建前后解析结果一致，命名空间投影不再丢失。
- 常驻内存不因重建而增大。

### 验证

- 新增「插入 → 清理 → 重建 → 再查询」对照用例（第 3 节的用例同时覆盖本项）。

## 5. 指标口径修正

### 修改

- 容量统计拆成「常驻条目/字节」与「持久条目」两组，返回结构替代原来的二元组。
- `symbol_table_entries` / `symbol_table_estimated_bytes` 只反映常驻估算；新增 `symbol_table_persisted_entries` 反映构建库中的 qualified 键总量。
- 该字段贯通 stage 结果、API DTO、OpenAPI 模型与两份 perf TSV（服务基准、端到端性能示例）。

### 行为变化

- 磁盘模式的 `symbol_table_entries` 不再等于「索引总条目数」，可以直接用于判断常驻收敛；持久总量作为诊断字段单列。
- medium 复测时同时记录 RSS、候选裁剪、双指纹、实体/向量/关系计数与查询 p95。

## 6. 错误与等价性测试

### 修改

- 扫描清单条目数与批次数改为返回错误：查询失败不再静默归零（归零会让批次循环空转并把运行误判为完成）。

- 大批次场景沿用既有批次向量用例，规模按 medium 档量级取整（不引入 RSS 采样，避免测试环境噪声）。

## 7. 准备阶段失败的处理决定

### 现状问题

- 重建前准备失败（旧 generation 无法投影为磁盘视图）时只记录日志并继续，是否应中止全量操作没有结论。

### 决定

- 不中止。准备失败只影响重建窗口内的查询形态：查询侧退化为显式不可用，不返回空图或伪空结果；真正能恢复服务的只有随后的发布，因此中止等于把一次仍可能成功的重建提前判死。
- 该分支不属于终态，不上报失败通知；终态仍由第 1 节的统一收口覆盖。标记不会因此悬挂：重建若未产出 generation，收口点一定会被走到。

### 验证

- 新增用例：准备失败的发布器替身下，重建标记保持置位、内存快照为空、未产生失败通知；随后收口时标记清除且失败原因被上报。

## 10. 复测中发现的阻断缺陷

这些缺陷不在原问题清单里，但会让磁盘化构建在真实项目上直接失败，属于本次复测的实际产出。

### 10.1 属性回看窗口按字节切分导致 panic

- 现象：索引本仓库源码时 `cce-parser` 连续 panic，报 `byte index N is not a char boundary`，位置在属性提取器的回看窗口。
- 原因：300 字节窗口的起点是裸字节偏移，落在非 ASCII 字符（破折号、箭头等）中间时切片非法。中文项目里这类字符很常见。
- 修改：窗口起点用 `floor_char_boundary` 对齐；codegraph 里同构的 200 字节导入上下文窗口一并处理（那段代码原文会让 `from_utf8` 失败并静默丢掉上下文）。
- 验证：新增用例在 284..=291 的填充长度上扫过窗口边界，修复前必然 panic，修复后属性仍能正常提取。

### 10.2 类型索引无法序列化，关系阶段直接失败

- 现象：关系阶段报 `Failed to persist local symbols: key must be a string`，整次重建中止。
- 原因：模块记录以 JSON 落库，而类型索引的两张表分别用结构体键与实体 id 键，JSON 对象键必须是字符串——文件里只要出现一个被识别的类型就写不进去。合成语料恰好没有类型定义，所以一直没暴露。
- 修改：改为按键排序的键值对序列写出、读回时还原为映射；两张字符串键的索引也纳入同一写法，避免哈希迭代顺序进入持久化字节（否则同一索引每次写出的记录不同，指纹无法稳定）。
- 验证：新增两条用例——含成员的类型索引可写出并读回；不同插入顺序产生完全相同的 JSON。
