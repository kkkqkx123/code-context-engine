# 写路径规模化改进方案

## 依据与范围

本文基于 `docs/issue/performance-writepath-followup-2026-11-20.md`，以当前代码为准给出改进方案。
问题 1～5 是本轮直接改动对象；问题 6 是写路径改动后的复测口径；问题 7～9 属于独立 SLA 与观测治理，
不在本轮改变生产默认值或后端选择；问题 10 的恢复失配输入与大规模远端矩阵按容量条件安排复测。

已完成的实体批量事务、符号表 O(N²) 修复、hybrid 令牌桶夹具修复不重复实施。本轮只改现有写路径与指标契约，
不新增版本化模块，也不保留旧路径兼容层。

## 现状判断

50,000 文件档的瓶颈已不在解析、分组或关系符号表，而在提交边界：

- 向量写入每个编排批次结束即 flush。即使单个 embedding 微批只有约 100 点，也支付一次 WAL fsync、事务提交和
  索引发布，导致 5,000 点产生 50 次 flush。`VectorBatchWriter` 的 512 点阈值在跨批次场景下没有机会生效。
- BM25 每个编排批次调用一次提交。Tantivy 的 writer 已是长生命周期共享实例，剩余成本来自提交次数、reader
  刷新与后台段合并，但阶段 TSV 没有任何提交级指标可以区分这些来源。
- 批次剩余开销把状态投影、检查点读写、进度更新和批内簿记混成一个总数，无法定位下一个真实锁或事务瓶颈。
- 50,000 文件档 RSS 约 9.5 GiB，但只有全流水线峰值，没有阶段边界内存和聚合窗口容量数据。

因此先补齐提交次数、子阶段耗时和阶段内存，再把提交边界从“每个编排批次”上移到“聚合窗口”；
数据落盘、工作单元标记和批次检查点三者必须在同一边界推进。

## 修改方案

### 1. 向量跨批次聚合与检查点边界

在完整索引的批次循环中共享一个 `VectorBatchWriter`，而不是每批次新建。embedding 生成、SQLite chunk/映射落库
仍按原顺序执行，但点缓冲区跨批次累积到 512 点阈值或运行结束时才 flush。

提交边界定义为：先 flush 缓冲点，再把该范围内所有 embedding 工作单元改为 `Committed`，
随后推进批次检查点索引。任一环节失败时工作单元保持 `Running`，批次检查点不越过失败批次；
恢复后这些微批按原哈希重放，点 ID 的确定性保证重放是覆盖而不是重复。

文件级状态投影同步推迟：Embedding 模块成功、Embedding 阶段完成和文件 Completed 标记在提交成功后写入；
失败文件仍立即保持失败状态。热更新与死信重试继续使用原有的单次写入入口，不共享完整索引的跨批次缓冲。

### 2. BM25 聚合提交与可解释指标

在本地全文后端增加“暂存文档、提交并刷新”两段式写入：暂存只把文档交给长生命周期 Tantivy writer，
提交才执行 commit 与 reader reload。完整索引批次循环按文档数阈值或运行结束触发提交，
并把同一窗口内的 chunk 记录、实体映射和工作单元标记合并为一次落库与一次状态更新。
远端全文后端沿用契约的默认即时提交语义，不伪造本地计数器。

提交后立即可见的含义是：reader 在同一次提交中被显式刷新；一个聚合窗口内尚未提交的新文档不对外可见。
工作单元只在提交返回成功后标记 `Committed`，崩溃恢复会重放未提交窗口。

阶段指标新增 BM25 commit 次数、文档数、文档构造、commit、refresh、merge 等待耗时，
以及暂存文档峰值。merge 等待只在运行末尾 drain 一次，避免每次提交阻塞合并线程池。

### 3. 批次剩余开销拆分

在批次循环内显式计时状态投影、检查点读写、进度更新、批内调度和派生写入提交，
其余部分才计入 `batch_overhead_ms`。同一批中同一文件的重复状态标记在提交边界去重，
但失败状态不合并、不忽略。该拆分只改变观测粒度，不改变成功/失败分类。

### 4. 阶段内存与容量归属

在扫描结束、批次结束、关系构建结束和最终收尾采样进程 RSS，并记录批次循环内的峰值；
同时记录向量待写点峰值和 BM25 暂存文档峰值。容量结论以这三类数据为准：
允许随文件数增长的是最终索引与关系快照，必须有上限的是批次缓存、向量待写缓冲和 BM25 暂存窗口。

指标经 `IndexStageTimings`、API DTO、服务索引阶段 TSV 和完整流水线阶段 TSV 输出，
列变化时由报告工具重建表头，避免旧表头下继续追加新列。

## 验收标准

- 5,000 文件本地分支的 WAL flush 次数接近按 512 点聚合的下界；提交等待在阶段 TSV 中可解释。
- 50,000 文件本地档的向量与 BM25 阶段绝对耗时和占比下降，规模曲线接近线性；峰值暂存容量有上界。
- BM25 阶段能解释 commit 次数、每提交文档数、commit/refresh/merge 耗时；提交后新文档立即可见。
- `batch_overhead_ms` 被拆成可测子项，失败文件状态和检查点边界语义不变。
- 崩溃恢复用例覆盖：向量 flush 前失败、flush 后标记前失败、BM25 提交前失败、提交后派生写入失败。
- devs 上编译、单测和基准采集通过；四档服务矩阵错误数为 0，索引结果一致。

## 明确不做

- 不关闭 WAL、不降低 `synchronous`、不跳过 flush，也不把未提交工作单元标记为已提交。
- 不通过调整 `scan_batch_size` 或 `embedding_batch_size` 掩盖提交频率问题。
- 不改变召回口径、查询融合语义或 ES/Qdrant 的固有延迟 SLA。
- 不把 mock provider 的限流处理带入生产默认值。
- 不为了修正聚合边界新增旧路径兼容层。

## 执行方式

本地只做源文件与文档修改及格式化；按 `docs/dev/devs-sync.md` 同步到 devs，编译、单测与指标采集均在 devs 完成。
日志与 TSV 取回 `.bench_logs/`，结论与剩余问题回写 issue 文档。

## 执行结果与复测结论

全部改动以同步包 `cce-src-cc8f4daa-writepath.tar.gz` 部署到 devs。devs 上
`cargo check --workspace --all-targets`、`cargo build -p cce-cli -p cce-server`、
`cargo clippy --all-targets --all-features`、`cargo test --workspace --lib` 均通过；
检查点恢复、向量写入和 BM25 对齐三组集成测试分别为 6/6、13/13、4/4 通过。

| 指标 | 修复前 | 修复后 | 结论 |
|---|---|---|---|
| 5,000 文件本地向量 WAL flush | 50 | 10 | 达到 512 点聚合量级，提交等待 11.4 s 降至约 0.7 s |
| 5,000 文件 BM25 commit | 约 50 | 1 | 文档构造与 commit 不再按编排批次重复 |
| 5,000 文件服务索引墙钟 | 84.5–137.6 s | 59.7–64.2 s | 四档错误数为 0，索引结果一致 |
| 50,000 文件完整流水线墙钟 | 1,473 s | 752 s | 降幅约 49% |
| 50,000 文件 BM25 阶段 | 约 591 s | 0.06 s | 原成本的主体是每批全量实体 ID 重载，而非 Tantivy commit |
| 50,000 文件批次剩余开销 | 约 87 s | 24.6 s | 子阶段已拆分，状态投影 1.2 s、检查点 6.1 s、提交 1.9 s |

关键修复是两处提交边界调整：向量与 BM25 跨编排批次聚合到同一提交边界；实体 ID 映射以递增行游标增量扩充，
不再每个编排批次全量重扫。BM25 提交后 reader 显式刷新，新增文档立即可见；工作单元仅在提交成功后标记已提交，
批次检查点不越过未提交范围。

## 仍存在的问题

- 50,000 文件档向量阶段仍为约 542 s，占总墙钟约 72%；5,000 文件档约 24 s，规模曲线仍偏超线性。
  现有指标已排除 WAL flush 与 HNSW 构建，下一步需要在嵌入调用、chunk/entity 映射落库和点构造之间继续拆分。
- 50,000 文件档峰值 RSS 约 9.5 GiB 未下降；批次结束后约 1.5 GiB，关系构建后升至约 9.2 GiB。
  允许随文件数增长的是最终关系快照，但缺少逐结构容量上限的结论。
- 完整流水线基准的向量 WAL 计数器为 0，而服务路径计数器正常；基准夹具的 collection 指标快照口径需要在后续核对，
  不能在完整流水线 TSV 中用零值推断引擎未落盘。
- 首次 medium 服务矩阵中 Qdrant 因开发环境 `ulimit -n=1024` 出现文件描述符耗尽，重启服务后四档全部通过；
  这是环境容量问题，不通过降低服务持久化配置规避。
- 本地 `Cargo.lock` 与工作区 `mlua = "0.12"` 声明不一致，devs 首次 cargo 执行自动解析到 0.12.3；
  该偏差早于本轮改动，后续需单独决定锁文件基线。
- ES/JVM 常驻开销、Qdrant 冷查询小样本长尾与生产 provider 限流仍按独立 SLA 治理；
  恢复失配输入和 50,000 文件远端四档矩阵尚未覆盖。
