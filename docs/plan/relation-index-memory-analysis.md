# 关系索引峰值内存分析与下一阶段方案

## 结论先行

50,000 文件一轮的峰值 RSS 已不再来自关系 spool 的全量解析文件驻留：该路径已改为逐文件流式回放。
峰值来自构建结束后的**全内存查询索引**以及随后为写盘而做的**规范快照二次物化**。
两者都持有同一批实体和关系节点的不同表示，且 publisher 会把构建图的内存映射直接共享给查询运行时，
所以构建期不可能靠“写完就丢”来降峰值。

关系节点**应该**在构建过程中持久化，但仅“中途写入 SQLite”不能单独解决 RSS：
只要查询运行时仍要求全量 DashMap，最终仍必须把节点装回内存。
有效路径是：分块流式写出规范快照，并把查询侧索引改成有上界的磁盘/分片表示。
下一阶段以“任何 O(项目规模) 的全量 Vec 或全量驻留都是缺陷”为原则推进，
不为降低 RSS 截断关系、不改变快照指纹或召回。

## 实测证据

50,000 文件完整流水线阶段指标：

| 指标 | 数值 | 说明 |
|---|---:|---|
| 批次结束 RSS | 1,395,084 KiB | 约 1.4 GiB，实体与向量阶段后 |
| 关系结束 RSS | 9,300,324 KiB | 约 9.3 GiB，关系构建与发布后 |
| 峰值 RSS | 10,084,568 KiB | 约 9.6 GiB |
| spool 条目 / 编码字节 | 50,000 / 46,511,821 | 磁盘 spool，非内存驻留 |
| 符号表条目 | 725,024 | 包、全局索引、类型上下文合计 |
| 关系节点 | 1,349,968 | 实体与文件级节点合计 |
| 关系边 | 0 | 本合成夹具没有实体调用边，内存由节点主导 |
| 关系节点估算 | 8,292,438,392 B | 按实测约 6 KiB/节点估算 |

关系是唯一的 RSS 突增阶段：spool 编码仅 46 MB，符号表按每条目约 128 B 估算约 93 MB，
而 135 万个关系节点按实测单节点足迹估算约 8.3 GiB，与 7.9 GiB 的 RSS 增量吻合。
因此继续优化 spool 或符号表不会解决主要矛盾。

## 内存构成

1. **构建期关系索引**：`RelationIndex` 用 `DashMap` 持有函数实体、实体到文件、文件记录、
   名称索引、正向/反向关系与符号键映射。实体 `metadata` 是字符串到字符串的哈希映射，
   每个节点的真实开销远高于条目数本身，实测约 6 KiB。
2. **符号表**：包表、模块表、全局名称索引、类型上下文。它必须跨文件解析，不能按文件丢弃；
   但 72.5 万条目约 93 MB，量级远小于关系索引。
3. **规范快照二次物化**：`to_canonical_snapshot` 把内存索引再转换为
   `files / entities / relations / dependencies` 四组 Vec，随后写入 SQLite。
   写出期间同时存在内存图和 canonical Vec，peak 会再次抬高。
4. **查询运行时共享**：publisher 通过 `from_index_shared` 把构建期 DashMap 零拷贝交给运行时。
   这是发布性能优势，也意味着构建图的全部内存在发布后仍常驻；不能假设“发布后即可释放”。

## 横向核对：实体、块与状态存储

同类风险按 50,000 文件档实测排序如下：

| 结构 | 规模 | 估算/实测 | 结论 |
|---|---:|---:|---|
| 关系索引节点 | 1,349,968 | 约 8.3 GiB | 主因，必须治理 |
| 本地向量点与 HNSW | 50,000 点 | 约百 MB 量级 | 查询期索引，按设计常驻 |
| `source_entity_ids` | 674,984 项 | 约 86 MB | 全项目线性，需有界化 |
| 符号表 | 725,024 项 | 约 93 MB | 跨文件解析所需，纳入容量报表 |
| `UpdateStateTracker.states` | 50,000 文件 | 数十 MB 量级 | 全项目线性，需有界化 |
| 向量暂存窗口 | 7,788 派生行 | 有界 | 无同类问题 |
| BM25 暂存窗口 | 2,100 文档 | 有界 | 无同类问题 |
| 关系/导出 spool | 50,000 路径 | 磁盘支撑 | 无同类问题 |

实体行与 chunk 行都按批次写入并释放，不存在跨批次全量驻留；
唯一跨批次增长的是实体 ID 查询映射与文件状态映射，量级远小于关系索引，但应在本方案之后按同一原则有界化。
规范快照的 `Vec` 二次物化与查询期全内存关系图仍是唯二能解释 GiB 级增量的结构。

## 关系节点是否应该中途持久化

应该，但要区分两种“持久化”：

- **规范快照分块写入**：把已经稳定的实体、文件、关系、依赖按块写入 `Building` 状态的 epoch，
  最后原子激活。这样可避免写盘时的全量 Vec 二次物化，并与现有 manifest 的 `Building/Ready/Active`
  状态机自然衔接。这是下一阶段的第一步。
- **构建期节点逐文件落库后再释放**：只有当查询运行时不再要求全量内存图时才成立。
  当前 `RelationSnapshotLoader` 冷启动仍把规范快照完整装入 `RelationIndex`，
  查询接口直接读 DashMap。因此中途落库若不同时改造查询侧，只会增加写入放大，RSS 不会下降。

现有元数据层已经按批次持久化实体行，关系阶段又按 spool 重建一遍实体节点。
下一阶段不再增加第三份“构建中节点表”；而是让规范快照写入成为唯一持久出口，
并逐步让查询侧从该出口按需读取。避免把构建中间态当作可查询数据发布。

方案 B 的细化为下一阶段任务，见 `docs/plan/relation-sharded-query-index-design.md`。
本轮流式工件改造只关闭了规范快照二次物化，查询侧分片化尚未实施。

## 可选方案比较

- **方案 A：只分块写规范快照**。改动最小，能消除写盘时的第二份大对象；
  峰值仍受构建期全量关系图约束，预计只能部分下降。作为第一步实施。
- **方案 B：磁盘/分片关系索引**。把实体与关系按文件或符号前缀分片落盘，
  查询时只装载命中分片并保留有界 LRU。能真正压低 RSS，但需要改查询接口、热更新 delta 与
  指纹计算路径；风险最高，是最终目标。
- **方案 C：mmap 只读快照**。发布时生成紧凑、不可变的 mmap 结构，查询只读该结构。
  比 B 更集中，但需要重新设计 `RelationIndex` 的写入接口与热更新分层，仍需兼容现有快照指纹。
- **方案 D：声明容量 SLA 并保持现状**。只能用于过渡，不满足“全量入内存不可接受”的目标，
  不作为最终方案。

## 下一阶段执行顺序

1. 在现有 `RelationIndex` 与 publisher 上增加分块快照写出能力，取消 `to_canonical_snapshot`
   的全量 Vec 物化；保持 fingerprint、版本号、manifest 状态机与原子激活语义不变。
2. 增加构建期与发布期容量指标：canonical 实体/关系写出批次、写出缓冲峰值字节、
   发布后运行时索引条目数；与现有 `rss_after_relation_kb` 同表输出。
3. 以 50,000 文件档复测，确认分块写出的 RSS 降幅；若仍由构建期关系图主导，进入第 4 步。
4. 把查询侧关系索引改造为分片按需装载：默认内存有界，分片来自已激活的规范快照；
   热更新 delta 叠加在已装载分片上，不改变快照 fingerprint 与查询融合结果。
5. 在所有环境统一启用流式路径；不保留“小项目全量载入、大项目分片”的双路径，
   只用显式容量参数表达上界。

## 验收口径

- 50,000 文件档峰值 RSS 相较本轮至少下降 50%，或查询期内存有可实测的硬上界。
- 快照 fingerprint、canonical 内容、关系数量与查询结果与改动前逐字节一致。
- 冷查询 p95 不出现数量级回归；首字节延迟单独记录，不与 Tantivy 混同。
- 不关闭 WAL、不降低同步级别、不跳过 flush，不放宽事务边界。
- 不新增版本化模块或兼容层，不通过截断关系、丢弃边或降低召回换取内存下降。

## 明确不做

- 不在缺少分片查询方案前把构建期节点表当作正式数据源。
- 不把关系快照写入恢复失配数据伪装成容量优化。
- 不以调大 batch size、调低 spool 条目上限或缩短 manifest 保留期代替结构性改造。
- 不改变 `SnapshotDelta` 语义、CAS 发布流程与已有恢复用例。
