# 存储架构设计概述

## 架构概览

本项目采用多存储引擎架构，针对不同的数据访问模式优化存储方案：

```
┌─────────────────────────────────────────────────────────────┐
│                    应用层 (Application)                      │
├─────────────────────────────────────────────────────────────┤
│                协调层 (Orchestrator Layer)                   │
│  ┌─────────────┐  ┌─────────────┐  ┌───────────────────┐  │
│  │ IndexOrche- │  │ QueryOrche- │  │ StorageCoordinator│  │
│  │  strator    │  │  strator    │  │ (候选人两阶段提交) │  │
│  └─────────────┘  └─────────────┘  └───────────────────┘  │
├─────────────────────────────────────────────────────────────┤
│                   存储引擎层 (Storage Engines)               │
│  ┌─────────────┐  ┌─────────────┐  ┌───────────────────┐  │
│  │   SQLite    │  │    BM25     │  │     Qdrant        │  │
│  │ (元数据/关系) │  │ (全文搜索)  │  │   (向量搜索)      │  │
│  │  + checkpoint│ │  (Tantivy)  │  │                   │  │
│  └─────────────┘  └─────────────┘  └───────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

## 存储引擎职责划分

### 1. SQLite (结构化元数据存储)
- **职责**: 存储代码实体的结构化元数据、关系快照、索引清单与检查点
- **数据类型**: 文件、实体、chunk、关系快照、project_meta、project_index_manifests、checkpoint
- **访问模式**: 精确查询、关系遍历、事务操作、FTS5 实体搜索、epoch/版本管理
- **优势**: ACID 事务、外键约束、WAL 模式
- **使用场景**: 代码导航、依赖分析、增量索引断点恢复、版本发布账本

### 2. BM25 (全文搜索索引)
- **职责**: 提供基于关键词的全文搜索功能
- **数据类型**: 文档（包含标题、内容、关键词字段）
- **访问模式**: 相关性搜索、模糊匹配、高亮显示
- **实现**: 进程内 Tantivy 索引（IndexManager 管理 writer/reader）
- **使用场景**: 代码搜索、文档搜索、快速查找

### 3. Qdrant (向量数据库)
- **职责**: 存储代码片段的向量表示，支持语义搜索
- **数据类型**: 高维向量 + 元数据（epoch、project group、category 等过滤字段）
- **访问模式**: 相似性搜索、最近邻查询
- **使用场景**: 语义代码搜索、代码推荐、相似代码发现
- **运维**: 可内嵌管理 Qdrant 子进程（健康检查/自动重启），集合配置定时升级（导出→重建→导入）

## 数据流设计

### 索引流程
```
文件扫描 → 解析 → 预处理 → 转换 → 存储
    │         │        │        │       │
    │         │        │        │       ├──→ SQLite (结构化数据)
    │         │        │        │       ├──→ BM25 (文本索引)
    │         │        │        │       └──→ Qdrant (向量存储)
    │         │        │        │
    └─────────┴────────┴────────┴─────────→ 实体映射表 (entity_detail_mappings)
```

热更新写入通过 `StorageCoordinator` 的候选人机制完成：先克隆活跃 epoch 到隔离候选代，处理器逐模块写入（embedding → bm25 → summary → relation），成功后原子激活候选清单，失败可回滚。跨存储写入不具备原子性，依靠幂等点 ID（稳定 hash）保证重复写入无害，失败恢复由 checkpoint/work_unit 断点续跑机制承担。

### 查询流程
```
用户查询 → 查询协调 → 并行查询 → 结果合并 → 丰富结果
    │          │          │          │          │
    │          ├──→ SQLite (关系/元数据)  │         │
    │          ├──→ BM25 (关键词搜索)    │         │
    │          └──→ Qdrant (语义搜索)    │         │
    │                                   │         │
    └───────────────────────────────────┴─────────┘
```

Hybrid 查询通过 `tokio::join!` 并行执行向量召回与 BM25 召回，再按 alignment_key（entity_id → segment_id → chunk_id）融合加权排序，最后由 SQLite 富化行号/内容等信息。

## 数据一致性模型

### 最终一致性设计
- **索引时**: 数据同时写入多个存储，SQLite 内事务原子，跨存储不保证原子性
- **版本管理**: epoch（全量重建）+ batch_id（热更新批次）双层版本，查询只读活跃 epoch
- **查询时**: 通过实体映射表（entity_detail_mappings）关联不同存储的数据
- **删除时**: 同步删除所有存储中的相关数据（幂等，可重试）
- **发布机制**: `project_index_manifests` 作为发布账本（building/active/failed 状态）

## 性能考虑

### 读优化
- **SQLite**: WAL 模式 + 索引优化 + FTS5
- **BM25**: 进程内索引，按 project_id/epoch 隔离
- **Qdrant**: HNSW 向量索引，按数据量自动选择配置预设

### 写优化
- **批量操作**: 索引时批量写入
- **幂等写入**: 稳定点 ID + upsert，可安全重试
- **增量更新**: 只更新变化的部分

## 扩展性设计

### 水平扩展
- **SQLite**: 单文件数据库，可按项目/epoch 分片（candidate 隔离）
- **BM25**: 支持多索引，可按项目或语言分片
- **Qdrant**: 分布式集群支持

## 容错与恢复

### 故障恢复
- **事务回滚**: SQLite 支持原子事务
- **断点恢复**: checkpoint 表族（checkpoint/checkpoint_batch/checkpoint_file/work_unit_checkpoint/index_state_projection）
- **索引重建**: BM25 和 Qdrant 支持全量重建（epoch 递增发布）；外部存储写入均为幂等 upsert，中断后重放即可收敛

## 设计原则

### 1. 关注点分离
- 每个存储引擎专注于特定类型的数据和查询
- 避免功能重叠，保持职责清晰

### 2. 最终一致性
- 接受短暂的数据不一致
- 通过幂等写入（稳定点 ID + upsert）与 checkpoint 断点续跑机制保证最终一致性，失败后重放写入即可收敛，无需独立重试队列
- 简化系统复杂度

### 3. 可扩展性
- 支持独立扩展每个存储组件
- 松耦合设计，便于替换存储引擎

### 4. 性能优先
- 针对不同查询模式优化存储
- 批量操作减少 I/O 开销
- 缓存热点数据

## 总结

本存储架构设计采用多引擎策略，充分利用每个存储引擎的优势：
- **SQLite** 提供 ACID 事务、关系查询、版本管理、断点恢复
- **BM25** 提供快速的全文搜索
- **Qdrant** 提供语义搜索能力

通过协调层统一管理，实体映射表解决数据关联问题，最终一致性模型平衡了性能和数据一致性需求。该设计支持水平扩展，具备良好的容错能力，满足代码索引和分析的高性能需求。
