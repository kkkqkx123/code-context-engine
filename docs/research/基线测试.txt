## 设计思路（基于现有Rust架构）

### 一、方案合理性判断

**总体合理**，核心设计思路正确。主要优势：

1. **职责分离清晰**：fixture定义标准测试集 → 向量化 → 序列化存储 → 评估输出
2. **可复现性强**：rkyv二进制序列化保证嵌入一致性，便于对比不同方案
3. **轻量级评估**：本地运行，无需外部服务

**需要改进的关键点**：

| 问题 | 改进方向 |
|------|---------|
| 缺少对比基线 | 至少测试3种方案：原始代码 / NL转换 / 混合 |
| 查询类型未区分 | 分类测试：精确符号查询 / 语义查询 / 跨语言 |
| 指标单一 | 增加MRR、Recall@K、NDCG |
| 无统计分析 | 多次运行计算均值和方差 |

### 二、Fixtures设计思路

#### 2.1 数据对构造策略

```
正例构造:
  - 精确匹配: 查询函数名 → 对应函数片段
  - 语义匹配: "初始化一次" → get_or_init / set / try_insert
  - 类型匹配: "线程安全" → sync::OnceCell (排除unsync)
  
负例构造:
  - 同级负例: 同文件但功能无关的函数
  - 相似负例: get和get_mut（易混淆但不同）
  - 随机负例: 完全无关类型
```

#### 2.2 查询分类体系

```yaml
Type A - 精确查询:
  特征: 包含具体符号名(::, <, fn)
  示例: "OnceCell::get_or_init"
  预期: BM25强，向量中
  
Type B - 语义查询:
  特征: 自然语言描述功能
  示例: "如何安全地获取可能未初始化的值"
  预期: 向量强，BM25弱
  
Type C - 跨语言查询:
  特征: 中文描述代码概念
  示例: "懒加载的全局变量"
  预期: NL转换方案有优势
```

### 三、序列化存储设计

#### 3.1 分层存储策略

```
一级存储 (rkyv):
  - 目的: 快速加载嵌入向量
  - 格式: 连续内存布局的Vec<f32>
  - 优势: 零拷贝反序列化
  
二级存储 (serde_json):
  - 目的: 可读的评估结果
  - 格式: 结构化JSON
  - 优势: 便于后续分析和可视化
```

#### 3.2 存储内容规划

```yaml
data/embeddings/{scheme}:
  - vectors.rkyv: 原始浮点向量
  - metadata.rkyv: id到索引的映射
  
data/fixtures:
  - queries.json: 查询集（固定不变）
  - corpus.json: 代码片段库（固定不变）
  - relevance.json: 相关性判断（三元组）
  
outputs/{timestamp}/{scheme}:
  - scores.json: 每个查询的匹配分数
  - metrics.json: MRR/Recall@K等指标
  - confusion.json: 分类错误分析
```

### 四、评估指标体系

#### 4.1 核心指标

```
Rank-based:
  - MRR: 第一个正例的倒数排名均值
  - Recall@K: K个结果中正例覆盖率
  - MAP: 平均精确率均值
  
Category-specific:
  - 按查询类型分层统计
  - 按难度分层统计
  - 按代码特征分层(unsafe/generic/async)
```

#### 4.2 统计显著性

```
建议: 重复运行5次，计算:
  - 均值 ± 标准差
  - 配对t检验（对比方案间差异）
  - 效应量(Cohen's d)
```

### 五、方案对比矩阵

| 方案 | 向量化文本 | 预期优势 | 预期劣势 |
|------|-----------|---------|---------|
| A: 原始代码 | `fn get(&self) -> Option<&T>` | 精确符号匹配 | 语义泛化弱 |
| B: NL转换 | `FUNC get : receives &self returns Option ref T` | 平衡精确与语义 | 信息有损 |
| C: 混合 | 拼接原始代码+NL描述 | 最全面 | 向量最长 |
| D: 仅签名 | `fn get(&self) -> Option<&T>` | 最简洁 | 丢失实现细节 |

### 六、实验流程设计

```yaml
阶段1 - 数据准备:
  - 从once_cell提取100-200个函数片段
  - 人工标注30-50个查询的相关性
  - 确保每个查询至少2个正例、5个负例

阶段2 - 嵌入生成:
  - 对每个方案生成独立嵌入
  - 验证嵌入维度一致(384 for all-MiniLM-L6-v2)
  - 保存rkyv序列化文件

阶段3 - 检索评估:
  - 每个查询独立进行top-10检索
  - 记录每个方案的排序结果
  - 计算分层指标

阶段4 - 结果分析:
  - 生成对比表格
  - 分析失败案例
  - 统计显著性检验
```

### 七、关键设计决策

#### 7.1 为什么不用FAISS？

如果数据量小(<10k片段)，可以直接暴力搜索：
- 避免额外依赖
- 结果精确可复现
- 性能足够（N=1000时约1ms/查询）

#### 7.2 查询处理策略

```
同一查询在评估不同方案时保持一致:
  - 方案A: 查询原文
  - 方案B: 查询原文（NL模型已理解）
  - 方案C: 查询原文
  
不需要针对方案B做查询转换，让模型自己泛化
```

#### 7.3 序列化格式选择

```
rkyv适用场景:
  - 嵌入向量（重复读取，内存映射）
  - 索引映射（快速随机访问）
  
serde_json适用场景:
  - 评估结果（人类可读）
  - 配置信息（便于修改）
  - 相关性标注（版本控制友好）
```

### 九、潜在风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 标注偏差 | 多人标注+一致性检查 |
| 过拟合测试集 | 预留20%作为验证集 |
| 随机性影响 | 固定随机种子+多次运行 |
| 模型版本敏感 | 记录精确模型版本和参数 |

### 十、下一步建议

1. **先做小规模验证**：10个查询 × 3种方案，验证流程通畅
2. **建立基线**：实现BM25作为底线对比
3. **迭代优化**：根据失败案例改进NL转换模板
4. **扩展测试**：增加更多crate（如lazy_static, parking_lot）

这个设计思路在你的Rust架构下完全可行，核心是保持fixture的固定性、评估的科学性、结果的可复现性。
