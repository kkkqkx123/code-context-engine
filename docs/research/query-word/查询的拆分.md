结论非常明确：**强烈建议尽可能拆分不同问题，独立进行查询。**
无论是在向量检索还是 BM25 检索中，将多个子问题合并为一个查询，都会显著降低召回率和准确性，但两者的原因各不相同。
下面详细剖析原因，并给出代码库检索场景下的最佳实践架构。
---
### 一、 为什么向量检索必须拆分？
向量检索的本质是计算**语义质心**。当你把多个问题合并成一个字符串去求 Embedding 时，产生的是所有意图的“平均向量”。
*   **语义质心漂移（语义模糊化）**：
    *   假设用户问题：*"如何连接Redis，以及如何解析JWT token？"*
    *   如果**合并查询**：生成的向量会落在“Redis连接”和“JWT解析”的中间地带。这个中间向量可能既不靠近 `RedisClient` 的代码，也不靠近 `AuthService` 的代码，最后召回的是一堆毫无关联的“中间地带文档”（比如可能召回一些关于网络连接配置的通用代码）。
    *   如果**拆分查询**：查询1精准定位 Redis 相关代码，查询2精准定位 JWT 相关代码，两路都能获得极高的语义相似度得分。
*   **长文本截断风险**：合并后的问题变长，在经过 Embedding 模型时，如果超过最大长度限制，部分意图会被直接截断丢失。
### 二、 为什么 BM25 也必须拆分？
BM25 是基于词频（TF）和逆文档频率（IDF）的词袋模型。合并查询会带来严重的词频干扰。
*   **词频稀释与不公正的 IDF 加权**：
    *   假设合并查询：*"connect redis parse validate jwt token"*
    *   在代码库中，`redis` 和 `jwt` 都是低频、高区分度的词（IDF 高）。如果放在一起查，BM25 会寻找同时包含这些词的文档。但现实中，极少有一个代码块同时包含 Redis 连接和 JWT 解析。
    *   如果某个文档只包含 `jwt token`，但因为查询中混入了 `redis`，该文档的得分会被拉低；反之亦然。
*   **逻辑关系混乱**：
    *   子问题之间通常是 **OR（并行）** 关系（找 A **或** 找 B），但合并成一个查询词串后，BM25 的默认打分逻辑倾向于奖励**同时命中多个词**的文档（类似 AND 逻辑），导致精确的单一命中文档排在后面。
### 三、 唯一的例外：何时可以合并？
只有在**子问题之间是强约束的 AND 关系，且必须在同一个代码块中同时满足**时，才应该合并。
*   **例子**：*"找到删除用户**并且**清理相关缓存的函数"*。
*   这种情况下，"delete user" 和 "clean cache" 必须在同一个方法里出现，此时合并查询（或者构造 MUST 逻辑）才是合理的。
---
### 四、 代码库检索的最佳实践架构：Query Decomposition + RRF
既然必须拆分，那么系统该如何设计？目前主流的 RAG 检索架构（如 LangChain 的 MultiQueryRetriever 或自研架构）通常采用以下流程：
#### 1. LLM 意图拆解
让 LLM 充当 Query Planner，将复杂问题拆解为独立的子查询。
**Prompt 示例**：
```markdown
你是一个代码检索专家。请将用户的复杂问题拆解为 1-3 个独立的子查询，每个子查询聚焦于一个特定的代码功能或实体。
严格以 JSON 列表格式输出。
用户问题：如何连接数据库，并在出错时记录日志？
输出：
[
  {"vector_query": "初始化并连接数据库", "bm25_query": "connect init database db"},
  {"vector_query": "错误处理与日志记录", "bm25_query": "error exception log logger handle catch"}
]
```
#### 2. 并行独立检索与结果合并（RRF 算法）
针对每个子查询，同时进行向量检索和 BM25 检索。然后我们需要把多路结果合并成一个最终列表。
此时**绝对不能直接把分数相加**（因为向量分数和 BM25 分数量纲不同，且不同子查询的分数不可比）。必须使用 **互惠排名融合** 算法。
**RRF 核心逻辑**：
不再看绝对分数，只看排名位置。公式为：$Score = \sum \frac{1}{k + rank}$ （通常 $k=60$）
*   子查询 1 的向量检索：Doc A 排名 1，Doc B 排名 2
*   子查询 1 的 BM25 检索：Doc A 排名 2，Doc C 排名 1
*   子查询 2 的向量检索：Doc C 排名 1，Doc D 排名 2
*   ...
通过 RRF，Doc A 因为在子查询1的两种检索中都排名靠前，会获得较高得分；Doc C 也会因为跨越不同子查询被命中而获得得分加成。这完美解决了多路、多子查询的合并问题。
#### 3. 针对你项目的特定优化建议
结合你上一轮提到的架构（Tree-sitter 提取，BM25 仅处理实体名转空格），拆分查询时需要特别关注**查询的粒度**：
*   **按代码实体粒度拆分**：因为你的 BM25 索引是按 Tree-sitter 节点构建的，一个节点通常是一个函数或类。所以，一个子查询应该刚好对应“寻找一个特定职责的函数/类”。
*   **示例**：
    *   用户：*"我想看看怎么验证用户权限，然后获取用户详情"*
    *   拆分 1（对应验证权限的方法）：`bm25_query: "check validate permission auth access"`
    *   拆分 2（对应获取详情的方法）：`bm25_query: "get fetch user detail info profile"`
    *   *(如果合并，就会变成 `check validate permission auth get fetch user detail`，这几乎不可能在同一个函数名里出现，导致 BM25 召回失败)*
### 总结
**“拆分到底，独立检索，RRF 融合”** 是解决多意图检索的黄金法则。让向量模型专注捕捉单一且清晰的语义，让 BM25 专注匹配精简且专注的实体命名，才能最大化双路检索的优势。
